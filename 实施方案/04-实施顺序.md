# TeamBlog 实施顺序

> 本文只回答一个问题：**先写哪一行代码，后写哪一行**。方案（做什么、为什么）见 [03-实施方案-v1.2.md](./03-实施方案-v1.2.md)。
>
> 每步都给了「产出物」和「验收」——没有验收标准的步骤不算完成。

---

## 1. 排序原则

**P1 · 表先行。** 数据库 schema 是三个服务的共同契约（Spring 实体、AI 只读视图、前端字段名）。建表成本在第一天是 2 小时，在第 8 天是两天联调。

**P2 · 认证先行。** 除公开浏览外，每个接口都要 `currentUser`。认证没跑通之前写的业务代码，最后都要回头改签名——这是最常见的返工来源。

**P3 · 垂直切片优于水平分层。** 不做"先把所有接口写完"，而是"登录能走通→主页能显示→能发内容"。每完成一条切片，产品就是可演示的；分层做完之前，它一直是 0。

**P4 · API 与页面成对交付。** 一个接口写完 4 小时内要有一个页面在用它。否则等到前端接入时才发现字段设计错了，而那时后端已经有 20 个接口建立在错误假设上。

**P5 · AI 与后台最后。** AI 依赖真实链路（Nginx 的 SSE、真实跨域、真实限流），链路没通之前写的流式代码全是本地假象；管理后台依赖所有接口稳定，早写必改。

**P6 · 规则配单测，当天写。** 积分、连续天数、等级这类纯逻辑，写完当天下测例。攒到最后补测试，等于没测——因为你已经不记得当初的边界假设了。

## 2. 依赖图

```
Flyway V1 ──┬──> Spring 骨架 ──> 认证 ──> 权限矩阵 ────────────────┐
            │                        └──> 个人页 ──> 主页切片 ────┤
            ├──> 成果 ──> 学习内容 ──> 评论/留言 ──> 后台          │
            └──> 打卡 ──> 积分账本 ──> 热力图 ──> 对账任务        │
                                                                  ▼
Next 骨架(可并行, mock 数据) ─────────────────────────────> 全链路部署 ──> AI ──> 硬化
```

关键含义：**部署不是最后一步，而是 AI 的前置条件**。v1.0 原则一说"部署跑通再接 AI"，这里把它落成一个具体门禁（G5）。

## 3. 批次与步骤

### 批次 0 · 地基（0.5–1 天）

目标：一条命令拉起环境，空库能迁移，CI 能跑。

| # | 任务 | 依赖 | 产出 | 验收 |
|---|---|---|---|---|
| 0.1 | 仓库初始化 + 分支策略 + CI 骨架（三服务 lint/build） | — | `teamblog/{web,api,ai,ops}` | CI 三个 job 全绿 |
| 0.2 | `ops/docker-compose.dev.yml`：只起 PG | 0.1 | 一条命令有库 | `psql` 能连，库名 `blog` |
| 0.3 | **Flyway V1：全部表 + 索引 + `v_projects_public` 视图 + `ai_reader` 角色** | 0.2 | `V1__init.sql` | 空库迁移成功，`\d+ users` 正确 |
| 0.4 | 种子：4 管理员 + 8 演示成员 + 60 天打卡 | 0.3 | `R__seed_dev.sql` | 热力图查询有非零结果 |
| 0.5 | Spring 骨架：health、错误信封、RequestId、`ddl-auto=validate` | 0.3 | 可启动的 api | `/api/v1/health` 200 且含 Flyway 版本 |

> **0.3 为什么一次建全表**：后续 6 个批次都要读这些表，分批建会反复改迁移、反复改实体，还容易漏索引。表结构在需求里已经定了（v1.1 §3），不需要边写边发现。

**Gate G0**：`docker compose -f ops/docker-compose.dev.yml up -d` → `mvn -q verify` → 迁移在空库跑通 → 种子后热力图 SQL 返回数据。

### 批次 1 · 认证闭环（2 天）

目标：三种身份能登录、能刷新、能登出，权限矩阵能自动跑。

| # | 任务 | 依赖 | 产出 | 验收 |
|---|---|---|---|---|
| 1.1 | `User` 实体 + Repository + BCrypt(12) + 用户名小写唯一 | 0.3 | 实体与仓储 | 单测：密码哈希往返 |
| 1.2 | JWT 签发/校验（HS256，`sub/role/tv/exp`）+ 过滤器（查库 + tv 比对） | 1.1 | `JwtService`、`JwtFilter` | 有效 token 200，篡改后 401 |
| 1.3 | refresh 轮换 + 重放检测 + 登出 + 清理任务 | 1.2 | `RefreshTokenService` | 同一 rt 用两次，第二次触发全量撤销 |
| 1.4 | 登录限流（IP + 账号）+ 统一失败文案 + `last_login_at` | 1.2 | `LoginAttemptService` | 第 6 次失败返回 429，文案与密码错一致 |
| 1.5 | 邀请注册（`AdminInvite` 一次性 token） | 1.1 | `/invites/**` | 同一邀请用两次，第二次 410 |
| 1.6 | **权限矩阵测试骨架**：3 身份 × 全接口表，断言 200/401/403 | 1.2 | `PermissionMatrixTest` | 成员打 `/api/v1/admin/**` = 403 |
| 1.7 | 前端：登录页、邀请页、会话中间件、导航用户菜单 | 0.1 | 可登录的 UI | 登录后刷新页面仍在线；登出后跳登录 |

> **1.3 的重放检测必须现在做**：它是 refresh token 设计里唯一"出事就晚了"的部分。上线后再加，等于要求用户重新登录一次，而你已经不知道哪些 token 泄露了。

**Gate G1**：`curl` 走完 登录 → 带 at 访问 → 刷新 → 登出 → 用旧 at 访问得 401；权限矩阵 6 条断言全绿；浏览器能登录并看到用户名。

### 批次 2 · 第一条垂直切片（1 天）

目标：一条从数据库到像素的通路，证明三服务能拼起来。

| # | 任务 | 依赖 | 产出 | 验收 |
|---|---|---|---|---|
| 2.1 | OpenAPI 草案（auth/users/projects）+ 生成前端 TS 类型 + typed client | 1.2 | `schema.d.ts` | 前端改错字段名编译报错 |
| 2.2 | 用户列表 + `GET /users/{username}`（含 `email_public` 逻辑） | 1.1 | 两个只读接口 | 关闭邮箱的成员，接口不返回 email |
| 2.3 | 前端主页（静态骨架）+ 个人页（真实数据） | 2.1, 2.2 | 两个页面 | 访客打开 `/u/{username}` 看到真实资料 |

> **2.1 必须在写页面之前**：类型生成是后面所有前端工作的地基。先手写 interface 再回头换生成，等于白写。

**Gate G2**：`/` 和 `/u/member1` 在未登录状态可访问，数据来自数据库（改库里的 bio，页面刷新即变）。

### 批次 4 · 打卡与积分（1 天）

目标：本次项目里唯一有正确性风险的业务。全部规则进单测。

| # | 任务 | 依赖 | 产出 | 验收 |
|---|---|---|---|---|
| 4.1 | 打卡事务（唯一键幂等 + 409）+ 返回 streak/gained/total | 1.6 | `CheckinService` | 连点 5 次：1 成功 4 个 409，总分 +1 |
| 4.2 | `point_events` 账本 + 连续段判定 + 7/14/30 奖励 + 等级函数 | 4.1 | `PointsService`、`LevelCalculator` | v1.1 §4.5 的 11 条用例全绿 |
| 4.3 | 热力图查询（个人/团队/按成员筛选）+ 每日对账任务 | 4.2 | `/stats/heatmap` | 30 天只打卡 = 65 分（口径确认后） |
| 4.4 | 前端热力图组件（纯展示）+ 打卡交互 + 等级徽章 | 4.3 | `Heatmap` 组件 | 打卡后不刷新页面，数字和格子同时变 |

> **4.1 和 4.2 不能拆开做**：打卡和发分在同一个事务里，中间态会让"重复请求"产生半条数据。合并实现，一次 review。

**Gate G4**：`mvn test -Dtest=PointsServiceTest` 全绿；手动把种子数据改成连续 7 天，打卡后 +6；主页热力图有颜色分级。

| # | 任务 | 依赖 | 产出 | 验收 |
|---|---|---|---|---|
| 5.1 | compose 全栈（web/api/ai 空壳/db/nginx）+ 路由 + 健康检查 | 3.x, 4.x | 可访问的预发环境 | 公网域名下登录、发内容、打卡全可用 |
| 5.2 | Flyway 在容器启动时跑通 + 就绪探针 | 5.1 | `migrate` 服务 | 新机器从零起，5 分钟内可用 |
| 5.3 | 备份脚本 + **恢复演练一次** | 5.1 | `backup.sh` + 演练记录 | 还原到临时库，行数断言通过 |

**Gate G5（硬门禁）**：v1.1 §11.3 上线检查的前 4 条在预发环境全绿。**未过此门禁，不排 AI 任务。**

> 违反这条的代价：AI 的 SSE 在本地 dev server 上是好的，一过 Nginx 就变成"转 30 秒一次性出来"，而那时你已经写完前端解析逻辑，会误判是模型慢。

## 5. 常见错序及后果

| 错误顺序 | 后果 | 正确做法 |
|---|---|---|
| 先做首页视觉，后做接口 | 视觉定稿后字段不够用，页面重排 | 先 2.2 接口，页面按真实字段排 |
| 认证没跑通就写业务 | 所有 service 签名要重写一遍 | 批次 1 完整交付 |
| 先写后台管理 | 接口字段反复变，后台跟着改 3 遍 | 批次 6 再做 |
| 先接 AI | Nginx/SSE 问题被误判为模型问题，排查方向全错 | G5 门禁后再开始 |
| 积分规则边写边调 | 没人知道哪版是对的，历史数据无法解释 | 先定规则，当天下单测，再写实现 |
| 表和实体同时"演进" | `ddl-auto=update` 的经典事故：生产少一列 | Flyway 唯一入口 + `validate` |
| 最后两天统一联调 | 三服务 × 8 天的假设差异集中爆发 | 每批次一个 Gate，天天联调 |

## 6. 完成定义（DoD）

任何一步"完成"必须同时满足：

1. 代码在 `main`（或已合并的 PR），CI 绿；
2. 有对应的验收证据（测试名 / curl 输出 / 截图），贴在 PR 里；
3. 该步涉及的接口已进 OpenAPI，前端类型已重新生成；
4. 若涉及权限，权限矩阵用例已覆盖该接口；
5. 若涉及表结构，只有 Flyway 迁移，没有手工改库。

不满足第 4 条的接口一律视为未完成——它会在两周后变成一个洞。
