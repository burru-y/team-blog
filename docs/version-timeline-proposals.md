# 版本时间线：四种呈现方案

目标：从「v1.0 内测」进入「v1.1 测试」时，让人一眼看出**这个版本做了什么**，
而不是一堆提交记录的堆砌。

四个方案按「阅读成本」从低到高排列，下面给出每种的结构、数据来源和推荐场景。
推荐结论放在最后。

---

## 方案 A：版本胶囊（最轻）

### 长什么样

```
首页 / 时间线页顶部

┌────────────────────────────────────────────────────────────┐
│  v1.1 测试版   ·  2026-10-27 发布    ●  当前                │
│  ─────────────────────────────────────────────────────     │
│  公告与更新日志 · 头像上传 · OSS 存储 · 帮助中心             │
│                                          [ 查看全部更新 → ] │
└────────────────────────────────────────────────────────────┘

  v1.0 内测版   ·  2026-10-25                 已完成
  v0.9 内部版   ·  2026-10-20                 已归档
```

### 层次靠什么建立

| 层级 | 手法 |
|---|---|
| 当前版本 | 实心圆点 + 品牌色左边框 + 3 行摘要 |
| 历史版本 | 灰点 + 单行 + 折叠改动 |

### 优点 / 缺点

- 优点：**一眼看完**，不占地方，首页放得下
- 缺点：看不出「每个改动属于哪一类」，信息密度低

### 适合

想让人第一眼看到「有更新」，细节留给二级页。

---

## 方案 B：分类折叠（推荐）

### 长什么样

```
┌─ v1.1 测试版 ─────────────────────── 2026-10-27 ─┐
│  本次共 12 项改动                                  │
│                                                    │
│  ✦ 新增功能            5 项              ⌄ 收起   │
│    · 公告与更新日志                                │
│    · 头像上传                                      │
│    · 帮助中心                                      │
│                                                    │
│  ⚡ 体验改进            4 项              ⌄ 收起   │
│    · 图片改存 OSS，换机器不用搬文件                 │
│    · 静态资源缓存一年，二次访问更快                  │
│                                                    │
│  🐛 修复                3 项              ⌄ 收起   │
│    · 摘要生成因密钥错误失败                         │
│    · 部署后 nginx 指向旧 IP 导致 502                │
└────────────────────────────────────────────────────┘

┌─ v1.0 内测版 ─────────────────────── 2026-10-25 ─┐
│  首次可用版本 · 6 项功能                           │
└────────────────────────────────────────────────────┘
```

### 层次靠什么建立

1. **版本 > 分类 > 条目** 三级缩进，字号递减（16 / 14 / 13）
2. 分类用图标 + 颜色区分：新增（绿）、改进（蓝）、修复（橙）
3. 当前版本展开、历史版本收起，默认只显示最近两个版本
4. 每条改动一行，超过 2 行的细节进二级页

### 数据从哪来

改动条目**不写死在前端**，而是从公告表里的「更新日志」类型记录读：

```sql
announcements (id, version, title, body_md, kind, published_at)
  kind = 'CHANGELOG' 时，body 按分类分段
```

好处：发版时只写一条记录，首页/时间线/公告都从同一处读，不会三处不一致。

### 优点 / 缺点

- 优点：**结构清晰，不用点开就知道改了什么**
- 缺点：版本多了之后页面会很长（解法：分页或只展示最近 3 个）

### 适合

我们这种「改动量中等、想让人认真看」的场景。**推荐这个。**

## 方案 C：横向时间轴（视觉冲击强）

### 长什么样

```
  ●━━━━━━●━━━━━━●━━━━━━●
  v0.9   v1.0   v1.1   下阶段
  内部   内测   测试   待定

        ┌──────────────────────────┐
        │   v1.1 测试版             │
        │   2026-10-27             │
        │                          │
        │   公告与更新日志          │
        │   头像上传                │
        │   帮助中心                │
        │   OSS 图片存储            │
        │                          │
        │   [ 完整更新说明 → ]      │
        └──────────────────────────┘
```

### 层次靠什么建立

- 圆点大小区分「已发布 / 当前 / 计划」
- 只有选中的版本展开卡片，其余是圆点
- hover 或点击切换选中

### 优点 / 缺点

- 优点：**好看**，能表达「项目在推进」
- 缺点：信息一次只能看一个版本；实现成本最高（拖拽、动画、移动端适配）

### 适合

版本节点少（3-5 个）、更看重观感。

> 我们已经有 beUI 的横向可拖拽时间线组件（`/timeline` 页在用），
> 这个方案可以直接复用，不需要新写。

## 方案 D：更新日志流（最像产品）

### 长什么样

```
2026-10-27   新增   ·  公告与更新日志上线
2026-10-27   新增   ·  头像支持上传
2026-10-27   改进   ·  图片改存 OSS
2026-10-26   修复   ·  nginx 指向旧 IP 导致 502
2026-10-25   发布   ·  v1.0 内测版上线
```

类似 Notion / Linear 的 changelog：**一个条目一行，按时间倒序，不分组**。

### 层次靠什么建立

- 只有三列：日期、类型标签、描述
- 类型用彩色小标签，其余全部弱化
- 版本节点用一条更粗的分隔线 + 版本号标出

### 优点 / 缺点

- 优点：**最容易维护**（写一条加一条），也最容易扫读
- 缺点：版本感弱，看不出「这个版本整体做了什么」

### 适合

更新频繁（每周都有）时。

## 我的建议：B 为主，C 为辅

```
Timeline 页
├── 顶部：方案 C 的横向时间轴（已有组件，一眼看项目进度）
└── 下方：方案 B 的分类折叠（每个版本的具体改动）

首页
└── 方案 A 的胶囊卡（只显示当前版本 + 3 行摘要 + 链接）
```

三处共用一个数据源（公告表的 CHANGELOG 记录），发版时只写一次。

### 数据模型（已实现，见 `announcements` 表）

```
id            UUID
version       版本号，如 v1.1（公告可为空）
title         标题
body_md       Markdown 正文
kind          NOTICE（公告）| CHANGELOG（更新日志）
published_at  发布时间
is_pinned     是否置顶
```

### 发版流程

1. 后台 → 公告 → 新建，类型选「更新日志」
2. 版本填 `v1.1`，正文按「新增 / 改进 / 修复」分三节写
3. 发布
4. 首页胶囊、时间线、公告页自动出现，无需改代码
