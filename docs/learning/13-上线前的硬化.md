## 0. 先讲人话

前面七批做的是"功能"。这一批做的全是**功能之外、但没有就出人命**的事：

```
新机器部署 → 库里没有账号 → 而建账号需要管理员邀请 → 死锁
用户忘了密码 → 没有邮件服务 → 账号永久废掉
服务器每天 3 点备份 → 从没还原过 → 真出事时发现备份是空的
HTTP 明文 → refresh token 在网线上裸奔
```

这些都不是"写代码"的问题，而是"把东西交出去"的问题。**它们有个共同特征：本地开发时完全看不见。**

---

## 1. 先理解问题

### 1.1 首启死锁

```
数据库是空的
  ↓
没有任何账号
  ↓
创建账号需要管理员邀请（1.5 做的）
  ↓
创建邀请需要管理员登录
  ↓
没有账号 → 不能登录 → 不能邀请 → 永远没有账号
```

这个循环在开发环境永远发现不了——因为你的开发库里早就有种子账号。

### 1.2 忘记密码 = 账号报废

一期没有邮件服务，所以"忘记密码"不能自助找回。唯一的恢复路径是管理员重置。

**如果没有这个功能**：用户忘了密码，这个账号就永久废了——他的内容还在，但没人能登录。

### 1.3 备份为什么必须演练

```
pg_dump 成功    ≠    备份能还原
```

还原时会遇到：属主不存在、扩展缺失、序列不同步、时区不同、版本不兼容……

**没演练过的备份，等于没有备份。** 而且它比"没有备份"更糟——它让你以为自己有备份。

### 1.4 HTTPS 不只是"加密"

| 保护什么 | 怎么破的 |
|---|---|
| 密码 | 明文 HTTP 下，同一个 WiFi 的人能抓到 |
| access token | 同上 |
| refresh token | **最危险**：有效期 7 天，抓一次能用一周 |

而 HTTPS 的前提是 `Secure` 属性——浏览器只在 HTTPS 下发送带 `Secure` 的 Cookie。

## 2. 设计：四个问题

| 问题 | 答案 | 位置 |
|---|---|---|
| 空库怎么有第一个管理员 | 启动时检测 + 环境变量提供密码 | `AdminBootstrap` |
| 怎么上 HTTPS | Nginx 加 443 + `COOKIE_SECURE=true` | `https.conf` / `compose.tls.yaml` |
| 备份怎么不丢 | 容器内定时 + 先写 tmp 再 mv | `backup/schedule.sh` |
| 忘记密码怎么办 | 管理员重置（会踢掉所有会话） | `AdminUserController` |

## 3. 代码逐行

### 3.1 首启引导

```java
@Override
public void run(ApplicationArguments args) {
    if (userRepository.count() > 0) {
        return;                       // ① 已有用户：完全跳过
    }
    if (properties.password() == null || properties.password().isBlank()) {
        log.warn("数据库里没有任何账号，且未设置 ADMIN_BOOTSTRAP_PASSWORD。...");
        return;                       // ② 没密码：不建，给出提示
    }
    User admin = User.create(username, username + "@teamblog.local",
            passwordEncoder.encode(properties.password()), Role.ADMIN);
    userRepository.save(admin);
    log.warn("已创建初始管理员 '{}'。请立即登录并修改密码...", username);   // ③ 提醒
}
```

**① 为什么"已有用户就完全跳过"**：不做任何"修正"。如果它试图确保"至少有一个管理员"，那么在管理员被全部删除的情况下会自动创建一个——那就成了后门。

**② 为什么不生成默认密码**：`admin/admin123` 这种默认值，等于**每个忘记配置的环境都有一个公开后门**。宁可启动后不能登录，也不要静默地不安全。

**③ 为什么要日志提醒**：一期没有"强制改密"功能，所以只能在日志里喊。

配置：

```yaml
admin:
  bootstrap:
    username: ${ADMIN_BOOTSTRAP_USERNAME:admin}
    password: ${ADMIN_BOOTSTRAP_PASSWORD:}     # 默认空 → 不创建
```

### 3.2 HTTPS 的三个动作

**动作一：Nginx 加 TLS**

```nginx
server {
    listen 80;
    location / {
        return 301 https://$host:8443$request_uri;    # 80 只跳转
    }
}

server {
    listen 443 ssl;
    ssl_certificate     /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;

    location /api/ {
        proxy_pass http://teamblog_api;
        proxy_set_header X-Forwarded-Proto https;     # ← 关键
    }
}
```

**动作二：告诉应用"你在 TLS 后面"**

```nginx
proxy_set_header X-Forwarded-Proto https;
```

不加这个头，应用认为自己在 HTTP 上，可能做出错误判断（比如拒绝设置 Secure Cookie）。

**动作三：打开 Secure Cookie**

```bash
COOKIE_SECURE=true
```

```yaml
jwt:
  cookie-secure: ${COOKIE_SECURE:false}
```

效果：

```
Set-Cookie: rt=...; Path=/api/v1/auth; Secure; HttpOnly; SameSite=Lax
                                      ^^^^^^
```

**为什么 HSTS 先不开**：

```nginx
# add_header Strict-Transport-Security "max-age=15552000" always;
```

HSTS 一旦下发，浏览器会**强制该域名在有效期内只走 HTTPS**。本地用自签证书调试时，你会需要偶尔走 http——而浏览器已经不让你回去了。确认证书没问题后再打开。

### 3.3 备份：三个"便宜但救命"的细节

```sh
target="$BACKUP_DIR/$(date +%F).dump"
tmp="$target.tmp"

pg_dump -Fc -Z6 -f "$tmp" || { rm -f "$tmp"; return 1; }
[ -s "$tmp" ] || { rm -f "$tmp"; return 1; }      # 空文件检查
mv "$tmp" "$target"
```

**细节一：先写 `.tmp` 再 `mv`**。中途失败（磁盘满、连接断）会留下半个文件——如果它叫 `2026-10-24.dump`，恢复时会以为这是完整备份。

**细节二：检查非空**。0 字节的"成功备份"看起来一切正常。

**细节三：备份工具的版本必须 ≥ 数据库版本**

```yaml
backup:
  image: postgres:16-alpine     # 与 db 同版本
```

`pg_dump` 15 去导 16 的库会直接报错。

### 3.4 密码重置：改完必须踢人

```java
public void changePassword(String newPasswordHash) {
    this.passwordHash = requireHash(newPasswordHash);
    this.tokenVersion++;          // ← 关键
}
```

**为什么必须 `tokenVersion++`**：

```
10:00  用户密码被重置
10:01  但攻击者手里的 access token 还是有效的（JWT 是自包含的）
10:01–10:30  攻击者还能继续操作
```

改了密码但旧会话还能用，等于**改密码没改密码**。

**为什么自己改密码也要验证旧密码**：

```
如果被盗用的 access token 就能改密码 → 攻击者可以把真正的用户彻底踢出去、永久接管账号
```

### 3.5 BCrypt 的 72 字节陷阱

```java
int bytes = password.getBytes(StandardCharsets.UTF_8).length;
if (bytes > MAX_BYTES) {   // 72
    throw new BusinessException(VALIDATION_FAILED, "密码太长（BCrypt 只取前 72 字节）");
}
```

**为什么按字节不按字符**：一个汉字 3 字节。用户设了 25 个汉字（看起来"才 25 位"），实际 75 字节——**BCrypt 只处理前 72 字节，剩下的静默丢弃**。

后果：用户改密码时把第 25 个汉字换掉，会发现"密码看起来变了，但旧密码还能登录"。

## 4. 一次"从零部署"的完整时间线

```
T0  新机器克隆仓库
    cp .env.example .env → 填 POSTGRES_PASSWORD / JWT_SECRET / ADMIN_BOOTSTRAP_PASSWORD

T1  docker compose up -d --build

T2  db 起来 → Flyway 自动建表（V1__init.sql）

T3  api 起来 → AdminBootstrap 检测到空库
    → 创建 admin
    → 日志：WARN 已创建初始管理员 'admin'...

T4  管理员登录 → 生成邀请链接 → 发给成员 → 成员注册

T5  开启 HTTPS（compose.tls.yaml + COOKIE_SECURE=true）
    → 登录，Set-Cookie 带 Secure
    → http 访问自动 301 到 https

T6  凌晨 03:10 → backup 容器自动 pg_dump
    → 文件落在卷 backups 里，保留 14 天

T7  某天出问题 → 从备份还原 → 行数逐表核对
```

## 5. 六个容易写错的细节

### 5.1 给首启引导一个默认密码

`admin/admin123` = 每个漏配的环境都有公开后门。宁可启动后登录不了。

### 5.2 只开 HTTPS 不改 `COOKIE_SECURE`

HTTPS 下仍会发出不带 `Secure` 的 Cookie——能用，但一旦有 http 链路就漏。

### 5.3 忘了 `X-Forwarded-Proto`

应用不知道自己在 TLS 后面，可能拒绝设置 Secure Cookie。

### 5.4 备份直接写最终文件名

中途失败留下半个文件，还带着一个看起来正常的日期名。

### 5.5 备份不演练

`pg_dump` 成功 ≠ 能还原。属主、扩展、序列、版本都可能出问题。

### 5.6 改密码不 bump tokenVersion

改完密码，攻击者还能用 30 分钟。

## 6. 反面教材

| 写法 | 后果 |
|---|---|
| 默认管理员密码 | 每个漏配环境都是后门 |
| 首启时"确保至少一个管理员" | 管理员被删光后自动重建 = 后门 |
| 只加 TLS 不改 Secure Cookie | Cookie 仍可能在 http 下被发出去 |
| HSTS 一开始就开 | 自签证书调试时无法回退 |
| 备份直接写正式文件名 | 半成品被当成有效备份 |
| 只做备份不做演练 | 出事时才发现备份是空的 |
| 重置密码不踢会话 | 改了等于没改 |
| 自己改密码不验旧密码 | 被盗 token 可永久接管账号 |

## 9. 自测题

1. 为什么新部署会陷入"没有账号"的死锁？
2. 为什么首启引导不能有默认密码？
3. 为什么"确保至少有一个管理员"反而是后门？
4. HTTPS 之后为什么还要改 `COOKIE_SECURE`？
5. 为什么备份要先写 `.tmp` 再 `mv`？
6. 备份工具版本为什么必须 ≥ 数据库版本？
7. BCrypt 72 字节限制会造成什么误会？
8. 重置密码为什么必须让旧会话失效？

<details>
<summary>答案</summary>

1. 建账号需要管理员邀请，而创建邀请需要管理员登录——空库里没有任何账号，循环无法开始。
2. 默认密码等于每个忘记配置的环境都有一个公开的、已知的登录方式。
3. 如果管理员被全部删除/降级，它会自动再创建一个——攻击者只要删掉管理员就能获得一个新账号。
4. Cookie 的 `Secure` 属性是浏览器行为：只有带 `Secure` 才保证不在 http 下发送；只做 TLS 不改这个属性，一旦有 http 链路 Cookie 仍会明文发出。
5. 中途失败（磁盘满、连接断）会留下半个文件，而它的名字看起来像完整备份。
6. `pg_dump` 的版本必须 ≥ 服务端，低版本导出高版本数据库会报错或产生不兼容格式。
7. BCrypt 只处理前 72 字节，超出部分静默丢弃；按字符算会误判，且中文一字 3 字节，很容易超。
8. 否则攻击者手里的 access token 还能继续用（最长 30 分钟），等于改密码没生效。

</details>

## 10. 术语

| 名词 | 一句话 |
|---|---|
| 首启引导 | 空库启动时自动创建第一个管理员 |
| 死锁（部署） | 没有账号就无法创建账号的循环 |
| HSTS | 让浏览器强制只走 HTTPS 的响应头 |
| `Secure` Cookie | 只在 HTTPS 下发送的 Cookie |
| `X-Forwarded-Proto` | 告诉应用原始请求用的是 http 还是 https |
| 恢复演练 | 真的从备份还原一次并核对数据 |
| 重试攻击 / 定时攻击 | 通过响应时间差异逐字节推断密钥 |
| 明确不做清单 | 记录"权衡后决定不做"的功能，区别于"忘了做" |
