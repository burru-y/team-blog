## 0. 先讲人话

数据库里有一张表 `users`，你的 Java 代码里需要一个"用户"这种对象。

**最先要决定的是：这两者怎么对应上。**

你在 JavaWeb 里可能是这么干的：

```java
// 手写 JDBC：一行一行往外抠
ResultSet rs = stmt.executeQuery("select * from users where id = ?");
User u = new User();
u.setId(rs.getString("id"));
u.setUsername(rs.getString("username"));
u.setPasswordHash(rs.getString("password_hash"));
// ... 15 个字段，写 15 行
```

现在换成 JPA：**类本身就是表的说明**，`rs.getXxx` 那堆样板代码由框架生成。

这一节要回答三个问题：

1. 类怎么写，才能和表对上？
2. 主键从哪来？
3. "改密码之后把所有人踢下线"这种规则，放在哪？

---

## 1. 先理解问题：为什么不能"从表生成类"

很多工具能根据表结构生成 Java 类（Hibernate 逆向工程）。本项目**故意手写**，原因是
"谁是真相"不一样：

| 做法 | 谁说了算 | 后果 |
|---|---|---|
| 表 → 类（生成） | 表是真相 | 改类没用，下次生成被覆盖；改表又和迁移脚本打架 |
| **类 ↔ 表（校验）** | **迁移脚本是真相** | 类写错，启动就失败 |

本项目的选择是第二种：`spring.jpa.hibernate.ddl-auto: validate`。

它做的事很朴素：**应用启动时，把每个 `@Entity` 类的字段和数据库实际列逐个对一遍**。
对不上就启动失败。

```
实体说：password_hash varchar(100) not null
数据库说：password_hash varchar(100) not null
→ 通过

如果实体多了一个 updated_at，而表里没有：
→ 启动报 Schema-validation: missing column [updated_at]
```

这听起来很严格，但它救过很多人：**你不会在线上才发现"少了一列"**。

> 对比 `ddl-auto: update`（很多人图省事用）：Hibernate 会自动给表加列。某天你改了个
> 字段名，它默默加了一列新列，老数据还在旧列里，程序读到的全是 null——
> 而 Flyway 的版本记录还停在 V1，没人知道发生了什么。

## 2. 设计：三个必须回答的问题

### 2.1 类怎么和表对上？—— 注解

```java
@Entity                 // ① 这个类要映射表
@Table(name = "users")  // ② 表名叫 users
public class User {

    @Id                 // ③ 这个字段是主键
    private UUID id;

    @Column(name = "password_hash", nullable = false, length = 100)  // ④ 列名与约束
    private String passwordHash;
}
```

每个注解不写会怎样：

| 注解 | 不写会怎样 |
|---|---|
| `@Entity` | 启动不报错，但 `save()` 时报 `Not an entity` |
| `@Table(name="users")` | 默认类名转表名 → `user`；而 `user` 是 PostgreSQL 保留字，SQL 语法错误 |
| `@Id` | 启动直接报 `No identifier specified for entity` |
| `@Column` | 按字段名推断（驼峰转下划线）。多数情况能对上，但"猜"意味着字段改名时会静默变化 |

### 2.2 主键从哪来？—— UUIDv7

| 方案 | 好处 | 问题 |
|---|---|---|
| 数据库自增 `bigserial` | 简单、索引最友好 | **可枚举**：`/users/1`、`/users/2`，能数出用户量；分库冲突 |
| `UUID.randomUUID()`（v4） | 不可枚举、全局唯一 | **完全随机**，插入时索引乱序 → 写放大 |
| **UUIDv7**（本项目） | 前 48 位是时间戳 → 插入近似顺序；剩余 74 位随机 → 不可枚举 | 要自己生成（JDK 17 没有） |

为什么"时间有序"很重要，见 §3.2。

### 2.3 "改密码要踢人下线"放哪？—— 放进实体

这是本节最重要的设计。

你可能会想在 Service 里写：

```java
@Transactional
public void changePassword(UUID userId, String newHash) {
    User u = repo.findById(userId).orElseThrow();
    u.setPasswordHash(newHash);       // 如果实体有 setter
    u.setTokenVersion(u.getTokenVersion() + 1);   // 别忘了这一行
}
```

问题：**"别忘了这一行"就是 bug 的来源**。改角色的地方也要 +1，软删也要 +1，
三个入口里只要有一个漏了，就会出现"降级了但旧 token 还能用"。

所以实体**只给 getter，不给 setter**，修改必须走带语义的方法：

```java
public void changePassword(String newHash) {
    this.passwordHash = requireHash(newHash);
    this.tokenVersion++;          // 想忘也忘不掉
}

public void changeRole(Role newRole) {
    this.role = Objects.requireNonNull(newRole);
    this.tokenVersion++;
}
```

调用方只能写 `user.changePassword(hash)`，不可能只改一半。

## 3. 代码逐行

### 3.1 `User`：字段与方法

```java
@Entity
@Table(name = "users")
@Getter                                                    // 只生成 getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)         // 给 JPA 用的无参构造器
public class User {

    @Id
    private UUID id;

    @Column(nullable = false, length = 20, updatable = false)
    private String username;

    @Column(name = "password_hash", nullable = false, length = 100)
    private String passwordHash;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 10)
    private Role role;

    @Column(name = "total_points", nullable = false)
    private int totalPoints;

    @Column(name = "token_version", nullable = false)
    private int tokenVersion;

    @Column(name = "deleted_at")
    private OffsetDateTime deletedAt;

    @CreationTimestamp
    @Column(name = "created_at", nullable = false, updatable = false)
    private OffsetDateTime createdAt;
}
```

**为什么无参构造器是 `protected` 而不是 `public`**：

JPA 用反射创建对象，必须有它；但业务代码不该用它——

```java
User u = new User();   // 如果 public，这行能编译
u.getRole();           // null；它是个"不合法的用户"，但编译器不管
```

`protected` 挡住了包外误用，同时满足 JPA 的要求。

**为什么只有 `@Getter`**：见 §2.3。给了 `setRole`，就有人绕过 `tokenVersion++`。

**`@Enumerated(EnumType.STRING)` 为什么必须写**：默认是 `ORDINAL`，存的是枚举下标：

```java
enum Role { ADMIN, MEMBER }            // ADMIN=0, MEMBER=1
```

哪天你在前面加一个 `VISITOR`：

```java
enum Role { VISITOR, ADMIN, MEMBER }   // VISITOR=0, ADMIN=1, MEMBER=2
```

数据库里原本代表 `ADMIN` 的 `0`，现在被读成 `VISITOR`——**一个"给访客看的接口"，
突然把管理员权限给出去了**，而且没有任何报错。

### 3.2 `UuidUtils`：那 8 行位运算

```java
public static UUID v7() {
    long unixTsMs = System.currentTimeMillis() & 0xFFFF_FFFF_FFFFL;    // ①
    long hi = ThreadLocalRandom.current().nextLong();
    long lo = ThreadLocalRandom.current().nextLong();

    long msb = (unixTsMs << 16) | 0x7000L | (hi >>> 52 & 0x0FFFL);      // ②
    long lsb = (lo & 0x3FFF_FFFF_FFFF_FFFFL) | 0x8000_0000_0000_0000L;  // ③

    return new UUID(msb, lsb);
}
```

**先解释符号**（`00-必读`没细讲，这里补）：

| 符号 | 叫法 | 作用 | 例子（4 位二进制示意） |
|---|---|---|---|
| `&` | 按位与 | 只有两边都是 1 才是 1 → **只保留想要的位** | `1010 & 1100 = 1000` |
| `\|` | 按位或 | 有一个是 1 就是 1 → **把某些位设成 1** | `1010 \| 1100 = 1110` |
| `<<` | 左移 | 整体往左挪，右边补 0（= ×2ⁿ） | `0001 << 2 = 0100` |
| `>>>` | 无符号右移 | 整体往右挪，左边补 0（= ÷2ⁿ） | `1000 >>> 2 = 0010` |

**逐句读**：

① `unixTsMs` = 当前毫秒时间戳，只留低 48 位。
`0xFFFF_FFFF_FFFF` 是 48 个 1，与它做 `&` 就是"只留低 48 位"（时间戳用 48 位存，
够用到公元 10889 年）。下划线只是给人看的分隔符，编译时忽略；结尾 `L` 表示这是 `long`
（不加会被当 `int`，48 位放不下）。

② 拼 `msb`（高 64 位）：

```
msb = [ unix_ts_ms 48 位 ][ 0111 版本号 ][ rand_a 12 位 ]
        └─ unixTsMs << 16 挪到最左，右边空出 16 位
                              └─ 0x7000L 把版本位写成 0111（=7）
                                            └─ hi 的高 12 位填进来
```

③ 拼 `lsb`（低 64 位）：

```
lsb = [ 10 变体 ][ rand_b 62 位 ]
       └─ 0x8000... 把最高两位置为 10
                     └─ lo 的低 62 位（用 & 掩码清掉最高 2 位）
```

**为什么用 `|` 而不是 `+`**：`+` 可能进位污染相邻的位；`|` 只置位，在目标位已知是 0 时
更安全，意图也更明确。

**为什么"时间有序"能加速插入**：数据库索引是按 key 排好序的。自增 id 永远插在最后一页；
完全随机的 v4 可能插到任意页，页满了就要"分裂"（搬一半数据到新页）。v7 前 48 位单调递增，
插入集中在最右页，接近自增的性能。

### 3.3 静态工厂：不变量集中在一处

```java
public static User create(String username, String email, String passwordHash, Role role) {
    User user = new User();
    user.id = UuidUtils.v7();
    user.username = normalizeUsername(username);
    user.email = normalizeEmail(email);
    user.passwordHash = requireHash(passwordHash);
    user.role = Objects.requireNonNull(role);
    user.emailPublic = false;
    user.totalPoints = 0;
    user.tokenVersion = 0;
    return user;
}
```

为什么不让 Service 自己拼：主键、归一化、初始积分、`token_version=0` 这些是**不变量**。
散到三个 Service 里各拼一次，迟早有一个忘了把 `tokenVersion` 置零。

**归一化为什么用 `toLowerCase(Locale.ROOT)`**：

```java
"I".toLowerCase()            // 土耳其语环境下 → "ı"（无点 i）
"I".toLowerCase(Locale.ROOT) // 永远 → "i"
```

同一份数据在不同语言环境的服务器上变成不同用户名，唯一键就形同虚设。

**为什么要归一化**：数据库有 `uq_users_username` 唯一键，`Admin` 和 `admin` 在它看来是两个
不同的值。不归一化，用户能注册出两个"看起来一样"的账号，登录输哪个全看运气。

### 3.4 `UserRepository`：为什么它没有实现类

```java
public interface UserRepository extends JpaRepository<User, UUID> {
    Optional<User> findByUsername(String username);
    boolean existsByUsername(String username);

    @Query("select u from User u where u.username = :username and u.deletedAt is null")
    Optional<User> findActiveByUsername(@Param("username") String username);
}
```

你在 JavaWeb 里一定写过 `UserDaoImpl`，里面是 `PreparedStatement` 和 `rs.getString`。
这里**一个实现类都没有**，却能跑，原因是两层：

**第一层：Spring Data 启动时生成动态代理。** 你声明的接口被一个代理类包住，调用时转发给
`SimpleJpaRepository`（它提供了 `save/findById/delete/count` 等通用实现）。

**第二层：方法名被解析成查询。**

```
findByUsername  →  select * from users where username = ?
```

| 写法 | 生成的 SQL 片段 |
|---|---|
| `findByUsername(String u)` | `where username = ?` |
| `existsByUsername(String u)` | `select count(*) > 0 ...` |
| `findTop10ByOrderByCreatedAtDesc()` | `order by created_at desc limit 10` |

方法名解析不了的（比如 `lower(email) = ?`），才用 `@Query` 写 JPQL：

```java
@Query("select u from User u where u.username = :username and u.deletedAt is null")
```

> **JPQL 不是 SQL**：它写的是"实体和属性名"（`User`、`u.deletedAt`），框架再翻译成
> 真实表名列名（`users`、`deleted_at`）。好处是实体改名时编译期就能发现。

**为什么返回 `Optional<User>` 而不是 `User`**：

```java
User u = repo.findByUsername("nobody");   // null
u.getRole();                               // NullPointerException，堆栈在很远的调用处
```

`Optional` 把"可能没有"写进类型，调用方必须先处理这个分支。

**为什么要两套查询（active 与非 active）**：见 §5.2 软删除。

### 3.5 `PasswordConfig`：密码为什么要慢

```java
@Configuration
public class PasswordConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(12);
    }
}
```

`@Configuration` + `@Bean` = 这个方法由 Spring 调用一次，返回值放进容器，谁需要就注入谁。

BCrypt 的成本因子 12 意味着 2¹² = 4096 轮，单次约 250ms：

| 谁在等 | 感受 |
|---|---|
| 正常用户登录 | 250ms，无感 |
| 攻击者猜密码 | **每猜一个也要 250ms**，8 位密码空间下等于几百年 |

如果你用 `SHA-256(password)`：单次微秒级，一张显卡每秒几十亿次——等于明文。

**为什么用 `matches()` 而不是 `equals()`**：每次 `encode` 的盐不同，同一个密码两次结果不同。
`matches` 会从存储的哈希里解析出盐和成本因子，重算再比。

## 4. 一次保存的完整时间线

这是 JPA 最反直觉的地方，也是我踩过的坑（测试里 `createdAt` 是 null）。

```java
User user = User.create("member1", "m@example.com", hash, Role.MEMBER);
userRepository.save(user);            // ← 你以为已经插库了
userRepository.findById(user.getId()); // ← 其实还没
```

真正发生的事：

```
t=0ms   create()       → 内存里一个对象，id 已经生成（v7 在应用侧生成）
t=1ms   save()         → 放进"持久化上下文"，**没有 SQL**
t=2ms   findById()     → 命中上下文（一级缓存），返回同一个对象
t=2ms   getCreatedAt() → null！因为 INSERT 还没执行，@CreationTimestamp 还没赋值
──────────────── flush 的边界 ────────────────
t=3ms   saveAndFlush() → 此刻才 INSERT，@CreationTimestamp 赋值
t=4ms   commit()       → 事务提交
```

改 `saveAndFlush` 就对。**这个坑说明一件事：JPA 的 "save" 是"登记"，不是"保存"。**

## 5. 五个容易写错的细节

### 5.1 实体加了 `@Data`

Lombok 的 `@Data` 会生成 `equals/hashCode`（基于所有字段），还会生成 setter。

- `equals` 踩代理：Hibernate 给懒加载生成子类，`getClass()` 不同，`equals` 可能判不等
- setter 绕过业务规则（见 §2.3）

规范 J-22：实体只用 `@Getter`。

### 5.2 软删除：可见性 ≠ 唯一性

```java
findActiveByUsername(...)   // 加 deletedAt is null：给登录、个人页
existsByUsername(...)       // 不加过滤：给"这个用户名还能不能用"
```

为什么占用检查**必须**包含已软删的账号：

```
1. 张三离职，被软删（行还在，username 仍是 zhangsan）
2. 新人想注册 zhangsan
3. 如果只查未删的 → 认为"可用"
4. INSERT → 撞上 uq_users_username → 500
```

数据库的唯一约束**根本不认识 `deleted_at`**。软删除把"表上的唯一性"和"业务上的可见性"
拆成了两个口径，代码里必须显式区分。

### 5.3 映射了 `updated_at`

`users` 表没有这一列（V1 漏了）。如果你在实体里写 `private OffsetDateTime updatedAt`，
`ddl-auto=validate` 会在启动时报 `missing column`。

正确做法：将来加 `V2__add_users_updated_at.sql`。**不要改 V1**——已执行的迁移改了，
各环境的校验和就不一致，启动失败（D-02）。

### 5.4 用 `LocalDateTime` 存时间

它没有时区。中国服务器写 10:00，UTC 服务器读出来也是 10:00，但那是 8 小时之后的
另一个瞬间。用 `OffsetDateTime`（带偏移）。

### 5.5 在实体里调 `LocalDate.now()`

**没法测**。"连续 7 天奖励"这种规则，你总不能等到真的连续 7 天。时间要从 `Clock` 注入
（`config/ClockConfig`），测试里塞一个固定时刻。

## 6. 反面教材

| 写法 | 后果 |
|---|---|
| `@Enumerated` 不写参数 | 存 0/1，枚举顺序一变语义全错，且无报错 |
| 实体加 `@Data` / `@Setter` | setter 能绕过 `tokenVersion++`，等于留了提权后门 |
| Controller 直接返回 `User` | 序列化出 `passwordHash`、`tokenVersion`，一条记录泄露全站 |
| `ddl-auto: update` | 生产上 Hibernate 自动加列，老数据在旧列里，读出来全是 null |
| 改 V1 迁移 | 各环境校验和不一致，启动失败 |
| `toLowerCase()` 不带 Locale | 土耳其环境 `I` → `ı`，用户名"找不到" |
| `save()` 后直接读 `createdAt` | 还是 null，INSERT 没发生 |

## 7. 测试怎么写

### 7.1 两层，各有各的原因

| 测试 | 起 Spring？ | 覆盖什么 |
|---|---|---|
| `UserTest`（7 个） | 否 | 纯对象：哈希往返、归一化、`tokenVersion` 副作用 |
| `UserRepositoryTest`（3 个） | 是 | **真写 PostgreSQL 再读回** |

**为什么纯对象测试不起容器**：起了容器，失败原因会藏在 bean 装配、数据源、Flyway 一堆日志里；
纯对象测试挂了，堆栈直接指着你那一行。

**为什么还需要真库测试**：`ddl-auto=validate` 只校验"列存在、类型兼容"，
**不校验驱动层能否往返**。比如 `OffsetDateTime ↔ timestamptz` 看着类型对，
但时区偏移可能在写库时被静默丢掉，只有读回来比对值才能发现。

### 7.2 一个真实的故事

第一次跑测试，`createdAt` 断言失败（null）。原因见 §4——`save()` 之后 `findById()` 拿到的是
缓存里那个还没赋值的对象。改成 `saveAndFlush` 才对。

**这个坑如果是 mock 仓储，永远发现不了。**

<summary>答案</summary>

1. `save()` 只把对象登记进持久化上下文，INSERT 要到 flush 才执行；`@CreationTimestamp` 在 INSERT 那一刻才赋值。
2. 存的是枚举下标。在前面插入新值时，旧数据的 `0` 含义变了，权限直接错位且无报错。
3. 改密码/改角色/软删都要让 token 失效，三个入口容易漏；放进实体方法里，想忘也忘不掉。
4. 可见性面向业务（登录要当它不存在），唯一性面向数据库（唯一约束不认识 `deleted_at`）。占用检查若排除软删行，新人注册会撞唯一键报 500。
5. 前 48 位单调递增，插入集中在索引最右页，避免随机 key 造成的页分裂与写放大。
6. 每 +1 计算量翻倍，16 时单次可能 4 秒以上——正常用户在登录页干等，而攻击者是离线慢慢算，不划算。
7. Hibernate 会自动改表结构，可能与迁移文件、其它环境不一致；最坏是生产少一列，排查半天。
8. 纯对象测试定位故障快；真库测试能发现 mock/validate 发现不了的映射问题（如时区偏移丢失）。

</details>

## 10. 术语

| 名词 | 一句话 |
|---|---|
| 实体（Entity） | 映射数据库表的 Java 类 |
| 持久化上下文 | JPA 的"待写入清单"，flush 时才发 SQL |
| flush | 把上下文里的改动真正发给数据库 |
| 一级缓存 | 同一事务里，同一个 id 查到的是同一个对象 |
| 脏检查 | 改了实体字段，提交时自动生成 UPDATE（不用调 save） |
| 派生查询 | 由方法名生成 SQL，如 `findByUsername` |
| JPQL | 面向实体/属性的查询语言，不是 SQL |
| 软删除 | 不删行，只标记 `deleted_at` |
| 唯一约束 | 数据库层面的"不许重复"，不认识软删标记 |
| 加盐 | 哈希时掺随机值，让相同密码结果不同 |
