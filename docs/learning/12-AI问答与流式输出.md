# 12 · AI 问答：SSE、流式与 prompt 评测（零基础版）

> **前置**：[00-零基础必读](./00-零基础必读.md)（HTTP 报文）、[07-前端骨架](./07-前端骨架与登录页.md)（同源代理）。

> **对应门禁**：批次 7，Gate G7。

## 0. 先讲人话

普通接口是这样的：

```
浏览器：给我数据
服务器：（想 3 秒）给你整段数据
浏览器：（3 秒后）一次性显示
```

流式输出是这样的：

```
浏览器：给我数据
服务器：给你一个字（0.1 秒后）
        再给你一个字
        ...
浏览器：逐字显示，用户感觉"它正在说"
```

**同样总耗时，体验完全不同。** ChatGPT 那种"打字机效果"就是流式。

但流式很容易被毁掉：**任何一层中间代理如果把响应攒起来再发，用户看到的就还是"转半天、一次性出现"**。

---

## 1. 先理解问题

### 1.1 为什么 AI 不走 Spring 转发

最自然的想法是：

```
浏览器 → Spring（鉴权）→ FastAPI（AI）→ 模型
```

但 SSE 是**长连接**：从第一个字到最后一个字，连接一直开着。经过 Spring 转发意味着：

- 一个请求占住一个 Tomcat 线程（默认 200 个）
- 20 个用户同时问，就占掉 10% 的线程池
- 2C4G 的机器扛不住

所以架构改成：

```
/ai/*     →  ai:8000（FastAPI）
/api/*    →  api:8080（Spring）
```

**Nginx 直连 AI**，只有 `/v1/summarize` 这种"内部端点"由 Spring 走容器网络调用（并带 HMAC 签名）。

### 1.2 三个能让流式失效的地方

| 位置 | 问题 | 后果 |
|---|---|---|
| Nginx | `proxy_buffering` 默认 **on** | 响应被攒成一整块 |
| 应用 | 没设 `X-Accel-Buffering: no` | Nginx 不知道这是流 |
| 中间层 | 空闲超时太短 | 模型"思考"15 秒，连接被掐 |

三个都得处理。少一个，现象都是"转很久然后一次性出现"——**而你会以为是模型慢**。

### 1.3 为什么不能用 `EventSource`

浏览器原生有 `EventSource` 吃 SSE，但它只能发 **GET** 请求：

```js
new EventSource("/ai/v1/project-chat?question=...")   // 只能是 GET
```

而问答必须 POST（问题在 body 里，还可能很长）。所以只能手写：

```js
const response = await fetch(url, { method: "POST", body });
const reader = response.body.getReader();
```

### 1.4 prompt 为什么必须评测

> 方案原话：prompt 在 20 条上表现不稳定的话，前端做得再好也只是把错误答案渲染得很流畅。

模型有个讨厌的特性：**它不知道就编**。我们的场景是"只依据项目资料回答"，如果它编了，用户会以为项目真的用了那个技术。

这类问题只能靠**用固定用例反复测**来发现，看代码看不出来。

## 3. 代码逐行

### 3.1 Nginx：一行配置定生死

```nginx
location /ai/ {
    proxy_pass http://teamblog_ai/;
    proxy_http_version 1.1;
    proxy_buffering off;          # ← 不关这一行，流式变成"一次性"
    proxy_cache off;
    proxy_read_timeout 300s;      # 模型可能要想很久，默认 60s 会掐断
    chunked_transfer_encoding on;
}
```

`proxy_buffering` 默认是 `on`——Nginx 会把上游响应攒在内存/临时文件里，等攒够了再发给客户端。对普通网页这是优化（减少客户端慢速连接占用的时间），对 SSE 是灾难。

### 3.2 应用：告诉 Nginx "别缓冲"

```python
return StreamingResponse(
    event_stream(),
    media_type="text/event-stream",
    headers={
        "Cache-Control": "no-cache, no-store",
        "X-Accel-Buffering": "no",   # 关键
        "Connection": "keep-alive",
    },
)
```

**为什么两个都要**：`proxy_buffering off` 是"这一层关掉"；`X-Accel-Buffering: no` 是"应用请求代理别缓冲"。后者让你换代理（Caddy、ALB）时不用改配置。

> 有意思的是：Nginx 会**消费**这个头，所以客户端看不到它。测试时别指望从响应头里找到它。

### 3.3 心跳：防止空闲被掐

```python
async def _with_heartbeat(source, request):
    iterator = source.__aiter__()
    while True:
        try:
            chunk = await asyncio.wait_for(iterator.__anext__(), timeout=15)
        except StopAsyncIteration:
            return
        except asyncio.TimeoutError:
            yield ""          # 调用方据此发 ping
            continue
        yield chunk
```

外层：

```python
if chunk == "":
    yield b": ping\n\n"    # SSE 注释行，前端会忽略
    continue
```

**为什么需要**：模型有时候要想 10–20 秒才吐第一个字。中间代理（Nginx、CDN、云负载均衡）都有空闲超时，连接被静默掐断，前端表现为"卡住然后报错"。

`:` 开头是 SSE 的注释语法，客户端会忽略——正好用来做心跳。

### 3.4 前端：SSE 解析没有"一条消息 = 一个事件"

```ts
let buffer = "";
for (;;) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });

  let boundary = buffer.indexOf("\n\n");
  while (boundary >= 0) {
    const block = buffer.slice(0, boundary);
    buffer = buffer.slice(boundary + 2);      // 保留残余
    handleBlock(block, handlers);
    boundary = buffer.indexOf("\n\n");
  }
}
```

**这是最容易写错的地方**。TCP 是字节流，不是消息流：

```
一次 read() 可能拿到：
  "event: delta\ndata: {\"text\":\"你\"}\n\nevent: delta\ndata: {...}"   ← 两个半事件
  或者
  "event: del"                                                          ← 半个事件
```

如果每次 `read()` 就当整体解析，会随机丢字、JSON 解析失败。

正确做法：**累积到 buffer，按 `\n\n` 切，切不出来的留在 buffer 等下次**。

### 3.5 关页面就停：别烧 token

```tsx
useEffect(() => {
  return () => controllerRef.current?.abort();   // 卸载时
}, []);

function close() {
  controllerRef.current?.abort();                // 点关闭时
  ...
}
```

服务端：

```python
async for chunk in _with_heartbeat(stream_answer(settings, prompt), request):
    if await request.is_disconnected():
        stopped = True
        logger.info("客户端断开，停止生成")
        break
```

**为什么认真做这件事**：不做的话，用户关掉抽屉后模型还在生成——**按 token 计费**，账单上看不出来是"用户关了页面"。

服务端日志应该是这样：

```
INFO teamblog.ai: 生成被取消（客户端断开）
```

这条日志来自 `asyncio.CancelledError` 分支，说明包装 httpx 的**上游请求真的被取消了**。

### 3.6 provider 抽象：没有 key 也能验

```python
async def stream_answer(settings, prompt):
    if settings.provider == "mock":
        async for chunk in _mock_stream(prompt):
            yield chunk
        return
    async for chunk in _openai_compatible_stream(settings, prompt):
        yield chunk
```

**mock 不是返回固定文本**——它把问题回显，并逐字发送：

```python
answer = f"（mock 模式）你的问题是：{question}\n\n如果这段文字是「逐字出现」的..."
for char in answer:
    await asyncio.sleep(0.01)
    yield char
```

好处：没有 API key 时，**整条链路（含 Nginx 缓冲）都能端到端验证**。接真模型只改环境变量：

```bash
AI_PROVIDER=deepseek
AI_API_KEY=sk-xxx
```

### 3.7 成本熔断

```python
if not quota.try_consume(_client_key(request)):
    raise HTTPException(status_code=429, detail="今天的提问次数已用完")
```

两层限制：

- **每人每天 N 问**（按 IP + 日期，跨天自动换桶）
- **单次问题长度**（防止有人把整篇论文塞进 prompt）

### 3.8 HMAC：内部端点也要验身份

```python
expected = hmac.new(settings.internal_hmac_secret.encode(),
                    payload.content.encode(), hashlib.sha256).hexdigest()
if not hmac.compare_digest(expected, x_internal_signature):
    raise HTTPException(status_code=403, detail="签名无效")
```

**为什么需要**：AI 服务在容器网络里，任何容器都能直连 `ai:8000`。Nginx 挡了 `/ai/v1/summarize` 一层，但"只有一层"不够。

`hmac.compare_digest` 而不是 `==`：**定时攻击**——普通字符串比较在第一个不同字节就返回，攻击者能通过响应时间逐字节猜出签名。

### 3.9 prompt 评测：自动 + 人工两层

20 条用例分四类：

| 类型 | 数量 | 检查 |
|---|---|---|
| answerable | 9 | 必须命中关键词（不能答非所问） |
| absent | 6 | 必须说"资料里没有写"（不能编） |
| injection | 3 | 绝不能输出系统提示词 |
| out_of_scope | 2 | 应当拒绝（写诗、问天气） |

自动判定只能覆盖**可枚举的硬性要求**：

```python
if case.get("expect_any"):
    return any(k in answer for k in case["expect_any"]), ...

if case.get("expect_refusal"):
    return any(m in answer for m in REFUSAL_MARKERS), ...

for text in case.get("forbid", []):
    if text in answer:
        return False, f"泄露了禁止内容：{text}"
```

**"有没有编造"最终只能靠人读。** 所以脚本会把每条问答原文写进 `report.md`。

## 4. 一次提问的完整时间线

```
T0  访客点开项目详情页 → 点"问问 AI" → 输入问题
    → POST /ai/v1/project-chat（经 Nginx）
    → Nginx：proxy_buffering off，直接转发

T1  FastAPI
    → 查 v_projects_public（只读视图，AI 不碰业务表）
    → 拼 prompt（系统指令 + 项目资料 + 问题）
    → 额度检查（每人每天 N 次）
    → 调模型，流式返回

T2  第一个字到达（实测 1.8s）
    → 前端 reader.read() 收到 "event: delta\ndata:{...}"
    → setState，界面出现第一个字

T3  后续逐字到达（每块几十毫秒）
    → 前端不断追加（每块可能含多个事件，也可能只有半个）

T4  模型说完
    → 服务端发 "event: done"
    → 前端结束 loading

T5  访客直接关掉抽屉
    → AbortController.abort()
    → 服务端 is_disconnected() 为真 / CancelledError
    → 日志 "生成被取消（客户端断开）"，上游请求真的被取消
```

## 5. 六个容易写错的细节

### 5.1 只关了一半缓冲

只改 Nginx 不加 `X-Accel-Buffering`，换代理环境就复发。两个都做。

### 5.2 每次 `read()` 当一条消息

TCP 分包不保证边界。必须累积 buffer、按 `\n\n` 切、保留残余。

### 5.3 不处理断开

用户关了页面，模型还在跑，token 还在烧。

### 5.4 用 `EventSource`

它只能 GET。GET 里放长问题会进 URL，日志、浏览器历史都会记下来。

### 5.5 不做额度限制

一个脚本能把你的 API 余额刷光。

### 5.6 跳过 prompt 评测

前端做得再好，也只是把错误答案渲染得更流畅。

## 6. 反面教材

| 写法 | 后果 |
|---|---|
| 不关 `proxy_buffering` | 流式变"转 30 秒一次性出现"，且你会误判成模型慢 |
| 没有心跳 | 模型思考 15 秒，连接被中间层掐断 |
| SSE 不处理分包 | 随机丢字、JSON 解析失败 |
| 断开不停止生成 | 关页面后继续烧钱 |
| `EventSource` 发问题 | 长文本进 URL，日志/历史泄露 |
| HMAC 用 `==` 比较 | 定时攻击可逐字节猜签名 |
| mock 返回固定字符串 | 验证不了"请求真的到了模型层" |

N1–N6  资料里没有   → 全部明确拒答

三条最能说明问题的回答原文：

## 9. 自测题

1. 为什么 AI 服务不让 Spring 转发？
2. `proxy_buffering` 默认是开的，为什么对网页是优化、对 SSE 是灾难？
3. 为什么不能用 `EventSource` 做问答？
4. 为什么 SSE 客户端必须自己维护 buffer？
5. 心跳为什么用 `: ping` 这种形式？
6. 用户关掉抽屉后，服务端怎么知道该停？
7. prompt 评测里，什么东西自动判定不了？

<details>
<summary>答案</summary>

1. SSE 是长连接，经 Spring 转发会占住 Tomcat 线程（默认 200 个），20 个并发就吃掉 10%。
2. 攒起来再发能减少慢速客户端占用服务端资源；但 SSE 的价值恰恰是"边生成边发"，攒起来就失去了意义。
3. 它只能发 GET，而问题需要 POST（长文本放 URL 会进日志和历史）。
4. TCP 是字节流不保证消息边界，一次 read 可能是多个事件、也可能只有半个事件。
5. `:` 开头是 SSE 的注释语法，客户端会忽略，正好用来保活。
6. `AbortController` 中止请求 → 服务端 `request.is_disconnected()` 为真或触发 `CancelledError` → 停止调用模型。
7. "有没有编造"——它需要对内容正确性的判断，只能人读。

</details>

## 10. 术语

| 名词 | 一句话 |
|---|---|
| SSE | Server-Sent Events，服务器单向推送文本流 |
| 流式输出 | 边生成边发送，而不是等全部完成 |
| `proxy_buffering` | Nginx 是否把上游响应攒起来再转发 |
| 心跳 | 定期发一个无意义的数据包，证明连接还活着 |
| `AbortController` | 浏览器取消 fetch 的机制 |
| provider 抽象 | 把"用哪个模型"隔离成一个可替换的实现 |
| 成本熔断 | 达到额度就拒绝，防止费用失控 |
| 提示词注入 | 在输入里塞指令，试图让模型违背原指令 |
| 定时攻击 | 通过响应时间差异逐字节猜出密钥 |

## 11 · 追加：把"AI 好蠢"拆成三个问题

> 这一节是上线后真实反馈驱动的改动，保留原始现象与数据，因为**"为什么改"比"改成什么"更值得记**。

### 现象

用户拿一个内容全是 `test` 的项目问 AI，得到的回答是：

> 项目资料里没有写"test"具体是什么。
> 资料中仅显示：标题：test、类型：PROJECT、描述：test、项目内容：test。

用户的评价是：「这也太蠢了」。

### 先别急着改 prompt

看到"回答很蠢"，第一反应通常是改 prompt。但这次要先把现象拆开——**它是三个独立问题叠在一起**：

| # | 问题 | 属于哪一层 |
|---|---|---|
| 1 | 项目资料本身是 `test`，没有可回答的信息 | **数据** |
| 2 | 模型被要求"不许编"后，把知道的字段全复述一遍 | **产品/提示词** |
| 3 | 偶尔一个字都不输出（空白气泡） | **模型参数** |

只改第 2 条，第 1 条的"没东西可答"依然存在；只管第 2 条，第 3 条照样会出现空气泡。

### 问题 1：资料不足时，根本不该调模型

```python
if prompts.content_is_sparse(project, settings.min_usable_content_chars):
    return _plain_stream(prompts.SPARSE_CONTENT_REPLY, remaining)
```

```python
def content_is_sparse(project: dict, min_chars: int) -> bool:
    body = f"{project.get('description') or ''}{project.get('content_md') or ''}".strip()
    return len(body) < min_chars
```

**为什么这是产品层而不是 prompt 层**：prompt 能让它"少说两句"，但没法让 `test` 里长出信息。
从"不存在的资料"里挤回答，最好的结果也只能是一句正确的废话。

固定文案要**有用**，不是道歉：

> 这个项目的资料还很少（标题、描述、正文看起来都是占位内容），没法基于资料回答。
> 可以让作者补充项目介绍后再来问；或者换个问题，比如它解决了什么问题、用了什么技术。

顺带省了 token——占位项目点一次 AI，现在零成本。

**阈值为什么看"描述 + 正文"而不算标题**：标题通常只有一个名字（`test`、`我的项目`），
本身不含可回答的信息。把它算进长度，会把"只有标题"的项目误判成"有内容"。

### 问题 2：prompt 要禁止"复述字段"

原来的 prompt 只说"资料中没有的信息直接说没有写"，模型于是把**已有的字段**逐条列出来凑长度。
补一句就行：

```text
如果资料明显不足以回答（例如正文只有几个字），用一句话说明资料不足并建议用户换个问题，
不要罗列资料里的字段，也不要重复同一句结论。
```

这是 prompt 能解决的部分——**它不改变"没有信息"这个事实，只改变"怎么承认"**。

### 问题 3：思考模式在偷偷吃掉预算

`deepseek-v4-pro` 默认**开思考模式**（`effort=high`）：先输出思维链，再输出正文。
思维链也消耗 `max_tokens`。

于是出现了"空白气泡"：`max_tokens=600` 被推理吃光，正文一个字都没剩。

两个修法一起上：

```python
# 1. 预算按档位给足
member_max_tokens: int = 1500

# 2. 真的一个字都没产出时，报错而不是静默返回空
if produced == 0 and not stopped:
    yield sse("error", {"code": "EMPTY_ANSWER", "message": "这次没答上来，请再问一次"})
    return
```

**静默返回空比报错更糟**：用户看到一个空气泡，不知道是没回答、还是没加载出来。

顺便实测了关掉思考的收益（同一问题）：

| 档位 | 模型 | 首字延迟 |
|---|---|---|
| 匿名 | `deepseek-flash` | 0.95 – 1.11s |
| 成员（关思考） | `deepseek-v4-pro` | 1.40 – 1.42s |
| 成员（开思考） | `deepseek-v4-pro` | **2.40 – 9.21s** |

我们做的是"只依据资料回答"的检索式问答，思考带来的增益不明显，但 9 秒的首字延迟是实打实的。
于是默认关掉（`AI_THINKING=disabled`），留了开关。

> **一个可复用的判断**：优化"质量"之前，先量一下"延迟"。
> 用户对 3 秒以上的等待非常敏感，而"更聪明的回答"很多时候感知不到。

### 顺带：为什么要分档

同一个接口，两类调用者的需求完全不同：

| | 访客 | 成员 |
|---|---|---|
| 频率 | 偶尔问一两句 | 天天用 |
| 值得给的模型 | 便宜、快 | 更强、更长 |
| 被刷的损失上限 | 小 | — |

所以分两档，并且**额度键也不同**：

```python
quota_key = f"user:{subject}" if logged_in else f"ip:{client_ip}"
```

匿名按 IP（他只有 IP 这个身份），成员按用户 id——**换个 IP 也刷不动成员额度**。

### 身份怎么传，边界在哪

前端把已有的 `accessToken` 放进请求头：

```ts
headers: {
  "Content-Type": "application/json",
  ...(token ? { Authorization: `Bearer ${token}` } : {}),
}
```

AI 服务用**和 Spring 共享的 JWT 密钥**验签，只读 `sub`：

```python
claims = jwt.decode(token, secret, algorithms=["HS256"])
```

**这不算"AI 做用户认证"**（方案 §1.2 明确禁止它查库、管会话）。它只验证一个已经签好的声明：

- 不查用户表 → 没有额外查询、没有额外失败点
- 验签失败 → **按匿名处理，不报 401**（匿名本来就允许访问，报错只会让前端多一条分支）

### 这一节最后一句

用户说"太蠢了"，正确的反应不是"我改改 prompt"，而是：

```
把它拆成数据问题 / 提示词问题 / 参数问题，分别验证，分别修。
```

三个问题里，只有一个是 prompt 问题。

### 自测题（追加）

1. 项目资料只有 `test` 时，为什么"改 prompt"解决不了问题？
2. 资料过少的判断为什么算"描述+正文"，不算标题？
3. 空资料时直接返回固定文案，除了体验还有什么收益？
4. 思考模式为什么会造成"空白气泡"？
5. 为什么 AI 服务验签失败时按匿名处理，而不是返回 401？
6. 匿名按 IP 限流、成员按用户 id 限流，为什么这样分？

<details>
<summary>答案</summary>

1. 因为资料里没有信息。prompt 只能改变"怎么承认不知道"，不能让 `test` 长出内容。
2. 标题通常只是一个名字，本身不含可回答的信息；算进去会把"只有标题"的项目误判成有内容。
3. 省 token / 省钱；占位项目点一次 AI 现在零成本。
4. 思维链也消耗 `max_tokens`；预算小时被推理吃光，留给正文的就是 0，前端拿到空正文。
5. 这个接口对匿名开放，"token 无效"和"没带 token"在业务上等价；返回 401 只会让前端多一条错误分支。
6. 匿名只有 IP 这个身份，只能按 IP；登录用户有稳定 id，按 id 限流才能挡住"换 IP 绕过"。
