# AI 问答服务：SSE、流式与提示词评测

前置：[00-零基础必读](./00-零基础必读.md)（HTTP 报文与线程池）、[07-前端骨架](./07-前端骨架与登录页.md)（同源代理）。

本文说明三件事：流式输出如何实现、哪些环节会让它失效、提示词质量如何验证。

---

## 1. 流式输出

普通接口等待处理完成后一次性返回。流式接口按生成进度分多次返回，用户先看到前半段内容。

两者总耗时相同，可感知的等待时间不同。

浏览器端有两种实现：WebSocket 与 SSE（Server-Sent Events）。本项目用 SSE，因为数据方向只有服务端到客户端，SSE 基于普通 HTTP，不需要建立双向连接。

---

## 2. 服务边界

最直接的方案是让 Spring 转发 AI 请求：

```
浏览器 → Spring（鉴权）→ FastAPI（AI）→ 模型
```

本项目没有采用，原因是线程占用。SSE 连接从第一个字保持到最后一个字，期间占用一个 Tomcat 工作线程（默认上限 200）。二十个并发提问会占掉约一成线程池，且这部分时间绝大部分在等待网络。

因此 AI 请求不经过 Spring：

```
/ai/*  → FastAPI（容器内 8000）
/api/* → Spring（容器内 8080）
```

Nginx 直接路由到 AI 服务。只有内部摘要接口例外：它由 Spring 通过容器网络调用，并附加 HMAC 签名，外网无法访问（Nginx 返回 403）。

架构说明见 `teamblog/ops/README.md`。

---

## 3. 三个会让流式失效的环节

| 环节 | 默认行为 | 后果 |
|---|---|---|
| Nginx `proxy_buffering` | 开启 | 响应被攒成一整块再下发 |
| 应用缺少 `X-Accel-Buffering: no` | 代理无法识别流式 | 同上，换代理环境时复发 |
| 中间层空闲超时 | 常见 60 秒 | 模型思考期间连接被断开 |

三个都要处理。任一环节出问题，现象都是"等待很久后一次性出现"，且容易被误认为模型响应慢。

Nginx 配置：

```nginx
location /ai/ {
    proxy_pass http://teamblog_ai/;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 300s;
    chunked_transfer_encoding on;
}
```

应用侧响应头：

```python
headers={
    "Cache-Control": "no-cache, no-store",
    "X-Accel-Buffering": "no",
    "Connection": "keep-alive",
}
```

Nginx 会消费 `X-Accel-Buffering`，客户端看不到该头部。测试时不宜从响应头判断是否生效。

## 4. 心跳

模型可能长时间不输出第一个字符。中间层（Nginx、CDN、负载均衡）存在空闲超时，连接会在静默中被断开。

处理方式是按固定间隔发送注释行：

```python
if chunk == "":
    yield b": ping\n\n"
    continue
```

`:` 开头是 SSE 注释语法，客户端忽略，用于保活。本项目间隔为 15 秒。

## 5. 客户端解析

浏览器原生 `EventSource` 只支持 GET，而提问内容需要放在请求体中，因此改用 `fetch` 加 `ReadableStream`。

TCP 是字节流，不保证一次读取正好对应一条完整消息：

```
一次 read() 可能返回：两个半事件，或半个事件
```

因此必须在客户端维护缓冲区，按空行切分事件，切不出完整事件的残片留待下次拼接：

```ts
let buffer = "";
for (;;) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });

  let boundary = buffer.indexOf("\n\n");
  while (boundary >= 0) {
    const block = buffer.slice(0, boundary);
    buffer = buffer.slice(boundary + 2);
    handleBlock(block, handlers);
    boundary = buffer.indexOf("\n\n");
  }
}
```

事件类型共三种：`delta`（增量文本）、`done`（结束，带剩余额度）、`error`（错误码与提示）。

## 6. 连接中断

用户关闭抽屉或离开页面时，前端调用 `AbortController.abort()`。服务端检测到断开后停止调用模型：

```python
async for chunk in _with_heartbeat(stream_answer(...), request):
    if await request.is_disconnected():
        break
```

模型按 token 计费，不停止会持续产生费用。服务端日志中对应"生成被取消（客户端断开）"一条。

## 7. 模型提供方抽象

`provider.py` 中提供 `mock` 与 OpenAI 兼容协议两种实现。`mock` 将问题回显并逐字发送，用于在没有 API key 的情况下验证完整链路（含 Nginx 缓冲配置）。

切换到真实模型只需修改环境变量：

```
AI_PROVIDER=deepseek
AI_API_KEY=sk-...
AI_BASE_URL=https://api.deepseek.com/v1
```

模型名称按调用者身份选择，见第 9 节。

## 8. 成本控制

| 措施 | 配置项 | 说明 |
|---|---|---|
| 每日额度 | `AI_ANON_DAILY_LIMIT`、`AI_MEMBER_DAILY_LIMIT` | 按天分桶，`0` 表示不限 |
| 问题长度 | `max_question_chars` | 默认 500 字 |
| 回答长度 | `ANON/MEMBER_MAX_ANSWER_CHARS` | 提示词中限定字数 |
| 输出 token | `ANON/MEMBER_MAX_TOKENS` | 硬上限 |
| 资料过短不调用模型 | `min_usable_content_chars` | 见第 10 节 |
| 一键关停 | `AI_ENABLED=false` | 两个端点返回 503 |

额度与限流保存在内存，进程重启清零。单实例部署下可接受。

## 9. 访客与成员

同一个接口服务两类调用者，策略不同。

| 项 | 访客 | 成员 |
|---|---|---|
| 标识 | 无 | `Authorization: Bearer <accessToken>` |
| 每日额度 | 8 次（按 IP） | 不限（按用户 id，`0`） |
| 回答字数上限 | 300 | 800 |
| 可问范围 | 项目资料与通用概念 | 不限 |

身份识别在 `app/auth.py`：用与 Spring 相同的 `JWT_SECRET` 校验签名并读取 `sub`。这一步不查询用户表，不管理会话，只验证已签发的声明。

验签失败按访客处理，不返回 401。该接口对匿名开放，"令牌无效"与"未携带令牌"在业务上等价，返回 401 只会让前端多一条错误分支。

额度键的差异很重要：访客按 IP，成员按用户 id。后者换 IP 也无法重置额度。

两档使用不同提示词，见 `app/prompts.py`。访客限制在项目资料范围内；成员不受限，但涉及项目事实时仍以资料为准，避免模型编造技术栈。两档差异由 `tests/test_prompts.py` 断言保护。

## 10. 资料不足的处理

项目正文与描述合计少于 20 字时，服务端不调用模型，直接返回固定说明：

```
这个项目的资料还很少（标题、描述、正文看起来都是占位内容），没法基于资料回答。
可以让作者补充项目介绍后再来问；或者换个问题，比如它解决了什么问题、用了什么技术。
```

原因：资料为占位内容时，模型只能反复声明"资料中没有写"，既消耗 token 也没有信息量。这类问题在提示词层无法解决，属于数据问题，需要在调用前拦截。

标题不计入长度。标题通常只是一个名称，本身不含可回答的信息。

## 11. 思考模式

DeepSeek 的模型默认启用思考模式（`effort=high`）：先输出推理内容，再输出正文。推理同样消耗 `max_tokens`。

当 `max_tokens` 设得过小，推理耗尽预算后正文为空，前端表现为空白回答。

本项目默认关闭思考模式（`AI_THINKING=disabled`）。实测同一问题：

| 档位 | 模型 | 首字延迟 |
|---|---|---|
| 访客 | deepseek-flash | 0.95 至 1.11 秒 |
| 成员，思考关闭 | deepseek-flash | 1.40 至 1.42 秒 |
| 成员，思考开启 | deepseek-v4-pro | 2.40 至 9.21 秒 |

本项目是"依据资料回答"的问答场景，推理带来的质量提升不明显，延迟差异则直接可感知。

若正文仍为空，服务端返回 `error` 事件（`EMPTY_ANSWER`），而非静默结束。

## 12. 提示词评测

提示词是代码，改动后需要回归验证。评测位于 `ai/evals/`，用例存于 `cases.jsonl`，共 22 条。

| 类型 | 数量 | 判定方式 |
|---|---|---|
| 资料可答 | 9 | 回答须包含预期关键词 |
| 资料缺失 | 6 | 须明确声明资料中没有 |
| 通用概念 | 2 | 须给出解释并命中关键词 |
| 越权与注入 | 5 | 不得输出系统提示词；成员档不得拒答正常问题 |

自动判定只覆盖可枚举的条件。是否存在编造，需要人工阅读 `report.md` 中的问答原文。

运行方式：

```bash
python teamblog/ai/evals/run_eval.py
```

## 14. 常见错误

| 写法 | 后果 |
|---|---|
| 只关闭应用侧头部，未关闭 Nginx 缓冲 | 换代理环境后流式失效 |
| 每次 `read()` 当作一条完整消息 | 随机丢字或 JSON 解析失败 |
| 不处理连接中断 | 页面关闭后模型继续生成并计费 |
| 使用 `EventSource` 发送提问 | 只能 GET，长文本进入 URL 与访问日志 |
| 无额度限制 | 脚本可耗尽账户余额 |
| 空正文静默结束 | 前端显示空白回答，无法区分故障与无输出 |
| 跳过提示词评测 | 回答质量退化为不可观测 |

## 16. 术语

| 术语 | 解释 |
|---|---|
| SSE | Server-Sent Events，服务端单向推送文本流 |
| 流式输出 | 边生成边发送 |
| `proxy_buffering` | Nginx 是否缓存上游响应后一次性转发 |
| 心跳 | 定期发送无内容数据包以维持连接 |
| `AbortController` | 浏览器取消请求的接口 |
| provider 抽象 | 将模型供应商隔离为可替换实现 |
| 成本熔断 | 达到阈值停止调用 |
| 提示词注入 | 输入中夹带指令以改变模型行为 |
