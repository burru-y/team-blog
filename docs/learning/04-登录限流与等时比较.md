# 04 · 登录限流与等时比较（零基础版）

> **前置**：先读 [00-零基础必读](./00-零基础必读.md) 的 §1（HTTP/状态码）、§4（编码/加密/哈希）、§6（并发）。
> **本篇目标**：读完能自己从零写出这个功能，并且能说出每一行为什么这么写。
> **对应代码**：`auth/LoginAttemptService`、`auth/LoginProperties`、`common/RateLimitException`、`auth/AuthService#login`
> **对应门禁**：批次 1.4，验收项「第 6 次失败返回 429，文案与密码错一致」

---

## 0. 先讲人话：这一节要解决什么

想象你的登录接口没有任何限制。攻击者写一个脚本：

```
用户名 admin1，密码 000000  → 401
用户名 admin1，密码 000001  → 401
用户名 admin1，密码 000002  → 401
...（每秒 50 次，一晚上跑 400 万次）
```

`admin1` 如果密码是 `123456` 这种，几分钟就被试出来了。

**限流就是给这个脚本踩刹车**：同一个账号或同一个 IP 连续错 5 次，第 6 次直接拒绝，
连密码都不验。

但刹车不能随便踩，踩错了会伤到正常用户：

| 踩法 | 后果 |
|---|---|
| 只按账号限 | 攻击者换用户名继续试（他要找的是"哪些用户名存在"） |
| 只按 IP 限 | 公司/学校同一个出口 IP 的人会互相连累 |
| 一锁定就提示"账号已锁" | 等于告诉攻击者"这个账号存在" |
| 先验密码再限流 | 被拒的请求照样消耗 250ms，攻击者反而拖垮你的 CPU |

这一节的所有设计，都是在回答"怎么踩得准"。

## 1. 先理解敌人：三种攻击，三种目的

| 攻击 | 做法 | 目的 | 防线 |
|---|---|---|---|
| **暴力破解** | 盯着一个账号不停试密码 | 进入这个账号 | 限流（账号维度） |
| **撞库** | 拿别的网站泄漏的"邮箱+密码"批量试 | 捞到一批能登录的账号 | 限流（IP 维度） |
| **账号枚举** | 观察"用户不存在"和"密码错误"的差异 | 找出哪些账号真实存在 | 统一文案 + 等时比较 |

第三种最容易被忽略：攻击者**不需要登进来**，只要知道哪些账号存在，就能卖名单、
或者集中爆破。

所以你会在代码里看到两个看起来"多此一举"的设计：

1. 用户不存在时，也跑一次 250ms 的 BCrypt（防计时枚举）
2. 429 的提示文案和密码错误一模一样（防文案枚举）

它们都在防第三种攻击。

---

## 2. 设计：三个问题

### 2.1 记什么？—— 账号 + IP 两个维度

```
键1：u:admin1        → 失败 5 次
键2：ip:<sha256>     → 失败 5 次
```

- **账号维度**挡住"盯着一个人试"
- **IP 维度**挡住"换着账号试"（撞库）
- 任一维度命中就拒绝

为什么 IP 要哈希：库/日志里不留明文 IP（P-14），而且我们只需要"区分不同 IP"，
不需要知道它具体是多少。

### 2.2 记在哪？—— 内存

| 方案 | 优点 | 缺点 |
|---|---|---|
| **内存 Map**（本项目） | 零依赖、纳秒级、不会写坏数据库 | 重启清零、多实例不共享 |
| 数据库表 | 持久、多实例共享 | 每次失败都写库，攻击者能刷爆 |
| Redis | 共享、自带过期 | 为了一个计数器多一个运维组件 |

结论：单机 + 4G 内存的规模，内存最合适。**代价必须写清楚**：如果以后扩到多实例，
每个实例各算各的，实际阈值会变成"N × 5"。

### 2.3 记多久？—— 固定窗口 10 分钟

```
10:00 第一次失败 → 窗口开始
10:09 第五次失败 → 已满 5 次
10:10 窗口结束 → 计数清零，重新来过
```

这叫**固定窗口**。它有个著名缺陷：如果攻击者在 09:59 错 5 次、10:01 再错 5 次，
这 2 分钟内他就试了 10 次。

为什么还用它：登录爆破是**连续快速重试**，这个边界漏洞最多让攻击者多试几次，
不影响整体强度。而精度更高的"滑动窗口"要为每个键存一串时间戳，内存开销大十倍。

## 3. 代码逐行：`LoginAttemptService`

### 3.1 数据结构

```java
private final Map<String, Attempt> attempts = new ConcurrentHashMap<>();

private record Attempt(Instant windowStart, int failures) {
}
```

逐点解释：

- **`ConcurrentHashMap`** 不是 `HashMap`：同时可能有几十个人登录，普通 HashMap 在多线程
  写入时可能损坏内部结构（见 00-§6）。`ConcurrentHashMap` 是线程安全版本。
- **键是字符串**：`"u:"` 前缀区分账号、`"ip:"` 前缀区分 IP。这样两套计数共用一个 Map，
  清理逻辑也只写一份。
- **值是 `record Attempt`**：只存两个东西——窗口什么时候开始、这个窗口里错了几次。
  `record` 是不可变的（`00-Java注解与语法` §3.5），所以每次更新都是**整条替换**，
  不会出现"两个人同时改同一条"的撕裂。

### 3.2 检查：`ensureAllowed`

```java
public void ensureAllowed(String... keys) {
    Instant now = clock.instant();
    for (String key : keys) {
        Attempt attempt = attempts.get(key);
        if (attempt == null) continue;                       // ① 没记录 → 放行
        if (isExpired(attempt, now)) {                       // ② 窗口过了 → 清掉、放行
            attempts.remove(key, attempt);
            continue;
        }
        if (attempt.failures() >= properties.maxFailures()) { // ③ 满了 → 抛 429
            long retryAfter = Math.max(1,
                    Duration.between(now, attempt.windowStart().plus(properties.window())).toSeconds());
            throw new RateLimitException(retryAfter, "用户名或密码错误");
        }
    }
}
```

三处值得说：

**① 没有记录不是错误。** 第一次登录的人当然没有记录，不能拦。

**② 过期了要顺手删。** 否则 Map 里会堆满"昨天失败过、今天早已解封"的键。

**③ `Retry-After` 用"剩余秒数"。** 这里踩过坑：最初写 `remaining + 1`，窗口刚开始时
算出 601 秒，超过了窗口本身 600 秒——测试断言 `1..600` 直接失败。正确写法是
"剩余多少秒，最少 1 秒"。

**注意 `ensureAllowed` 只读不写。** 它不负责"记一次失败"。为什么这样设计？因为
"检查"和"记账"的时机不同：参数不合法（400）不该计入失败，只有**密码确实错了**才计。

### 3.3 记账：`recordFailure`

```java
public void recordFailure(String... keys) {
    if (attempts.size() > MAX_TRACKED_ENTRIES) {
        purgeExpired();                    // 先清一遍过期的
    }
    Instant now = clock.instant();
    for (String key : keys) {
        attempts.compute(key, (ignored, previous) -> {
            if (previous == null || isExpired(previous, now)) {
                return new Attempt(now, 1);          // 新的窗口
            }
            return new Attempt(previous.windowStart(), previous.failures() + 1);
        });
    }
}
```

**为什么用 `compute` 而不是 `get` + `put`**：

```java
// ❌ 错误的写法：两个线程同时读、同时写，会丢计数
Attempt a = attempts.get(key);
attempts.put(key, new Attempt(a.windowStart(), a.failures() + 1));
```

`compute` 是**原子的**：整个"读—算—写"在一次加锁里完成，两个线程不会覆盖彼此。

**为什么有 `MAX_TRACKED_ENTRIES`**：攻击者可以发 100 万个随机用户名，让 Map 无限增长，
把 4G 内存吃满。这道检查在超过 10 万条时先强制清理一次。

> 说清楚局限：如果攻击者持续用**唯一的**用户名猛刷，清理速度可能跟不上。这属于
> "防呆"而不是"防 DDoS"——真正的 DDoS 要在 Nginx/云防火墙层拦。

### 3.4 清零：`recordSuccess`

```java
public void recordSuccess(String... keys) {
    for (String key : keys) keys.remove();
}
```

为什么登录成功要清零？不清零的话：

```
早上手滑错了 4 次 → 中午正常登录（成功）
晚上又手滑 1 次 → 第 5 次 → 被锁 10 分钟
```

用户会觉得"这破网站老是锁我"。清零是最符合直觉的策略。

> 有人会问：这样攻击者只要在爆破途中成功一次，计数就清了——但"成功一次"意味着
> 他已经进来了，限制计数没有意义。

### 3.5 定期清理

```java
@Scheduled(fixedDelay = 600_000)     // 每 10 分钟
public void purgeExpired() {
    Instant now = clock.instant();
    attempts.entrySet().removeIf(entry -> isExpired(entry.getValue(), now));
}
```

没有这一步，每个失败过的键都会永久占一份内存。`@Scheduled` 需要
`@EnableScheduling`（在 `config/SchedulingConfig` 里）。

## 4. 代码逐行：登录流程

```java
@Transactional
public IssuedTokens login(LoginRequest request, String clientIp) {
    String username = User.normalizeUsername(request.username());
    String accountKey = "u:" + username;
    String ipKey = "ip:" + HashUtils.sha256Hex(clientIp == null ? "unknown" : clientIp);

    loginAttemptService.ensureAllowed(accountKey, ipKey);            // ① 先限流

    User user = userRepository.findActiveByUsername(username).orElse(null);
    String hashToCheck = user == null ? dummyPasswordHash : user.getPasswordHash();
    boolean passwordMatches = passwordEncoder.matches(request.password(), hashToCheck);  // ② 等时比较

    if (user == null || !passwordMatches) {
        loginAttemptService.recordFailure(accountKey, ipKey);        // ③ 记账
        throw new BusinessException(UNAUTHENTICATED, "用户名或密码错误");  // ④ 统一文案
    }

    loginAttemptService.recordSuccess(accountKey, ipKey);            // ⑤ 清零
    user.markLoggedIn(OffsetDateTime.now(clock));
    return issueTokens(user);
}
```

### 4.1 为什么"限流"必须在"验密码"之前

BCrypt 一次约 250ms。假设攻击者每秒发 50 个请求：

| 顺序 | 服务端每秒消耗 |
|---|---|
| 先验密码再限流 | 50 × 250ms = **12.5 个 CPU 核**（直接打满） |
| 先限流 | 50 × 0.01ms ≈ 0.5ms（Map 查询） |

**先限流等于把攻击成本从"你的 CPU"变成"他的请求"**。这是本节最容易被写反的地方。

### 4.2 等时比较：用户不存在时也要跑一次 BCrypt

```java
String hashToCheck = user == null ? dummyPasswordHash : user.getPasswordHash();
boolean passwordMatches = passwordEncoder.matches(request.password(), hashToCheck);
```

`dummyPasswordHash` 是启动时随机生成的一个合法 BCrypt 哈希，永远匹配不上：

```java
this.dummyPasswordHash = passwordEncoder.encode("timing-equalizer-not-a-real-password");
```

**不这么做会怎样**：

| 输入 | 耗时 | 攻击者推断 |
|---|---|---|
| 用户名不存在 | 5ms（查库没查到，直接返回） | 这个号不存在 |
| 用户名存在 + 错密码 | 255ms（跑了 BCrypt） | 这个号存在 |

攻击者发 5000 个请求，按耗时排序，就能得到一份"真实用户名清单"——**他一次都没登进来**。

这叫**计时侧信道**（timing side channel）：不靠数据本身，靠"处理这些数据所花的时间"
泄露信息。

> 做不到完全相等（数据库查询本身有微小差异），但把 250ms 级别的差异抹掉，剩下的
> 噪声已经不足以稳定区分。

### 4.3 为什么失败文案要统一

```java
throw new BusinessException(UNAUTHENTICATED, "用户名或密码错误");
```

不管用户不存在还是密码错误，都是这一句。否则：

```
"用户不存在"   → 这个号没了，换一个试
"密码错误"     → 这个号存在！记下来
```

一句话就能把枚举成本降一半。

## 5. 一次失败登录，完整时间线

```
t=0ms     请求到达
t=0.1ms   normalizeUsername("  Admin1 ") → "admin1"
t=0.2ms   拼出两个键：u:admin1、ip:sha256(203.0.113.7)
t=0.3ms   ensureAllowed → 查 Map，没有记录 → 放行
t=0.4ms   查库 findActiveByUsername("admin1") → 查到了
t=0.5ms   BCrypt.matches("wrong", 真哈希) → false（耗时约 250ms）
t=250ms   recordFailure → Map 里 u:admin1 现在 1 次
t=250ms   抛 BusinessException(UNAUTHENTICATED, "用户名或密码错误")
t=251ms   GlobalExceptionHandler 捕获 → HTTP 401 + {"ok":false,"error":{...}}
```

对比**用户不存在**时：

```
t=0.4ms   查库 → 没查到，user = null
t=0.5ms   BCrypt.matches("wrong", dummyHash) → false（同样约 250ms）
t=250ms   同样的 401、同样的文案
```

两条路径耗时一致、响应一致——攻击者拿不到任何额外信息。

## 6. 五个容易写错的细节

### 6.1 `Retry-After` 的计算

```java
long retryAfter = Math.max(1, Duration.between(now, windowStart.plus(window)).toSeconds());
```

- 窗口 10 分钟 = 600 秒
- 第 1 秒被拦时，剩余 599 秒
- 窗口最后一刻被拦，剩余 0 秒 → `Math.max(1, 0)` = 1 秒

**不要写 `+ 1`**：那会让窗口刚开始时返回 601，超出窗口本身。

### 6.2 `X-Forwarded-For` 取最后一个

生产部署长这样：

```
攻击者（可自带 XFF: 1.2.3.4） → Nginx（追加真实 IP） → 应用
最终应用收到的头： "1.2.3.4, 203.0.113.7"
```

- 取**第一个** = 取到攻击者自己写的值 → 每次换一个就绕过限流
- 取**最后一个** = 取到 Nginx 追加的真实来源

```java
String[] hops = forwarded.split(",");
return hops[hops.length - 1].trim();
```

> 前提：应用端口不直接暴露公网、Nginx 在可信网络。如果应用直接对公网开放，
> 这个头完全不可信，应该只看 `request.getRemoteAddr()`。

### 6.3 为什么 429 的文案也叫"用户名或密码错误"

直觉上应该说"尝试过于频繁"。但这样会泄露信息：如果只有存在的账号才会触发账号维度的
锁定，那么 429 本身就是"这个账号存在"的信号——**攻击者可以拿 429 当枚举器**。

所以这里刻意沿用同一句话，靠 `Retry-After` 头告诉客户端何时重试。

牺牲的是可读性（真被锁的人看不出原因），换的是不泄露。真实产品通常在"忘记密码"入口
做引导，而不是在失败文案上做区分。

### 6.4 成功必须清零

见 §3.4。不清零会让"手滑 4 次 + 明天正常登录"的人随时处在被锁的边缘。

### 6.5 内存计数会丢——这没关系，但要知道

- 重启服务 → 计数清零（攻击者可以"等你重启"）
- 多实例 → 各算各的（实际阈值变成 N × 5）

这是用内存的代价。当前单机部署可以接受；扩展时要换 Redis，
`LoginAttemptService` 没有依赖任何 Web 类型，是干净的替换点。

## 7. 反面教材：五种写错的方式

| 写法 | 后果 |
|---|---|
| 先 `matches` 再 `ensureAllowed` | 被限流的请求照样烧 250ms，攻击者用它打满 CPU |
| 只用 `HashMap` | 并发下计数丢失，甚至结构损坏 |
| `get` 再 `put` 更新计数 | 两个线程同时失败只记一次，阈值形同虚设 |
| 用户不存在时直接 `return` | 响应快 250ms，成为账号枚举器 |
| 429 返回"尝试过于频繁" | 泄露账号存在，甚至可当枚举器 |
| `Retry-After` 写 `+1` | 超过窗口长度，客户端等更久，测试也会挂 |
| 用 `request.getRemoteAddr()` 而不取 XFF | 部署在 Nginx 后，所有人都是同一个 IP，一起被限 |

## 8. 测试怎么写

### 8.1 为什么要"可推进的时钟"

想测"10 分钟后自动解封"，最直接的办法是 `Thread.sleep(11 分钟)`——测试要跑 11 分钟，
而且慢机器上可能偶发失败。

正确做法是把 `Clock` 作为依赖注入，测试里换成一个能手动拨的：

```java
private static final class MutableClock extends Clock {
    private Instant instant;
    void advance(Duration d) { instant = instant.plus(d); }
    public Instant instant() { return instant; }
    public ZoneId getZone() { return ZoneOffset.UTC; }
    public Clock withZone(ZoneId z) { return this; }
}
```

```java
for (int i = 0; i < 5; i++) service.recordFailure(ACCOUNT, IP);
assertThatThrownBy(() -> service.ensureAllowed(ACCOUNT, IP)).isInstanceOf(RateLimitException.class);

clock.advance(Duration.ofMinutes(11));          // 瞬间"过了 11 分钟"

assertThatCode(() -> service.ensureAllowed(ACCOUNT, IP)).doesNotThrowAnyException();
```

这是"依赖注入"最实际的收益之一：**时间也能被注入**。

### 8.2 为什么每个用例要用独立 IP

限流按 IP 计数。如果所有用例都走 MockMvc 默认的 `127.0.0.1`：

```
用例1 攒了 5 次失败 → 127.0.0.1 被锁
用例2 登录 → 429！失败
用例3 登录 → 429！失败
```

测试就变成了"看谁先跑"，违反 Q-09（可重复、不依赖顺序）。所以每个用例带一个独立的
`X-Forwarded-For`：

```java
mockMvc.perform(post("/api/v1/auth/login").header("X-Forwarded-For", uniqueIp()) ...)
```

顺带还把"经 Nginx 转发"的场景测了。

### 8.3 验收用例长什么样

```java
// 连错 5 次
for (int i = 0; i < 5; i++) { 期望 401 }

// 第 6 次用**正确密码**也必须被拦 —— 证明限流发生在验密码之前
mockMvc.perform(... RAW_PASSWORD ...)
    .andExpect(status().isTooManyRequests())
    .andExpect(header().exists("Retry-After"))
    .andExpect(jsonPath("$.error.code").value("RATE_LIMITED"))
    .andExpect(jsonPath("$.error.message").value("用户名或密码错误"));
```

那句"用正确密码也必须被拦"是关键——如果实现里限流写在验证之后，这条断言会失败。

## 9. 动手练习（理解了就自己写一遍）

不看代码，按顺序实现：

1. 定义 `LoginProperties`（`maxFailures`、`window`），用 `@ConfigurationProperties` 绑定
2. 建 `LoginAttemptService`，用 `ConcurrentHashMap<String, Attempt>` 存
3. 实现 `ensureAllowed`（只读）、`recordFailure`（`compute`）、`recordSuccess`（删除）
4. 加 `@Scheduled` 清理过期键
5. 在 `AuthService#login` 里按"限流 → 等时比较 → 记账 → 统一文案"的顺序接线
6. 用可推进时钟写 5 个单测；再用 MockMvc 写"第 6 次正确密码也 429"

写完后对照本文 §3、§4，看你有没有把"限流放在验密码之后"。

7. `X-Forwarded-For` 为什么取最后一个？
8. 为什么测试要用"可推进的时钟"？
9. `recordFailure` 用 `get` + `put` 而不是 `compute`，会发生什么？
10. 10 万个随机用户名会让服务出什么事？现在怎么防的？

<details>
<summary>答案（先答完再看）</summary>

1. 只按账号：换用户名就能继续试，用户名本身也会被爆破出来；只按 IP：同一出口（公司/学校）的正常用户互相连累。两个维度同时限制，任一命中即拦。
2. BCrypt 约 250ms。先验密码再限流，被拒的请求也消耗服务端 250ms；攻击者用低成本就能打满 CPU。
3. 通过响应时间差异推断信息："用户不存在"比"密码错误"快一个 BCrypt 的时间，攻击者能批量筛出有效用户名。
4. 因为"账号被锁"会泄露"账号存在"，甚至能用 429 当枚举器。牺牲的是用户可读性。
5. 窗口边界可能双倍突发（09:59 错 5 次、10:01 再错 5 次）。登录爆破是连续突发，多试几次不影响整体强度。
6. 每个实例各算各的，实际阈值变成 N × 5，攻击者可以在不同实例上各试 5 次。换成 Redis 共享计数。
7. 前面的段是客户端可伪造的；Nginx 用 `$proxy_add_x_forwarded_for` 把真实来源追加在末尾。取第一个等于让攻击者自选 IP。
8. `Thread.sleep(11 分钟)` 让测试跑十几分钟且不稳定；注入可控时钟后瞬间完成，且确定性。
9. 两个线程同时失败时，后写的会覆盖先写的，计数少一次，阈值实际上永远达不到。
10. Map 无限增长吃满内存。现在超过 10 万条会先强制清理过期项；更彻底的做法是给 Map 设上限或用带淘汰的缓存。

</details>

## 11. 本节术语

| 名词 | 一句话 |
|---|---|
| 固定窗口 | 从第一次失败开始计时，窗口内计数，结束后清零 |
| 滑动窗口 | 记录每次失败的时间点，精确但更占内存 |
| 计时侧信道 | 靠响应时间差异推断信息 |
| 等时比较 | 让"存在/不存在"两条路径耗时一致 |
| 账号枚举 | 找出哪些账号真实存在 |
| 撞库 | 拿别处泄漏的账号密码批量试 |
| `Retry-After` | 429 响应头，告诉客户端多少秒后重试 |
| `ConcurrentHashMap` | 线程安全的 Map |
| 原子操作 | 一个动作不可被其他线程打断（`compute` 就是） |
