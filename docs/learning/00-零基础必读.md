## 0. 这份文档想解决什么

你写 JavaWeb 时的世界是这样的：

```
浏览器 → Tomcat → Servlet → JDBC → MySQL → 拼 HTML → 返回
```

现在多出来的这些东西——JWT、Cookie 属性、状态码、缓存、并发、时区——**不是新语言，
是同一件事的不同侧面**。它们之所以让人晕，是因为没人告诉你"它们各自在解决什么问题"。

这份文档就是把它们一个个拆开。

## 1. HTTP 到底长什么样

### 1.1 一次请求 = 一段纯文本

你在浏览器里输入 `http://127.0.0.1:8080/api/v1/me`，浏览器发出去的东西长这样：

```http
GET /api/v1/me HTTP/1.1
Host: 127.0.0.1:8080
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ...
Accept: application/json
```

拆成四块：

| 部分 | 例子 | 说明 |
|---|---|---|
| 方法 | `GET` | 想干什么（查/改/删） |
| 路径 | `/api/v1/me` | 对谁做 |
| 头（Headers） | `Authorization: Bearer ...` | 附带信息：我是谁、我要什么格式 |
| 体（Body） | 空 | 要提交的数据（GET 一般没有） |

服务器回的东西：

```http
HTTP/1.1 200 OK
Content-Type: application/json
Set-Cookie: rt=xxx; HttpOnly; Path=/api/v1/auth

{"ok":true,"data":{"username":"admin1"}}
```

| 部分 | 例子 | 说明 |
|---|---|---|
| 状态码 | `200` | 结果如何（成功？没权限？限流？） |
| 响应头 | `Content-Type`、`Set-Cookie` | 附带的元信息 |
| 响应体 | `{"ok":true,...}` | 真正的数据 |

> **和 Servlet 的对应**：`req.getHeader("Authorization")` 读的是请求头，
> `resp.setStatus(401)` 设的是状态码，`resp.getWriter().write(...)` 写的是响应体。
> Spring 只是把这些动作变成了注解和返回值。

### 1.2 方法（Method）

| 方法 | 语义 | 本项目例子 |
|---|---|---|
| `GET` | 读取，**不改数据** | `GET /api/v1/me` |
| `POST` | 新建 / 触发动作 | `POST /api/v1/auth/login` |
| `PUT` | 整体替换 | 后续批次 |
| `PATCH` | 局部修改 | 后续批次 |
| `DELETE` | 删除 | 后续批次 |

为什么非要分清：**GET 可以被浏览器缓存、可以被爬虫重复抓**。如果用 GET 做"删除"，
一个预加载就能把你的数据删光。

### 1.3 路径里的三种参数

```
/api/v1/learning-logs/abc-123?page=2&size=20
                    └──┬──┘ └────┬────┘
                  路径参数      查询参数
```

请求体（Body）是第四种——POST/PUT 才用：

```json
{"username": "admin1", "password": "ChangeMe123!"}
```

| 类型 | 位置 | Spring 注解 | 用途 |
|---|---|---|---|
| 路径参数 | URL 路径里 | `@PathVariable` | 定位资源（哪个用户） |
| 查询参数 | `?` 后面 | `@RequestParam` | 过滤、分页、排序 |
| 请求体 | Body | `@RequestBody` | 提交的数据 |

### 1.4 状态码：只需要记住这张表

| 码 | 含义 | 什么时候用 | 通俗解释 |
|---|---|---|---|
| `200` | OK | 查询成功、更新成功 | 办好了 |
| `201` | Created | 新建成功 | 办好并给你编号 |
| `204` | No Content | 删除成功，无返回体 | 办好了，没什么可说 |
| `400` | Bad Request | 参数格式错（缺字段、类型不对） | 你话说得不对，我没法理解 |
| `401` | Unauthorized | 没登录 / token 无效 / 过期 | 我不知道你是谁 |
| `403` | Forbidden | 登录了，但没权限 | 我知道你是谁，但不许你干 |
| `404` | Not Found | 资源不存在 | 没有这个东西 |
| `409` | Conflict | 唯一键冲突（重复打卡） | 和现有状态打架了 |
| `422` | Unprocessable | 语义违反（回复的回复） | 话能听懂，但这事不能这么干 |
| `429` | Too Many Requests | 限流 | 你太频繁了，歇会儿 |
| `500` | Internal Server Error | 代码崩了 | 我出错了（不告诉细节） |
| `503` | Service Unavailable | 依赖挂了（AI 服务） | 我暂时干不了 |

**401 和 403 的区别**是初学最常搞混的：

- 401 = **你还没证明你是谁**（没带 token、token 坏了、过期了）→ 前端应该跳登录页
- 403 = **已经知道你是谁，但你不能做这个**（成员访问管理员接口）→ 前端应该提示"没权限"，
  **不要**跳登录页，否则用户会陷入"我明明登录了却让我登录"的死循环

### 1.5 几个必须认识的头

| 头 | 谁发的 | 作用 |
|---|---|---|
| `Authorization: Bearer <token>` | 客户端 | 携带身份凭证（本项目用 JWT） |
| `Cookie: rt=...` | **浏览器自动** | 携带 refresh token |
| `Set-Cookie: rt=...; HttpOnly` | 服务端 | 让浏览器保存一个 Cookie |
| `Content-Type: application/json` | 双方 | 声明"这个体是 JSON" |
| `Retry-After: 573` | 服务端 | 429 时告诉客户端"573 秒后再试" |

## 2. Cookie：为什么它这么特殊

### 2.1 一句话

**Cookie 是服务器让浏览器"自动帮你带着"的一小段文字。**

```
第一次：浏览器 POST /auth/login
        服务器回：Set-Cookie: rt=abc123
        浏览器默默存下："访问 127.0.0.1 时，自动带上 rt=abc123"

之后：  浏览器每次请求 127.0.0.1 的 /api/v1/auth/*，
        都会自动加一行：Cookie: rt=abc123
```

你在 JavaWeb 里用的 `JSESSIONID` 就是这样一个 Cookie——只是你没关心过它的属性。

### 2.2 为什么它又爱又恨

**爱**：自动携带，前端什么都不用写。

**恨**：**自动携带**意味着任何第三方网站诱导你点一个链接，浏览器也会带上它——
这就是 CSRF（跨站请求伪造）。所以 Session 方案必须额外加 CSRF token。

本项目怎么处理：**access token 走 `Authorization` 头（不会自动带，天然免疫 CSRF），
refresh token 走 Cookie 但限制得极死**（见下）。

### 2.3 Cookie 的四个属性（本项目全用上了）

| 属性 | 写法 | 防什么 | 不写的后果 |
|---|---|---|---|
| `HttpOnly` | `HttpOnly` | JS 读不到 → XSS 偷不走 | 一段恶意脚本就能 `document.cookie` 拿走 7 天会话 |
| `Secure` | `Secure` | 只在 HTTPS 上发送 | 明文 WiFi 下被中间人截获 |
| `SameSite` | `SameSite=Lax` | 跨站请求不携带 | 别的网站能借你的登录态发请求 |
| `Path` | `Path=/api/v1/auth` | 只发给这个路径 | 每个接口请求都白带一个 200 字节的 Cookie |

`Max-Age=604800` 表示 7 天后过期（604800 秒）。

> 为什么 `Path` 不能窄到 `/api/v1/auth/refresh`：登出也要读这张票。太窄的话，
> 浏览器在 `/logout` 上不带 Cookie，用户点"退出"会退不掉。

## 3. JSON 和"统一信封"

JSON 就是"JS 的对象写法"，现在成了前后端传数据的通用格式：

```json
{
  "ok": true,
  "data": { "username": "admin1", "role": "ADMIN" },
  "error": null
}
```

本项目的**所有**接口都返回这同一个外壳（信封）：

| 字段 | 成功时 | 失败时 |
|---|---|---|
| `ok` | `true` | `false` |
| `data` | 真正的数据 | `null` |
| `error` | `null` | `{"code":"UNAUTHENTICATED","message":"..."}` |

为什么值得统一：前端只写一套解析和一套错误处理。如果有的接口返回数组、有的返回
`{code,msg}`、有的直接返回字符串，前端的 `if` 会越写越长，最后没人敢改。

**`code` 是给程序看的**（前端按它分支、决定跳登录还是提示），
**`message` 是给人看的**（日志、排查）。

## 4. 编码、加密、哈希：三个最容易混的词

这三个都长得像"一串乱码"，但用途完全不同。**混淆它们会直接导致漏洞。**

| | 能还原吗 | 目的 | 例子 | 生活类比 |
|---|---|---|---|---|
| **编码** | ✅ 能，谁都能 | 换个格式方便传输 | Base64、URL 编码 | 把信装进标准信封 |
| **加密** | ✅ 但要有钥匙 | 保密 | AES、RSA | 上锁的保险箱 |
| **哈希** | ❌ 不能 | 校验/存密码 | SHA-256、BCrypt | 绞肉机（肉进不出） |

### 4.1 Base64 不是加密

```java
Base64.encode("admin")   // → "YWRtaW4="
```

任何人贴到网上就能解回来。它只是把二进制变成"只用字母数字"的文本，方便放进 JSON 或 URL。

> **这就是为什么 JWT 的 payload 谁都能看**——它只是 Base64，不是加密。
> 所以 JWT 里绝不能放密码、手机号。

### 4.2 两种哈希，用途不同

```java
sha256("abc123")   // 快，微秒级，结果是固定 64 位十六进制
bcrypt("abc123")   // 慢，约 250ms，结果自带盐
```

| | SHA-256 | BCrypt |
|---|---|---|
| 速度 | 极快 | 故意慢（约 250ms） |
| 用途 | 校验数据完整性、存**随机值**的指纹 | 存**人想出来的密码** |
| 为什么 | 越快越好（比如对 refresh token 做指纹） | 慢了才能对抗暴力破解 |

本项目：

- refresh token 是 32 字节随机数 → 存 `sha256` 就够（随机数没有"弱口令"）
- 用户密码是人想出来的 → 必须 `bcrypt`（攻击者每猜一个都要付 250ms）
- IP 地址 → 存 `sha256`（P-14：不存明文 IP）

### 4.3 什么叫"加盐"

如果两个人密码都是 `123456`，用 SHA-256 存，哈希值一模一样。攻击者做一张"常见密码
→ 哈希"的表，就能一次破解所有人。

BCrypt 每次加密都会生成一段随机数据（盐）掺进去，所以同一个密码两次的结果不同：

```
bcrypt("123456") → $2a$12$KIXQJ3...（盐A）
bcrypt("123456") → $2a$12$Pq7Zm9...（盐B）
```

校验时从哈希里把盐读出来，用同样的盐重算一遍再比——所以不能说 `hash.equals(...)`，
必须用 `encoder.matches(raw, hash)`。

## 5. "无状态"是什么意思

### 5.1 有状态：Session

```
登录 → 服务器发一把钥匙（JSESSIONID），并在自己柜子里放一个抽屉（Session）
之后 → 你每次出示钥匙，服务器去柜子里翻抽屉
```

服务器必须**记住**每个人都有哪些抽屉。这就是"有状态"。好处是**想删就删**（把抽屉清空，
钥匙立刻作废）；坏处是**柜子只有一台**——加一台机器，抽屉不共享，用户就"掉线"了。

### 5.2 无状态：JWT

```
登录 → 服务器发一张盖章的通行证（JWT），自己不留底
之后 → 你每次出示通行证，服务器只验章真不真
```

服务器**不记**任何人。好处是加多少台机器都行（谁都能验章）；坏处是
**章是真的就放行，收不回来**——用户改密码了，旧通行证还没过期，照样能用。

### 5.3 本项目怎么兼得两者

```
通行证（access token）：30 分钟，无状态，放 Authorization 头
兑换券（refresh token）：7 天，**存在数据库里**，可以撤销，放 Cookie
```

- 平时用通行证，快、不查库
- 通行证到期，用兑换券换新的
- 要"踢人"时，作废兑换券 + 让通行证里的版本号对不上（见 02、03 文档）

**一句话：用无状态换性能，用数据库换撤销能力。**

## 6. 并发：为什么服务器会"串号"

### 6.1 线程池 = 银行窗口

Tomcat 不会为每个请求新开一个线程（太贵），而是维护一池子线程反复用：

```
请求A → 线程1 处理 → 结束 → 线程1 回到池子
请求B → 线程1 处理（同一个线程！）
```

如果线程1 在处理 A 时，往一个"全局变量"里放了 A 的身份，处理完没清干净，
那么处理 B 时，B 就**继承了 A 的身份**——这就是"串号"，最严重的越权 bug。

```java
try {
    SECURITY_CONTEXT.set(userA);       // 放进去
    chain.doFilter(request, response);
} finally {
    SECURITY_CONTEXT.clear();          // 必须清！放 finally 保证一定执行
}
```

`finally` 的意义：即使中间抛异常，清理也会执行。写在 `try` 结尾处，异常一抛就跳过了。

### 6.2 `ConcurrentHashMap` 是什么

普通 `HashMap` 在多线程同时写的时候可能把内部结构搞坏（JDK 7 甚至会死循环）。
`ConcurrentHashMap` 是线程安全的版本：多个线程同时读写也不会出问题。

本项目用它存"登录失败次数"（04 文档），因为同时可能有几十个人在登录。

> 不需要背它的实现。只要记住：**多线程共享的 Map，用 `ConcurrentHashMap`，不要用 `HashMap`。**

### 6.3 为什么"内存里的计数"会丢

```java
Map<String, Integer> attempts = new HashMap<>();   // 放在类字段里
```

- 重启服务 → 清零（攻击者可以等你重启）
- 多台机器 → 各算各的（在 A 机器试 5 次、B 机器试 5 次）

这是"用内存"的代价。什么时候能接受？**单机部署 + 重启不频繁**（本项目现状）。
要多机共享，就得换成 Redis。

## 7. 时间：为什么打卡会"差一天"

### 7.1 同一个时刻，不同的写法

```
北京时间 2026-10-24 10:00
= UTC 时间 2026-10-24 02:00
= 时间戳 1792807200
```

这三个说的是**同一个瞬间**。搞混它们，就会出现"23:30 打卡被算到第二天"。

### 7.2 Java 里的三个时间类型

| 类型 | 带时区吗 | 例子 | 用在哪 |
|---|---|---|---|
| `Instant` | 不带（永远是 UTC） | `2026-10-24T02:00:00Z` | 机器内部计算、过期时间 |
| `LocalDate` | 不带（只有年月日） | `2026-10-24` | **业务日期**（打卡算哪一天） |
| `OffsetDateTime` | 带偏移 | `2026-10-24T10:00:00+08:00` | 存数据库 `timestamptz` |

**为什么禁用 `LocalDateTime`**：它既没有时区也没有偏移。中国服务器写进去 10:00，
UTC 服务器读出来也是 10:00，但那已经是 8 小时之后的另一个瞬间了。

### 7.3 本项目的规矩

- 数据库时间列一律 `timestamptz`
- 实体字段用 `OffsetDateTime`
- "今天"由注入的 `Clock` 决定，时区固定 `Asia/Shanghai`
- **不允许**代码里直接写 `LocalDate.now()`

为什么最后一条很重要：写死了 `now()`，你就没法测"跨天""月底""闰年"——
那些 bug 只能等到那天才被发现。

## 8. 数据放哪儿：内存 / 数据库 / 缓存

| | 内存（变量/Map） | 数据库（PostgreSQL） | 缓存（Redis） |
|---|---|---|---|
| 速度 | 纳秒 | 毫秒 | 微秒 |
| 重启后还在吗 | ❌ 没了 | ✅ 在 | 看配置 |
| 多台机器共享吗 | ❌ 各是各的 | ✅ 共享 | ✅ 共享 |
| 成本 | 最便宜 | 要维护 | 多一个组件 |

本项目的选择，每一条都有理由：

| 数据 | 放哪 | 为什么 |
|---|---|---|
| 用户、成果、打卡 | 数据库 | 必须持久、必须共享 |
| 登录失败次数 | **内存** | 丢了大不了重新计数；引 Redis 不值得（禁止清单第 13 条） |
| refresh token | 数据库 | 必须能撤销、能跨机器校验 |
| access token | **不放**（客户端持有） | 无状态，服务端不留 |

## 9. 术语表（本项目出现过的名词）

| 名词 | 一句话解释 |
|---|---|
| **API** | 程序之间约定的接口，这里是"HTTP + JSON" |
| **端点（endpoint）** | 一个具体的"方法 + 路径"，如 `POST /api/v1/auth/login` |
| **DTO** | 用来传数据的对象（不是实体），只带该露的字段 |
| **实体（Entity）** | 映射数据库表的 Java 类 |
| **Repository** | 数据访问接口（代替你手写的 DAO） |
| **Service** | 放业务规则的地方 |
| **Controller** | 接收 HTTP、转 DTO、调用 Service |
| **JWT** | 带签名的"通行证"字符串，格式 `头.载荷.签名` |
| **access token** | 短期通行证（30 分钟） |
| **refresh token** | 长期兑换券（7 天），存 Cookie，用来换新的通行证 |
| **轮换（rotation）** | 每用一次兑换券就换一张新的，旧作废 |
| **重放（replay）** | 拿已经用过的旧券再用一次——通常意味着被盗 |
| **限流（rate limit）** | 限制单位时间内的请求次数 |
| **哈希（hash）** | 单向摘要，不能还原 |
| **加盐（salt）** | 哈希时掺入随机值，让相同密码得到不同结果 |
| **迁移（migration）** | 用 SQL 脚本版本化管理表结构（Flyway） |
| **事务（transaction）** | 一组操作要么全成、要么全不成 |
| **幂等（idempotent）** | 同样的请求做多次，结果和执行一次一样 |
| **side channel** | 侧信道：不直接读数据，靠时间/长度等间接推断 |
| **CSRF** | 跨站请求伪造：借你的登录态发请求 |
| **XSS** | 跨站脚本：往页面注入 JS 偷数据 |
| **时区偏移** | 比如 `+08:00`，表示比 UTC 早 8 小时 |
