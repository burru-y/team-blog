# 10 · 打卡、连续段与积分对账（零基础版）

> **本篇目标**：理解"日期算术"类业务为什么最容易算错，以及账本 + 对账这套机制在解决什么。
> **对应门禁**：批次 4，Gate G4。

## 0. 先讲人话

前几批的规则都是"看一眼就知道对不对"：密码对不对、是不是作者、文件头是不是 PNG。

打卡不一样。它的规则长这样：

```
连续第 7 天额外 +5 分
连续第 14 天额外 +10 分
连续第 30 天额外 +20 分
断一天，连续天数归零
每天只能打一次
```

这些规则**很难用眼睛验证**：你得连续点 30 天，或者伪造 30 天的数据。而一旦算错，
用户看到的是"我明明连续打了 7 天，为什么只加了 1 分"——这种 bug 投诉起来最费劲，
因为它需要你把某个人 60 天的历史全部复盘一遍。

所以这一批的重点不是"实现打卡"，而是**让日期规则可以被测试**。

---

## 1. 先理解问题

### 1.1 "今天"到底是哪天

```
服务器在 UTC 时间 2026-03-01 16:30
北京时间的此刻是 2026-03-02 00:30
```

那么用户点打卡，应该算在 **3 月 1 日**还是 **3 月 2 日**？

答案是 3 月 2 日——用户在中国的凌晨打卡，对他来说是"新的一天"。

结论：**日期必须按 Asia/Shanghai 计算，不能依赖服务器时区**（J-14）。
如果服务器跑在 UTC，凌晨 0 点到 8 点打卡的人会被算到前一天，连续段直接错乱。

### 1.2 为什么规则不可测

```java
LocalDate today = LocalDate.now();     // ❌ 永远只能测"今天"
```

想测"连续第 7 天"，你得真的等到第 7 天。想测"断签"，得先断一天。

解决办法是**把时间变成依赖**：

```java
LocalDate today = LocalDate.now(clock);   // ✅ 测试里塞一个可拨的 Clock
```

这就是 1.1 就引入 `ClockConfig` 的原因——当时看着像过度设计，这一批开始回本。

### 1.3 积分为什么要有账本

两种记法：

```
方案 A：users.total_points += 1          （只有结果）
方案 B：point_events 插一条流水，再更新总分（结果 + 过程）
```

方案 A 的问题是：**出了错无法发现，也无法恢复**。

比如某个事务提交到一半失败，用户的 `total_points` 加了但流水没写（或反过来）。
一年后用户说"我的分不对"，你手上只有 `total_points = 46` 这一个数字，
没有任何依据判断它该是多少。

方案 B 有流水，于是可以问一个致命问题：

```sql
-- 缓存 vs 事实
select u.id, u.total_points as recorded, coalesce(sum(e.points), 0) as computed
  from users u left join point_events e on e.user_id = u.id
 group by u.id, u.total_points
having u.total_points <> coalesce(sum(e.points), 0)
```

有差异 = 有 bug；而且能**按流水修正**。

### 1.4 连续段奖励的"只发一次"难在哪

规则是"连续第 7 天 +5"。但用户可能：

- 第 7 天连点 5 次（重复请求）
- 断签后重新连续 7 天（应该**可以再拿**）

所以"只发一次"的粒度不是"人"，也不是"永久"，而是**"每一段连续"**。

## 2. 设计：四个问题

| 问题 | 答案 | 位置 |
|---|---|---|
| "今天"怎么算 | 注入 `Clock`（Asia/Shanghai） | `ClockConfig` + `LocalDate.now(clock)` |
| 重复打卡怎么挡 | 数据库唯一约束 `(user_id, checkin_date)` | `uq_checkins_user_date` |
| 奖励怎么"每段一次" | `ref_id` 用**本段第一天** | `CheckinService` |
| 总分怎么不丢 | 账本 + 原子 UPDATE + 每日对账 | `PointService` + `PointReconciliationService` |

## 3. 代码逐行

### 3.1 打卡事务

```java
@Transactional
public CheckinResult checkin(UUID userId, String note) {
    LocalDate today = LocalDate.now(clock);

    Checkin checkin = Checkin.create(userId, today, note);
    try {
        checkinRepository.saveAndFlush(checkin);   // ①
    } catch (DataIntegrityViolationException ex) {
        throw new BusinessException(ErrorCode.ALREADY_CHECKED_IN);   // ②
    }

    pointService.award(userId, PointEventKind.CHECKIN, checkin.getId().toString(), 1);  // ③

    Set<LocalDate> dates = recentDates(userId, today);
    int streak = currentStreak(dates, today);

    Integer bonus = STREAK_BONUS.get(streak);      // ④
    if (bonus != null) { ... }
    ...
}
```

**① 为什么 `saveAndFlush` 而不是 `save`**：`save` 可能把 INSERT 攒到事务提交时才执行，
那时再撞唯一约束就**来不及翻译成 409** 了（异常会在切面之外抛出）。`flush` 让它立刻执行。

**② 为什么捕获异常而不是先查一次**：先 `exists` 再 `insert` 在并发下会双写——
两个请求同时查到"没打过"。唯一约束才是最终保证，代码里的检查只能算优化。

**③ 打卡和加分在同一个事务**：中途失败整体回滚，不会出现"打卡了没加分"。

**④ 奖励判断用 `Map.get(streak)`**：只有 7/14/30 三个键，其它天数返回 `null`，
不用写一串 `if`。

### 3.2 连续天数

```java
private static int currentStreak(Set<LocalDate> dates, LocalDate today) {
    int streak = 0;
    LocalDate cursor = today;
    while (dates.contains(cursor)) {
        streak++;
        cursor = cursor.minusDays(1);
    }
    return streak;
}
```

从今天往回数，遇到断档即停。一次查近 60 天的日期集合（30 天奖励 + 缓冲），
而不是逐天查库。

**为什么不支持补签**：一期明确不做。补签会让"连续"这个概念变得依赖操作顺序，
规则复杂度翻倍，收益很小。

### 3.3 奖励的 `ref_id`：本段第一天

```java
LocalDate streakStart = today.minusDays(streak - 1L);
pointService.award(userId, kind, streakStart.toString(), bonus);
```

配合唯一约束 `(user_id, kind, ref_id)`，效果是：

| 场景 | `ref_id` | 结果 |
|---|---|---|
| 第 7 天发放 | 本段第 1 天 | 发 5 分 |
| 同一天重复请求 | 同一个 | 唯一约束挡住，不发 |
| 第 14 天 | 同一个（kind 不同） | 发 10 分 |
| 断签后新的一段第 7 天 | **新的第 1 天** | 可以再发 5 分 |

如果 `ref_id` 用"当天"，同一天重复请求会重复发；如果 `ref_id` 固定成用户 id，
断签后就永远拿不到第二次。**"本段第一天"同时满足这两条**。

### 3.4 等级是纯函数

```java
public static int levelOf(int totalPoints) {
    if (totalPoints < 50) return 1;
    if (totalPoints < 150) return 2;
    ...
}
```

放在后端算，并通过 `UserResponse.level` 返回。**前端不复制一份阈值表**——
复制就会漂移，改了后端忘了前端，用户看到"分涨了但等级没变"。

### 3.5 对账

```java
@Scheduled(cron = "0 10 3 * * *", zone = "Asia/Shanghai")
public void scheduledReconcile() {
    try {
        ReconciliationReport report = reconcile();
        ...
    } catch (RuntimeException ex) {
        log.error("积分对账任务失败", ex);   // 定时任务抛异常会静默消失
    }
}
```

修正策略：

```java
for (UserRepository.PointsMismatch row : mismatches) {
    log.error("积分不一致 userId={} 记录值={} 账本汇总={}，按账本修正", ...);   // ERROR 不是 WARN
    userRepository.setTotalPoints(row.getId(), (int) row.getComputed());
}
```

**只告警不修** → 用户一直看着错的分；**只修不告警** → 真正的 bug 永远发现不了。
所以两只手都要：打 ERROR 日志（需要人看）并按账本修正。

### 3.6 前端：打卡后不刷新

```tsx
const result = await api.checkin(null, token);
setStatus({
  checkedInToday: true,
  today: result.checkinDate,
  streak: result.streak,
  totalPoints: result.totalPoints,
  level: result.level,
});
```

接口把 `streak / gained / totalPoints / level` 一起返回，就是为了**一次请求把界面全部更新**。
再发一次请求会有半秒空窗，体验上就是"点了没反应"。

409 也不当错误：

```tsx
if (err instanceof ApiError && err.code === "ALREADY_CHECKED_IN") {
  const next = await api.checkinStatus(token);   // 别的标签页已经打过了
  setStatus(next);
  setFlash("今天已经打过卡了");
}
```

### 3.7 热力图：为什么按周排

```tsx
const leading = (start.getUTCDay() + 6) % 7;   // 周一作为每列第一天
```

每列 7 天，第一列用空白补齐。不补的话，同一行会随起始日期变化而对应不同的星期几，
看起来像乱码。

JS 的 `getUTCDay()` 里**周日是 0**，所以 `(day + 6) % 7` 才是"周一 = 0"。

## 4. 一次打卡的完整时间线

```
T0  用户点"打卡"
    → POST /api/v1/checkins

T1  后端（同一个事务里）
    → today = LocalDate.now(clock)         上海时区的今天
    → INSERT checkins(user_id, today)      唯一约束冲突 → 409
    → INSERT point_events(CHECKIN, +1)
    → 查近 60 天日期，从今天往回数 → streak
    → streak == 7 ? INSERT point_events(STREAK_7, ref_id=本段第 1 天, +5)
    → UPDATE users SET total_points = total_points + 6
    → 返回 { streak: 7, gained: 6, totalPoints: 52, level: 2 }

T2  前端
    → 直接把返回的数字填进界面（不刷新页面）
    → 按钮变成"今天已打卡"

T3  凌晨 03:10
    → 对账任务：total_points 与流水汇总对比
    → 有差异 → ERROR 日志 + 按流水修正
```

---

## 5. 六个容易写错的细节

### 5.1 用 `LocalDate.now()`

服务器在 UTC 时，凌晨 0–8 点打卡的人会被算到前一天。

### 5.2 先 `exists` 再 `insert`

并发下两个请求都查到"没打过"，于是写两条。唯一约束才是保证。

### 5.3 用 `save` 而不是 `saveAndFlush`

INSERT 攒到提交时才执行，唯一约束异常在切面之外抛出，变成 500。

### 5.4 `ref_id` 用当天或用户 id

用当天 → 重复请求重复发奖；用用户 id → 断签后再也拿不到。

### 5.5 定时任务不兜异常

`@Scheduled` 里抛出的异常不会重试、也不会让任务失败——它会**静默消失**。

### 5.6 前端复制等级阈值

两边各算一遍，改了一边就漂移。

## 6. 反面教材

| 写法 | 后果 |
|---|---|
| `LocalDate.now()` | 凌晨打卡算错天，连续段错乱 |
| 用 `created_at` 判断"今天" | 跨零点争议，且依赖服务器时区 |
| 逐天查库算连续 | 60 次查询，且逻辑难测 |
| 积分直接 `+1` 不记流水 | 出错了无法发现也无法恢复 |
| 总分"查出来加一再 save" | 并发丢分 |
| 对账只修不告警 | 真正的 bug 永远发现不了 |
| 对账只告警不修 | 用户一直看着错的分 |
| 打卡后 `router.refresh()` 整页刷新 | 体验抖动，还会丢输入状态 |

## 7. 怎么验证（Gate G4 的实测）

**单测（不碰数据库，靠可拨时钟）**

| 用例 | 期望 |
|---|---|
| 单次打卡 | +1，streak=1 |
| 连续第 7 天 | +1+5=6 |
| 第 8~13 天 | 每天 +1，无奖励 |
| 第 14 天 | +1+10=11 |
| 第 30 天 | +1+20=21 |
| 断签后连 7 天 | 再次拿到 +5 |
| 重复打卡 | 409，不再加分 |
| UTC 15:30 / 16:30 | 分别记在上海当天 / 次日 |

**等级边界**：49→Lv1、50→Lv2、149→Lv2、150→Lv3、299→Lv3、300→Lv4、599→Lv4、600→Lv5。

**集成测试**：真实唯一约束 → 第一次 201、第二次 409、总分只加一次。

**对账**：一致时 0 条；改错能被发现并修正；修完再跑归零。

**端到端（真起前后端）**：

| 步骤 | 结果 |
|---|---|
| 补 6 天历史打卡后今天打卡 | `streak=7`，`gained=6` |
| 重复打卡 | 409 `ALREADY_CHECKED_IN` |
| 首页 | 200，含"团队打卡"，热力图出现颜色分档 |
| 个人页 | 200，含 Lv 徽章与打卡记录 |

## 9. 自测题

1. 为什么"今天"必须按 Asia/Shanghai 算？
2. 为什么打卡要用 `saveAndFlush` 而不是 `save`？
3. 为什么不能"先查有没有打过再插入"？
4. 连续段奖励的 `ref_id` 为什么用"本段第一天"？
5. 积分为什么要记流水，而不是只存总分？
6. 对账为什么既要在日志里报错，又要修正？
7. 定时任务里为什么必须自己 try/catch？

<details>
<summary>答案</summary>

1. 用户按北京时间的自然日理解"今天"。服务器若在 UTC，凌晨 0–8 点打卡会被算到前一天，连续段错乱。
2. `save` 可能把 INSERT 攒到提交时执行，唯一约束异常会在事务切面之外抛出，变成 500 而不是 409。
3. 并发下两个请求会同时查到"没打过"从而双写。数据库唯一约束才是最终保证。
4. 用当天 → 同一天重复请求会重复发奖；用用户 id → 断签后永远拿不到第二次。用本段第一天，两者都对。
5. 只有总分的话，出错时既发现不了（没有对照）也恢复不了（不知道应该是多少）。
6. 只修不告警会让真正的 bug 永远隐藏；只告警不修会让用户一直看到错误的分。
7. `@Scheduled` 抛出的异常不会重试、也不会标记任务失败，它会静默消失，等于这个任务不存在。

</details>

## 10. 术语

| 名词 | 一句话 |
|---|---|
| 业务日期 | 按用户所在时区的自然日切分，与时间戳区分 |
| 可拨时钟 | 测试里能设定、推进的 `Clock`，让日期规则可测 |
| 连续段（streak） | 从今天往回数、未断档的连续天数 |
| 账本 | 只追加的事件流水，可对账、可去重 |
| 对账 | 比对缓存值与流水汇总，发现并修正分叉 |
| 幂等拒绝 | 重复请求返回 409 而不是报错，表示"已经是这个状态了" |
