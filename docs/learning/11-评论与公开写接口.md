> **本篇目标**：理解评论的两级限制、软删的两种表现、以及**全站唯一不需要登录的写接口**该怎么防。

## 0. 先讲人话

到这一批为止，系统已经能发内容了。但**没有人能讨论**，也没有任何渠道让访客说话。

这一批加两样东西：

```
成员之间：评论（可以回复）
访客对团队：留言
```

两件看起来都很简单——"不就是往表里插一行吗"。但它们各自踩到一个真实问题：

| 功能 | 真正的问题 |
|---|---|
| 评论 | **树会长歪**：允许回复的回复，渲染、折叠、计数全部复杂一个数量级 |
| 留言 | **不需要登录就能写**，是全站唯一的口子，会被脚本刷爆 |

---

## 1. 先理解问题

### 1.1 为什么评论只允许两级

三级评论长这样：

```
评论 A
└── 回复 B
    └── 回复 C
        └── 回复 D ...
```

看起来只是"多一层"，但真实成本在别处：

- **渲染**：从"两层循环"变成"递归组件"，还要处理缩进、折叠、深度限制
- **计数**：`A 有 12 条回复` —— 回复的回复算不算 A 的？
- **通知**（二期）：要通知整条链上的人吗？
- **加载**：一页 20 条，每条的子树大小不可预测，分页没法做

而团队博客的讨论规模根本用不上。所以：

```
一级评论（parent_id = null）
└── 回复（parent_id = 一级评论 id）
    └── ❌ 再回复 → 422
```

**注意"不能三级"这条规则要写在两个地方**：Service 里给人话，数据库触发器做最终保证。

### 1.2 删评论为什么不能真删

假设 B 回复了 A，然后 A 被删了：

```
真删 A → B 变成孤儿，界面上出现一条"回复了一个不存在的东西"的评论
```

所以用**软删**（`deleted_at`），并且分两种表现：

| 情况 | 界面上 |
|---|---|
| 删掉的评论**有回复** | 保留节点，显示"该评论已删除"，回复还在下面 |
| 删掉的评论**没有回复** | 整条不返回（不留无意义的占位） |

这就是几乎所有论坛的做法。

### 1.3 留言接口为什么特殊

```
POST /api/v1/feedback       ← 不需要登录
```

这是全站**唯一**一个匿名写接口。它的问题不是"数据对不对"，而是：

- 一个脚本一分钟能灌几十万条
- 数据库满了，管理员还以为是真人在反馈
- 加验证码？一期没有前端验证码组件，而且体验差

三层便宜且有效的防护：

| 层 | 手段 | 挡住什么 |
|---|---|---|
| 1 | **蜜罐字段** | 简单脚本（会填表单所有字段） |
| 2 | **IP 限流** | 同一来源的批量提交 |
| 3 | **IP 只存哈希** | 万一数据泄露，不暴露访客地址 |

### 1.4 蜜罐为什么要"假装成功"

如果蜜罐字段有值时返回 400：

```
机器人：收到 400，说明这个字段被检测到了 → 下次跳过它
```

如果返回 200 但什么都不存：

```
机器人：收到 200，以为成功了，继续用同样的方式提交（继续被丢弃）
```

**让攻击者得不到反馈**，比拦住他一次更有价值。

## 2. 设计：四个问题

| 问题 | 答案 | 位置 |
|---|---|---|
| 怎么禁止三级 | Service 判断（422）+ 数据库触发器兜底 | `CommentService` / `check_comment_depth` |
| 父评论挂错内容怎么办 | 校验 `parent.targetId == request.targetId` | `CommentService.create` |
| 软删怎么展示 | 有回复留占位，无回复隐藏 | `CommentService.list` |
| 匿名写接口怎么防 | 蜜罐 + 每 IP 每小时 3 条 + IP 哈希 | `FeedbackService` / `FeedbackRateLimiter` |

## 3. 代码逐行

### 3.1 两级校验：Service 给人话，数据库做保证

```java
if (parentId != null) {
    Comment parent = commentRepository.findById(parentId)
            .orElseThrow(() -> new BusinessException(NOT_FOUND, "被回复的评论不存在"));
    if (parent.getTargetType() != targetType || !parent.getTargetId().equals(request.targetId())) {
        throw new BusinessException(VALIDATION_FAILED, "父评论不属于该内容");
    }
    if (!parent.isRoot()) {
        // 数据库触发器也会拦，但这里要给出人能看懂的 422
        throw new BusinessException(RULE_VIOLATED, "只支持两级评论，不能回复一条回复");
    }
}
```

**为什么要校验"父评论属于同一个目标"**：不加这一条，你可以把 A 项目下的评论挂到 B 项目下——评论树会变得无法解释。

**为什么数据库还要有触发器**：

```sql
CREATE FUNCTION check_comment_depth() RETURNS trigger AS $$
BEGIN
  IF NEW.parent_id IS NOT NULL THEN
    IF EXISTS (SELECT 1 FROM comments WHERE id = NEW.parent_id AND parent_id IS NOT NULL) THEN
      RAISE EXCEPTION 'REPLY_DEPTH_EXCEEDED';
    END IF;
  END IF;
END $$ LANGUAGE plpgsql;
```

Service 是"正常路径"，触发器是"任何路径"——将来有人写批量导入脚本、直接连库改数据，`Service` 那层就被绕过了。

**但触发器抛的错没人看得懂**（`REPLY_DEPTH_EXCEEDED`），所以两层都要。

### 3.2 软删的两种表现

```java
for (Comment root : roots) {
    List<CommentResponse> replies = repliesByParent.getOrDefault(root.getId(), List.of()).stream()
            .filter(reply -> !reply.isDeleted())          // 已删的回复直接不显示
            .map(...)
            .toList();

    if (root.isDeleted() && replies.isEmpty()) {
        continue;                                     // 已删且没有回复：整条不返回
    }
    result.add(CommentResponse.of(root, usernames.get(...), replies));
}
```

而 `CommentResponse` 里：

```java
content = comment.isDeleted() ? null : comment.getContent()
```

一个 `deleted` 标记 + `content = null`，前端就知道该渲染"该评论已删除"。

**为什么用 null 而不是空字符串**：空字符串是"用户发了一条空白评论"（虽然被校验拦住，但语义上可能），`null` 才是"内容不存在"。

### 3.3 蜜罐

```java
public boolean submit(FeedbackCreateRequest request, String ipHashSource) {
    if (request.website() != null && !request.website().isBlank()) {
        return false;      // 静默丢弃，调用方仍然回 200
    }
    ...
}
```

Controller 那边完全不管返回值：

```java
@PostMapping
public ApiResponse<Void> submit(...) {
    feedbackService.submit(request, clientKey(httpRequest));
    return ApiResponse.ok(null);      // 一律 200
}
```

**为什么字段叫 `website`**：机器人也会读字段名。`hidden`、`honeypot` 这种名字会被识别；`website` 是表单里很常见的字段。

前端怎么藏：

```tsx
<div aria-hidden="true" className="absolute -left-[9999px] top-auto h-px w-px overflow-hidden">
  <input tabIndex={-1} autoComplete="off" ... />
</div>
```

**为什么不用 `display: none`**：有些爬虫会跳过 `display:none` 的字段（它们也知道那是陷阱），但不会跳过"在屏幕外"的字段。`tabIndex={-1}` 保证真人用 Tab 键不会撞上它。

### 3.4 限流：内存 + 上限

```java
public Long checkAndRecord(String key) {
    Instant now = Instant.now(clock);
    if (windows.size() > MAX_TRACKED_ENTRIES) {
        windows.clear();     // 键来自外部输入，无上限就会被撑爆
    }
    Window window = windows.compute(key, (k, current) -> {
        if (current == null || current.startedAt.plus(WINDOW).isBefore(now)) {
            return new Window(now, 1);
        }
        return new Window(current.startedAt, current.count + 1);
    });
    if (window.count > LIMIT) {
        return Math.max(Duration.between(now, window.startedAt.plus(WINDOW)).toSeconds(), 1);
    }
    return null;
}
```

**为什么必须有 `MAX_TRACKED_ENTRIES`**：`ConcurrentHashMap` 的键是客户端 IP——**外部可控**。不设上限，攻击者换 IP 就能把内存撑爆。清空的代价是短暂放宽限流，但不会 OOM。

**为什么用内存而不是 Redis**：单实例部署，重启后计数清零，代价只是"多放几条留言"。引入 Redis 会多一个必须运维的组件。

### 3.5 IP 只存哈希

```java
HashUtils.sha256Hex(ipHashSource)
```

需要时能判断"是不是同一个来源"（比如看有没有人在刷），但拿不到真实地址。留存明文 IP 属于多余的个人信息（P-14）。

## 4. 一次评论的完整时间线

```
T0  成员在项目详情页输入"写得不错"，点发表
    → POST /api/v1/comments {targetType, targetId, content}

T1  后端
    → 安全链：登录了吗？✓
    → Service：目标存在吗？（成果必须是 ACTIVE）✓
    → 没有 parentId → 一级评论
    → 入库 → 201

T2  另一个成员点"回复"
    → parentId = 上面那条的 id
    → Service：父评论存在 ✓ 属于同一目标 ✓ 父是根 ✓
    → 入库 → 201

T3  有人试图回复那条"回复"
    → Service：parent.isRoot() == false → 422 "只支持两级评论"

T4  作者删掉第一条评论
    → DELETE /api/v1/comments/{id}
    → 归属校验（作者或管理员）
    → deleted_at = now()（不真删）

T5  访客打开页面
    → GET /api/v1/comments
    → 那条评论有回复 → 保留节点，content=null，deleted=true
    → 前端渲染"该评论已删除" + 下面的回复
```

---

## 5. 五个容易写错的细节

### 5.1 只靠 Service 拦三级

将来有人写批量导入、直接连库改数据，Service 就被绕过了。数据库触发器是"任何路径"的保证。

### 5.2 软删直接把行删掉

回复会变孤儿。要么一起删（丢失讨论上下文），要么软删（正确）。

### 5.3 不校验"父评论属于同一目标"

可以把 A 项目的评论挂到 B 项目下，评论树无法解释。

### 5.4 蜜罐命中返回 400

等于告诉机器人"你被识别了"，它下次就换填法。

### 5.5 限流的 Map 不设上限

键来自外部输入（IP），无上限就能被撑爆内存。

---

## 6. 反面教材

| 写法 | 后果 |
|---|---|
| 允许无限层级 | 渲染要递归、计数说不清、分页做不了 |
| 前端隐藏蜜罐用 `display:none` | 一部分爬虫直接跳过这个字段 |
| 蜜罐命中返回 403 | 攻击者立刻知道被检测，换个字段名继续 |
| 限流只按 IP 不设上限 | 内存可被撑爆 |
| 存明文 IP | 数据泄露时连带暴露访客地址 |
| 删除不校验归属 | 任何人都能删任何人的评论 |
| 软删后把整条隐藏 | 有回复的评论消失，下面的回复变孤儿 |

## 7. 怎么验证（Gate G6 的实测）

**后端测试**：`CommentIntegrationTest` 7 个 + `FeedbackIntegrationTest` 5 个。

| 用例 | 断言 |
|---|---|
| 发表 + 回复 | 两级正确展示 |
| 回复的回复 | **422** `RULE_VIOLATED`（Service 与 HTTP 两层都测） |
| 软删（有回复） | `deleted=true`、`content=null`、回复仍在 |
| 软删（无回复） | 整条不出现 |
| 删别人的 | 403 |
| 管理员删别人的 | 200 |
| 留言（匿名） | 200，库里 1 条，`ip_hash` 长度 64 且不含 IP 片段 |
| 蜜罐有值 | **200 但库里 0 条** |
| 同 IP 第 4 条 | 429 |

**端到端实测**（真起前后端）：

```
[1] 发表一级评论        → 201
[2] 发表回复            → 201
[3] 回复的回复          → 422 RULE_VIOLATED
[4] 访客看详情页        → 200，一级与二级都可见
[5] 作者删除一级评论    → 200
[6] 删除后              → 内容不显示、回复仍在、"该评论已删除"占位出现

[7] 访客匿名留言        → 200
[8] 管理员看未读        → 200 且能找到
[9] 标记已读            → 200，之后不在未读列表
```

## 9. 自测题

1. 为什么评论只允许两级？三级会带来哪些成本？
2. 既然 Service 已经能拦三级，为什么数据库还要有触发器？
3. 软删为什么分"留占位"和"直接隐藏"两种？
4. 蜜罐命中为什么要返回 200 而不是 400？
5. 蜜罐字段为什么用 `display:none` 不好？
6. 限流的 Map 为什么要设 `MAX_TRACKED_ENTRIES`？
7. IP 为什么只存哈希？

<details>
<summary>答案</summary>

1. 渲染要递归组件、回复计数语义不清、通知链复杂、分页无法预估大小；团队博客规模用不上。
2. 触发器保证"任何路径"——批量导入、直接连库改数据都会绕过 Service。但触发器抛的错误名没人看得懂，所以两层都要。
3. 有回复的评论突然消失，会让下面的回复变成孤儿（"回复了一个不存在的东西"）；没有回复的评论直接隐藏，不留无意义的占位。
4. 返回 400 等于告诉机器人"这个字段被检测到了"，它下次会换填法；返回 200 但丢弃，攻击者得不到反馈。
5. 一部分爬虫会跳过 `display:none` 的字段（它们也知道那是陷阱），但不会跳过"在屏幕外"的字段。
6. 键来自外部输入（客户端 IP），不设上限就能被换 IP 撑爆内存。
7. 需要判断"是否同一来源"，但不需要知道真实地址；留存明文 IP 属于多余的个人信息。

</details>

## 10. 术语

| 名词 | 一句话 |
|---|---|
| 两级评论 | 一级评论 + 回复，不允许再嵌套 |
| 软删 | 只打时间戳，数据保留 |
| 孤儿回复 | 父评论被删后无人认领的回复 |
| 蜜罐（honeypot） | 正常用户看不见、机器人会填的诱饵字段 |
| 固定窗口限流 | 每个时间窗口内计数，超过就拒 |
| IP 哈希 | 存 SHA-256 而不是明文地址 |
| 兜底约束 | 应用层之外的最终保证（数据库触发器/约束） |
