# 08 · 第一条垂直切片（零基础版）

> **前置**：[00-零基础必读](./00-零基础必读.md)、[01-用户实体层](./01-用户实体层.md)、[07-前端骨架](./07-前端骨架与登录页.md)。
> **本篇目标**：打通"数据库 → 接口 → 页面"这一整条路，并理解分页、隐私裁剪、404 状态码三个坑。
> **对应门禁**：批次 2，Gate G2 —— 未登录访问 `/` 和 `/u/member1`，数据来自数据库；
> **改库里的 bio，刷新页面就变**。

## 0. 先讲人话

前两批做的是"基础设施"：表、认证、限流、邀请、前端壳。它们都能跑，但**用户看不到任何东西**。

这一批要证明一件事：

```
数据库里的一行 → 接口里的一段 JSON → 页面上的一张卡片
```

这条线打通了，后面每一批都是照抄这个形状。所以文档里叫它"第一条垂直切片"——
不是"把用户模块做完"，而是"**切一条最薄的、从头到尾能跑通的**"。

---

## 1. 先理解问题

### 1.1 分页：为什么不用 `?page=2&size=20`

最直觉的分页是 offset：

```sql
select * from users order by created_at desc limit 20 offset 20;   -- 第 2 页
```

问题在于"offset 20"的意思是"跳过前 20 条"。而列表是**会变的**：

```
第 1 页：A B C ... T（20 条）
此时有人新增了 X（排在最前面）
第 2 页：offset 20 → 从第 21 条开始
        但原来的第 20 条 T 现在变成了第 21 条 → T 又出现一次（重复）
```

有人删除则相反：会**漏掉**一条。

**游标分页**换个问法："接着这一条之后"：

```sql
select * from users
 where (created_at, id) < (:cursor_created_at, :cursor_id)
 order by created_at desc, id desc limit 20;
```

数据怎么变，都不会重复或漏。

### 1.2 游标为什么要带两个字段

因为 `created_at` **不唯一**。

本项目的种子数据是一个 `INSERT ... SELECT` 语句插入 12 个用户的——Postgres 的 `now()`
返回的是**事务开始时间**，所以这 12 行的 `created_at` **完全相同**。

只按时间翻页时，"接着 10:00:00 之后"会把这 12 行要么全带上、要么全跳过。加上 `id`
作为第二排序键（tiebreaker），才有严格的全序。

### 1.3 隐私字段：一个接口两种视角

`GET /users/{username}` 是给**访客**看的，但 `users` 表里有邮箱。

规则（S-10）：`email_public = true` 才返回邮箱。

错误做法是在前端判断——前端能做的是"显示了不显示"，但**数据已经发出去了**，
抓包就能看到。正确做法是后端按开关裁剪，前端只渲染拿到的字段。

### 1.4 404：UI 对不代表状态码对

`/u/不存在的用户` 应该返回 **404**，不是 200 配一个"用户不存在"的页面。

搜索引擎、监控、curl 全都看状态码。返回 200 会让爬虫把"用户不存在"页也收录进去。

## 3. 代码逐行

### 3.1 游标：编码、解码、容错

```java
public static String encode(OffsetDateTime createdAt, UUID id) {
    String raw = createdAt.toInstant() + "|" + id;
    return Base64.getUrlEncoder().withoutPadding()
            .encodeToString(raw.getBytes(UTF_8));
}
```

**为什么用 `Instant` 的字符串而不是毫秒数**：数据库的 `timestamptz` 精确到**微秒**。
截断到毫秒后，同一毫秒内的行会被错误排除——表现为"翻页偶尔少一条"，极难复现。

**为什么 Base64**：让客户端把它当成不透明字符串。它不是加密（不含隐私），
只是防止有人"自己拼一个游标"当成 API 特性来依赖。

```java
} catch (RuntimeException ex) {
    throw new BusinessException(ErrorCode.VALIDATION_FAILED, "cursor 无效");
}
```

客户端传来乱码时返回 **400**，而不是让它冒成 500——这是"错误归属"问题：
这是客户端的错，不该让服务端背锅（500 会让人去查服务端日志）。

### 3.2 查询：keyset

```java
@Query("select u from User u where u.deletedAt is null order by u.createdAt desc, u.id desc")
List<User> findFirstPage(Pageable pageable);

@Query("""
        select u from User u
         where u.deletedAt is null
           and (u.createdAt < :createdAt or (u.createdAt = :createdAt and u.id < :id))
         order by u.createdAt desc, u.id desc
        """)
List<User> findPageAfter(@Param("createdAt") OffsetDateTime createdAt,
                         @Param("id") UUID id, Pageable pageable);
```

三个细节：

- **`u.deletedAt is null`**：软删账号不能出现在列表里（D-13）。这个条件必须写在**查询里**，
  不要查出来再在 Java 里过滤——那样分页数就不对了。
- **`or (createdAt = :createdAt and id < :id)`**：这就是 tiebreaker 的写法。
- **`order by` 必须和 cursor 条件一致**：顺序不一致，keyset 就会跳着走。

### 3.3 Service：多取一条判断有没有下一页

```java
List<User> rows = cursor == null
        ? userRepository.findFirstPage(PageRequest.of(0, size + 1))
        : userRepository.findPageAfter(..., PageRequest.of(0, size + 1));

boolean hasNext = rows.size() > size;
List<User> page = hasNext ? rows.subList(0, size) : rows;
String nextCursor = hasNext
        ? CursorUtils.encode(last.getCreatedAt(), last.getId())
        : null;
```

**为什么取 `size + 1`**：多查一条就知道后面还有没有。比再发一次 `count(*)` 便宜，
也不会因为两次查询之间有人插入而算错。

**`limit` 的收敛**：

```java
if (limit <= 0) return DEFAULT_PAGE_SIZE;      // 20
return Math.min(limit, MAX_PAGE_SIZE);          // 100
```

`?limit=9999` 不报错，静默收敛到 100。分页参数写错不该让用户看到 400。

### 3.4 隐私裁剪：写在 DTO 里

```java
public static UserResponse fromPublic(User user) {
    return from(user, user.isEmailPublic());
}

private static UserResponse from(User user, boolean includeEmail) {
    return new UserResponse(..., includeEmail ? user.getEmail() : null, ...);
}
```

配置里 `spring.jackson.default-property-inclusion: non_null`，所以 `null` 字段会被**省略**，
不是返回 `"email": null`。两者对客户端都不难处理，但"字段不存在"更明确地表达了
"你没有权限看"，而不是"这个字段恰好是空的"。

### 3.5 前端：服务端组件的三件事

**① 构建时不能依赖后端。**

`next build` 会尝试预渲染页面。CI 里没有 API 在跑，预渲染就会失败：

```
Error [ApiError]: 网络异常，请检查后端是否已启动
Export encountered an error on /page
```

修法是显式声明动态：

```tsx
export const dynamic = "force-dynamic";
```

**为什么光写 `cache: "no-store"` 不够**：`no-store` 写在 `fetch` 里，而我们的 `fetch`
被包在 `request()` 函数里——Next 的静态分析**看不穿函数调用**，它只认写在页面文件里的
`fetch`。所以要用 `dynamic` 显式告诉它。

**② 服务端没有"当前站点"。**

浏览器里 `fetch("/api/v1/users")` 会自动补上 `http://localhost:3000`；Node 里没有这个
概念，相对路径会直接失败。所以新增 `lib/server-api.ts`：

```ts
const ORIGIN = process.env.API_ORIGIN ?? "http://127.0.0.1:8080";
export const serverApi = {
  listMembers: (cursor?: string, limit = 20) =>
    request<UserPage>(`/api/v1/users?${pageQuery(cursor, limit)}`, { base: ORIGIN }),
};
```

浏览器仍走同源代理（`/api/*`），服务端直连后端——两条路都通，且都不需要 CORS。

**③ `notFound()` 要能真的返回 404。**

```tsx
try {
  profile = await serverApi.getUserProfile(username);
} catch (error) {
  if (error instanceof ApiError && error.code === "NOT_FOUND") {
    notFound();     // 抛特殊错误，渲染 not-found 页面
  }
  throw error;
}
```

一开始我在 `app/loading.tsx` 加了一个全局骨架，结果 `/u/nobody_here` 返回 **200**——
原因在 §5.3。

## 4. 完整时间线

```
T0  浏览器 GET /（未登录）
    → Next 服务端组件执行
    → serverApi.listMembers() → GET http://127.0.0.1:8080/api/v1/users?limit=12
    → 后端：Security 放行（GET /users 是公开的）→ Controller → Service → keyset 查询
    → 返回 {"ok":true,"data":{"items":[...],"nextCursor":null}}
    → 渲染成 HTML 一次性返回
    → 用户在首屏就看到成员卡片（没有"先空一下再填"）

T1  点某个成员 → GET /u/member1
    → await params → serverApi.getUserProfile("member1")
    → 200 → 渲染个人页

T2  访问 /u/nobody_here
    → 后端返回 404 NOT_FOUND
    → 前端 notFound() → HTTP 404 + 404 页面

T3  Gate G2 的验收动作
    → psql: update users set bio='...' where username='member1'
    → 刷新 /u/member1 → 新简介立刻出现
    → 因为 no-store，没有任何一层缓存
```

## 5. 六个容易写错的细节

### 5.1 用 offset 分页

见 §1.1。表现：翻页时偶尔看到重复的人，或者漏掉一个人。

### 5.2 游标只带时间

见 §1.2。种子数据同一个事务插入，`created_at` 完全相同——边界处会整批丢或整批重复。

### 5.3 `loading.tsx` 让 404 变成 200

`app/loading.tsx` 会为路由创建 Suspense 边界，触发**流式响应**：

```
1. 先把 HTML 骨架发出去（HTTP 200 + 半截页面）
2. 数据到了再流式补上
3. 这时才执行 notFound() —— 但响应头早就发出去了，状态码改不了
```

结果是：**UI 正确、状态码错误**。curl、爬虫、监控看到的都是 200。

本项目选择删掉全局 `loading.tsx`，保证 404 语义正确。代价是首屏没有骨架屏——
成员列表在局域网内是毫秒级，可以接受。

> 如果以后一定要骨架，正确做法是把"是否存在"的判断提前到 `generateMetadata`（它在
> 发响应头之前执行），或者把 404 处理放到路由段之外。

### 5.4 忘了 `deletedAt is null`

软删的用户会出现在列表里，点进去 404——看起来像"列表数据不对"，其实是查询漏了条件。

### 5.5 前端判断 `email_public`

数据已经发出去了，抓包就能看到。裁剪必须在后端。

### 5.6 构建时打后端

见 §3.5 ①。CI 上没有后端在跑，`force-dynamic` 是必需的。

## 6. 反面教材

| 写法 | 后果 |
|---|---|
| `limit/offset` 分页 | 数据变动时重复或漏行 |
| 游标只编码时间 | 同时间戳的行在边界处丢失 |
| 游标用毫秒 | 微秒级差异被抛弃，偶发丢行 |
| 查询不带 `deletedAt is null` | 软删账号出现在列表里 |
| 前端裁剪邮箱 | 抓包可见，等于没裁 |
| 明文 cursor（如直接传 id） | 客户端会依赖格式，改不动 |
| `loading.tsx` + `notFound()` | UI 是 404、状态码是 200 |
| 构建时依赖后端 | CI 红，且离线开发无法 build |

## 9. 自测题

1. offset 分页在什么情况下会重复或漏行？为什么游标分页不会？
2. 游标为什么要带 `id`，只带 `created_at` 会怎样？
3. 为什么游标里存 `Instant` 字符串而不是毫秒数？
4. 为什么"多取一条"比再查一次 `count` 更好？
5. 邮箱裁剪为什么不能放前端？
6. `loading.tsx` 为什么会让 404 变成 200？
7. 为什么 Server Component 里不能写 `fetch("/api/...")`？
8. 为什么光写 `cache: "no-store"` 不够，还要 `force-dynamic`？

<details>
<summary>答案</summary>

1. offset 是"跳过 N 条"，数据在两次请求之间增删会让边界移动，于是重复或漏行；游标是"接着某个位置之后"，位置由数据本身决定，不受增删影响。
2. `created_at` 不唯一（同一事务插入的行时间相同），只按时间翻页会把同时间的行整批带上或跳过；加 id 才有严格全序。
3. `timestamptz` 精确到微秒，截断到毫秒会把同一毫秒内的行错误排除，表现为偶发丢行。
4. 多取一条只多一次行读取；`count` 是第二次往返，且两次查询之间数据可能变化（count 与后续查询不一致）。
5. 数据已经发给前端了，抓包就能看到；裁剪必须在服务端发出之前完成。
6. loading.tsx 创建 Suspense 边界 → 流式响应先把响应头（200）和骨架发出去；之后 notFound() 只能改页面内容，改不了已经发出的状态码。
7. Node 里没有"当前站点"的概念，相对 URL 无法解析；必须用绝对地址（API_ORIGIN）。
8. `no-store` 写在被包裹的 fetch 里，Next 的静态分析看不穿函数调用；`dynamic = "force-dynamic"` 是页面级的显式声明，构建时就不会去预渲染。

</details>

## 10. 术语

| 名词 | 一句话 |
|---|---|
| 垂直切片 | 一条从数据库到界面的最薄可运行路径 |
| keyset 分页 | 用"上一页最后一条的位置"翻页，而不是跳过 N 条 |
| 游标（cursor） | 编码了位置的不透明字符串 |
| tiebreaker | 排序键重复时用于确定顺序的第二排序键 |
| RSC | React Server Component，在服务端渲染的组件 |
| 流式响应 | 先把页面骨架发出去，数据到了再补 |
| 隐私裁剪 | 按规则决定返回哪些字段，而不是让前端隐藏 |
| 软删 | 不删行，只标记 `deleted_at` |
