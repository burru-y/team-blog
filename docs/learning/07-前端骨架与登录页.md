# 07 · 前端骨架与登录页（零基础版）

> **前置**：[00-零基础必读](./00-零基础必读.md) §1（HTTP）、§2（Cookie）；[02-JWT认证](./02-JWT认证.md)。
> **本篇目标**：理解前后端怎么连起来、登录状态存在哪、以及为什么"类型不能手写"。
> **对应代码**：`teamblog/web/`（Next.js 15 + TypeScript + Tailwind 4 + shadcn/ui）

---

## 0. 先讲人话

到现在为止，你的系统只有一个"会返回 JSON 的服务器"。用户不可能用 curl 登录。

前端要干四件事：

```
1. 把用户名密码发过去
2. 把返回的 access token 存起来
3. 之后的请求都带上它
4. 页面刷新后再把身份找回来
```

听起来简单，但有三个坑：

- 浏览器有**同源策略**：3000 端口的页面不能随便调 8080 的接口
- `access token` 存哪？存 localStorage 会被 XSS 偷，存内存刷新就没了
- 后端的字段改了，前端怎么**立刻知道**？

这一节就是把这四个问题逐个解掉。

---

## 1. 先理解问题

### 1.1 同源策略与代理

页面在 `localhost:3000`，接口在 `localhost:8080`——**端口不同就是不同源**。

浏览器的反应：

```
页面 → fetch("http://localhost:8080/api/v1/auth/login")
浏览器：先发一个 OPTIONS 预检请求，问后端"允许 3000 访问吗？"
后端没配 CORS 头 → 浏览器拒绝，控制台一片红
```

两条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| 配 CORS | 后端加 `Access-Control-Allow-Origin` 等头 | 要处理预检、Cookie 跨域（`SameSite`/`Secure`/`credentials`）一堆细节 |
| **代理**（本项目） | 前端 dev server 把 `/api/*` 转发到 8080，浏览器只看到"同源" | 多一层转发，但零跨域问题 |

代理的好处不止"省事"：**同源之后，httpOnly 的 refresh Cookie 会自动带上**。
跨域场景下 Cookie 需要 `SameSite=None; Secure` + `credentials: "include"`，
配置错一点就"登录后刷新又掉线"。

### 1.2 access token 存哪

三个选项，都有代价：

| 存哪 | 刷新页面还在吗 | 被 XSS 偷得到吗 |
|---|---|---|
| `localStorage` | ✅ 在 | ❌ **一行 JS 就能读走**（规范 T-19 禁止） |
| 内存（变量） | ❌ 没了 | ✅ 读不到（除非攻击者能执行代码） |
| httpOnly Cookie | ✅ 在 | ✅ 读不到 |

本项目的做法：**access token 只放内存，reload 之后用 refresh Cookie 换一个新的**。

这就是 1.3 设计的 refresh token 在客户端的用处——不只是"续期"，也是"恢复会话"。

### 1.3 类型从哪来

手写 interface 的问题：

```ts
// 前端手写
interface User { username: string; totalPoints: number }
// 后端某天把 totalPoints 改成了 points
// → 前端编译照样通过，运行时拿到 undefined，页面显示 NaN
```

规范 T-06 要求类型**只能来自 `openapi-typescript` 生成**。本项目已有
`docs/api/team-blog-api.openapi.yaml`，一条命令生成：

```bash
pnpm exec openapi-typescript ../../docs/api/team-blog-api.openapi.yaml -o src/lib/api-schema.d.ts
```

后端改字段 → 重新生成 → 前端编译报错。**契约漂移在 CI 阶段就暴露**，而不是上线后。

## 3. 代码逐行

### 3.1 代理

```ts
const nextConfig: NextConfig = {
  async rewrites() {
    return [{
      source: "/api/:path*",
      destination: `${process.env.API_ORIGIN ?? "http://127.0.0.1:8080"}/api/:path*`,
    }];
  },
};
```

前端代码里一律写 `/api/v1/...`，**不写主机名**。生产环境 Nginx 做同样的反代，
前端一行都不用改（这也是 03 方案里 `/api` 反代的原因）。

### 3.2 唯一的 HTTP 入口（T-08）

```ts
async function request<T>(path: string, options: RequestOptions = {}): Promise<T> {
  const response = await fetch(path, {
    method: options.method ?? "GET",
    cache: "no-store",                                   // ①
    headers: {
      ...(options.body === undefined ? {} : { "Content-Type": "application/json" }),
      ...(options.token ? { Authorization: `Bearer ${options.token}` } : {}),  // ②
    },
    body: options.body === undefined ? undefined : JSON.stringify(options.body),
  });

  const envelope = await response.json().catch(() => null);

  if (!response.ok || !envelope?.ok) {                   // ③
    throw new ApiError(envelope?.error?.code ?? "INTERNAL", ..., response.status);
  }
  return envelope.data;
}
```

三个点：

**① `cache: "no-store"` 是必须的。** 漏了这个参数，Next 可能把 A 的 `/me` 结果
缓存给 B——**数据泄漏**（T-03）。这种 bug 只在多用户场景下出现，测试很难发现。

**② token 走 `Authorization` 头，不走 Cookie。** 浏览器不会自动带这个头，
所以 CSRF 天然无效（02-§3.3）。

**③ 统一解信封、统一抛 `ApiError`。** 业务代码只写 `try/catch`，
不用每个调用点自己判断 `ok`。规范 T-08 要求所有 fetch 走同一个 client。

### 3.3 会话：`SessionProvider`

```tsx
export function SessionProvider({ children }) {
  const [user, setUser] = useState<UserResponse | null>(null);
  const [token, setToken] = useState<string | null>(null);
  const [loading, setLoading] = useState(true);

  // 启动时：用 refresh Cookie 换 access token
  useEffect(() => {
    (async () => {
      try {
        const tokens = await bootstrapSession();
        await adopt(tokens);          // 拿 token 再查一次 /me
      } catch {
        // 没有 Cookie：正常状态，不是错误
      } finally {
        setLoading(false);
      }
    })();
  }, []);
```

**为什么启动时要多查一次 `/me`**：token 里虽然有 role，但没有头像、积分这些展示字段。
而且"这个用户还在吗"必须由服务端回答（软删的账号不该恢复会话）。

**为什么有个模块级的 `refreshPromise`**：

```ts
let refreshPromise: Promise<TokenResponse> | null = null;

function bootstrapSession() {
  refreshPromise ??= api.refresh().catch((e) => { refreshPromise = null; throw e; });
  return refreshPromise;
}
```

React 开发模式（StrictMode）会把 effect 跑**两遍**。如果不共享 Promise：

```
请求A：refresh(rt1) → 服务端轮换，返回 rt2
请求B：refresh(rt1) → 服务端发现 rt1 已被轮换 → 判定重放 → 撤销全部会话
结果：开发环境一刷新就被踢下线
```

这正是 1.3 里"重放即全量撤销"的副作用。共享一个 Promise 只发一次请求就绕过了。

> 生产环境没有 StrictMode，这段代码在线上是"多余"的。但它不改变行为，
> 留着可以避免以后有人重开 StrictMode 时踩坑。

### 3.4 登录页

```tsx
async function handleSubmit(event) {
  event.preventDefault();
  setError(null);
  setSubmitting(true);
  try {
    await login(username, password);
    router.push("/"); router.refresh();     // refresh(): 让服务端组件重新渲染
  } catch (err) {
    setError(err instanceof ApiError ? messageFor(err.code) : "登录失败");
  } finally {
    setSubmitting(false);                    // 放 finally：失败也要恢复按钮
  }
}
```

**错误文案走 `messageFor(code)`，不直接渲染后端 message**（T-09）：
后端文案是给日志看的，前端要统一语气；两边各管各的，改文案不用重启后端。

### 3.5 邀请页：Next 15 的 `params` 是 Promise

```tsx
// 服务端组件：await 之后把 token 传给客户端表单
export default async function JoinPage({ params }: { params: Promise<{ token: string }> }) {
  const { token } = await params;
  return <JoinForm token={token} />;
}
```

Next 15 起 `params`、`searchParams`、`cookies()` 都是异步的（T-04）。
不 await 拿到的是 Promise，`token` 会是 `undefined`——而且**不报错**，只是行为诡异。

## 4. 一次登录的完整时间线

```
T0  用户打开 /login
    → SessionProvider 启动：POST /api/v1/auth/refresh（没有 Cookie）→ 401
    → 静默忽略，页面显示"未登录"

T1  填 admin1 / ChangeMe123!，点登录
    → POST /api/v1/auth/login（经 Next 代理到 8080）
    → 后端：限流检查 → BCrypt 比对 → 签 access token(30min) + 发 refresh Cookie
    → 200 {"data":{"accessToken":"eyJ..."}} + Set-Cookie: rt=...; HttpOnly

T2  前端拿到 token → 放进内存 → GET /api/v1/me 带上 Authorization
    → 200 {"data":{"username":"admin1","role":"ADMIN",...}}
    → Header 显示头像和用户名，跳转首页

T3  用户按 F5 刷新页面
    → 内存里的 token 没了（这是有意为之）
    → SessionProvider 再次启动：POST /refresh，这次 Cookie 里有 rt
    → 后端轮换：rt1 作废、发 rt2，返回新 access token
    → 前端拿到新 token → GET /me → 恢复登录态

T4  点"退出"
    → POST /api/v1/auth/logout（带上 rt Cookie）
    → 后端作废这张 refresh token，Set-Cookie 清空
    → 前端清空内存，跳登录页
```

## 5. 五个容易写错的细节

### 5.1 把 token 存进 localStorage

最"方便"的做法，也是最危险的：任何一段注入的 JS 都能读走，等于把 7 天会话交给 XSS。

### 5.2 忘了 `cache: "no-store"`

Next 的 fetch 默认会尝试缓存。`/me` 这种"按人返回"的接口一旦被缓存，
用户 A 可能看到用户 B 的数据（T-03）。

### 5.3 StrictMode 双请求触发重放

见 §3.3。表现：开发环境刷新页面就掉线，生产环境却正常——很容易被误判成"cookie 有问题"。

### 5.4 手写 interface

见 §1.3。它让"契约漂移"从编译期问题变成运行时问题。

### 5.5 直接用后端的 error.message

后端文案是给开发和日志看的（"用户名或密码错误"是刻意的安全设计），
前端要按 code 分支出自己的文案。直接渲染会让改文案变成改后端。

## 6. 反面教材

| 写法 | 后果 |
|---|---|
| 直连 `http://localhost:8080` 不配 CORS | 浏览器预检失败，所有请求红 |
| token 存 localStorage | 一次 XSS = 7 天会话被偷 |
| fetch 不写 `no-store` | 可能把 A 的数据缓存给 B |
| 手写 `interface User` | 后端改字段，前端不报错，运行时 undefined |
| `params` 不 await | `token` 是 Promise，页面行为诡异且不报错 |
| 每个组件自己 fetch | 错误处理、baseURL、鉴权各写一套（T-08 禁止） |
| 提交按钮不 disabled | 双击提交两次（后端幂等是兜底，不是替代，T-15） |

## 7. 怎么验证（没有前端单测时）

1.7 阶段不做组件测试（价值低、成本高），用两道检查：

**① `pnpm build`** —— 类型错误、lint 错误、服务端/客户端组件混用的问题都会在这里暴露。

**② 端到端冒烟（经代理）** —— 起后端 + `pnpm dev`，用 curl 打 3000 端口：

```bash
# 证明 rewrite 通了、Set-Cookie 能透传
curl -s -D - -X POST localhost:3000/api/v1/auth/login \
     -H "Content-Type: application/json" \
     -d '{"username":"admin1","password":"ChangeMe123!"}'
```

本项目的实测结果：

| 检查 | 结果 |
|---|---|
| 登录（经代理） | 200 + accessToken + `Set-Cookie: rt=...; HttpOnly; SameSite=Lax` |
| 带 token 访问 `/me` | 200，返回 admin1 的资料 |
| 错误密码 | 401 `UNAUTHENTICATED` |
| `/login`、`/join/xxx` 页面 | 200（SSR 外壳正常） |

> 顺带修了一个真 bug：请求体不是合法 JSON 时，后端返回的是 **500** 而不是 400。
> 这是联调里最容易忽略的一类错误——500 让人以为服务端挂了。

## 9. 自测题

1. 为什么用代理而不是配 CORS？代理还顺带解决了什么？
2. access token 为什么不放 localStorage？那刷新页面后怎么恢复登录？
3. 为什么 `SessionProvider` 启动时除了 refresh 还要再查一次 `/me`？
4. StrictMode 下"刷新就掉线"是怎么发生的？怎么解决？
5. 类型为什么必须从 OpenAPI 生成？
6. `cache: "no-store"` 漏了会出什么事？
7. Next 15 的 `params` 为什么必须 await？

<details>
<summary>答案</summary>

1. 不用处理预检、跨域 Cookie（SameSite/Secure/credentials）等一堆细节；代理让浏览器只看到同源，httpOnly Cookie 自动携带。生产由 Nginx 做同样的反代，前端代码不用改。
2. localStorage 能被任意一段注入的 JS 读走（XSS → 7 天会话）。access token 只放内存，刷新页面时用 refresh Cookie 换一个新的。
3. token 里没有头像、积分等展示字段；更重要的是"这个用户还在吗"必须由服务端回答（软删账号不该恢复会话）。
4. StrictMode 会把 effect 跑两遍，两次并发 refresh 携带同一个 token；后到的那次被服务端判为重放，触发全量撤销。用模块级 Promise 保证只发一次。
5. 手写 interface 等于本地复制契约，后端改字段前端不报错，运行时才炸。生成类型让漂移在编译期暴露。
6. Next 可能缓存 fetch 结果，导致 A 的 `/me` 数据被 B 看到（T-03）。
7. Next 15 起 `params` 是异步的，不 await 拿到的是 Promise，`token` 会是 undefined 且不报错。

</details>

## 10. 术语

| 名词 | 一句话 |
|---|---|
| 同源 | 协议 + 域名 + 端口三者相同 |
| CORS | 跨域资源共享，需要后端显式允许 |
| 预检（preflight） | 浏览器在真正的跨域请求前先发 OPTIONS 问一句 |
| rewrite | Next 的路径重写，把 `/api/*` 转发到后端 |
| Server Component | 在服务端渲染的组件，不能直接用 useState |
| Client Component | 加了 `"use client"`，可以交互、可以用浏览器 API |
| hydration | 服务端 HTML 到浏览器后接管成可交互 |
| 契约漂移 | 后端字段变了，前端类型没跟上 |
| XSS | 跨站脚本，往页面注入 JS 偷数据 |
