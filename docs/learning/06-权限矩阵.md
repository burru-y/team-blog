# 06 · 权限矩阵（零基础版）

> **前置**：[02-JWT认证](./02-JWT认证.md)（401/403 怎么来的）、[05-邀请注册](./05-邀请注册.md)（URL 级规则）。
> **本篇目标**：让"每个接口的权限都被验证过"从口头约定变成 CI 检查。
> **对应代码**：`src/test/java/com/teamblog/auth/PermissionMatrixTest.java`

---

## 0. 先讲人话

前面五节做了：登录、刷新、限流、邀请。每个接口都配了权限规则（`permitAll` / `authenticated` / `hasRole`）。

问题来了：**你怎么保证下一个接口也配对了？**

```
今天：加接口 → 记得配权限 → 写测试    ✅
三个月后：加接口 → 忙着赶功能 → 忘了 → 上线后被扫出来   ❌
```

权限漏配是**最不容易被发现**的 bug：功能一切正常，只是多了个口子。

这一节要做的事很朴素：**把"每个接口都得有权限用例"变成一条会自动失败的测试。**

---

## 1. 先理解问题

### 1.1 权限测试和普通测试不一样

普通功能测试：给输入，断言输出。

权限测试：**同样的输入，换身份，断言不同的结果**。

```
GET /api/v1/me    匿名   → 401
GET /api/v1/me    成员   → 200
POST /admin/invites  匿名 → 401
POST /admin/invites  成员 → 403
POST /admin/invites  管理员 → 200
```

所以它的形状天然是**一张表**：行是接口，列是身份。

### 1.2 光有表还不够

写了一张漂亮的表，跑全绿。然后有人加了个接口 `DELETE /api/v1/projects/{id}`，
忘了往表里加行——**测试还是全绿**，因为表里根本没有它。

所以真正的目标不是"表全绿"，而是：**"表没覆盖到的接口"必须让测试失败。**

### 1.3 401 和 403 各验证什么

| 场景 | 期望 | 验证的是 |
|---|---|---|
| 匿名打受保护接口 | **401** | 安全链拦住了未认证请求 |
| 成员打管理员接口 | **403** | 认证过了，但角色不够 |
| 管理员打管理员接口 | **200** | 规则没把该放行的也拦了 |

如果只测 401，你只能证明"没登录进不来"，证明不了"登录了但角色不够也进不来"——
后者才是越权的常见形态。

---

## 2. 设计：两个测试 + 三条守卫

| 部分 | 作用 |
|---|---|
| 参数化用例 | 验证"现在的行为是对的" |
| 覆盖守卫 | 验证"每个接口都被提到了" |
| 完整性守卫 | 验证"每个接口都测了匿名，且管理员用例配了成员用例" |

---

## 3. 代码逐行

### 3.1 用例表

```java
record Case(HttpMethod method, String pathPattern, Role role, int expectedStatus) {}

static Stream<Case> matrix() {
    return Stream.of(
        new Case(GET,  "/api/v1/health",                    null,       200),
        new Case(POST, "/api/v1/auth/login",                null,       400),
        new Case(POST, "/api/v1/auth/refresh",              null,       401),
        new Case(POST, "/api/v1/auth/logout",               null,       200),
        new Case(GET,  "/api/v1/invites/{token}",           null,       200),
        new Case(POST, "/api/v1/invites/{token}/accept",    null,       400),
        new Case(GET,  "/api/v1/me",                        null,       401),
        new Case(GET,  "/api/v1/me",                        Role.MEMBER, 200),
        new Case(GET,  "/api/v1/me",                        Role.ADMIN,  200),
        new Case(POST, "/api/v1/admin/invites",             null,       401),
        new Case(POST, "/api/v1/admin/invites",             Role.MEMBER, 403),
        new Case(POST, "/api/v1/admin/invites",             Role.ADMIN,  200));
}
```

三个细节值得说：

**① `pathPattern` 写的是带 `{token}` 的模式，不是具体路径。**
执行时把 `{token}` 替换成真实邀请码。这样"覆盖守卫"能直接用字符串比对，
不需要处理"具体路径 vs 模式路径"的差异。

**② 公开接口的期望码不一定 200。**

```java
new Case(POST, "/api/v1/auth/login", null, 400),   // 空 body → 校验失败
```

`400` 在这里不是"失败"，而是**证明请求到达了 Controller**：如果被安全链拦下，
拿到的是 401，400 根本不会出现。这是"公开但不需要 200"的标准测法。

**③ `null` 表示匿名**，不用另造一个枚举值。

### 3.2 执行：一个参数化测试

```java
@ParameterizedTest(name = "[{index}] {0} {1} 作为 {2} => {3}")
@MethodSource("matrix")
void 权限矩阵_三身份访问每个端点_状态码符合预期(Case testCase) throws Exception {
    String path = testCase.pathPattern().replace("{token}", inviteTokenValue);

    MockHttpServletRequestBuilder builder = request(testCase.method(), path)
            .contentType(APPLICATION_JSON)
            .content(bodyFor(testCase.pathPattern()));

    String token = testCase.role() == null ? null
            : testCase.role() == Role.ADMIN ? adminToken : memberToken;
    if (token != null) builder.header("Authorization", "Bearer " + token);

    int actual = mockMvc.perform(builder).andReturn().getResponse().getStatus();
    assertThat(actual).as("%s %s 作为 %s", ...).isEqualTo(testCase.expectedStatus());
}
```

准备好三样东西：**token（按身份）**、**路径（替换 token 占位符）**、**body（按接口）**。

token 直接用 `JwtService` 签，不走登录接口——否则每个用例都要登录一次，
既慢，又会撞上 1.4 的登录限流。

### 3.3 覆盖守卫：扫出所有已注册接口

```java
@Test
void 每个已注册接口都必须出现在矩阵里() {
    Set<String> covered = new TreeSet<>();
    matrix().forEach(c -> covered.add(c.method() + " " + c.pathPattern()));

    Set<String> registered = new TreeSet<>();
    for (Map.Entry<RequestMappingInfo, ?> entry : handlerMapping.getHandlerMethods().entrySet()) {
        for (String pattern : entry.getKey().getPatternValues()) {
            if (!pattern.startsWith("/api/")) continue;
            entry.getKey().getMethodsCondition().getMethods()
                    .forEach(m -> registered.add(m.name() + " " + pattern));
        }
    }

    assertThat(covered).as("未登记的接口：%s", ...).containsAll(registered);
}
```

`RequestMappingHandlerMapping` 是 Spring MVC 在启动时建立的"路径 → 处理方法"映射表。
遍历它，就能拿到**当前真正对外暴露的全部端点**——这是唯一可信的来源，比人工维护的清单可靠。

> 注意：这个类有两个实现 bean（`requestMappingHandlerMapping` 和
> `controllerEndpointHandlerMapping`），注入时要加 `@Qualifier`，否则启动报
> `NoUniqueBeanDefinitionException`。

### 3.4 完整性守卫：把 Q-05 机械化

覆盖守卫有个漏洞：它只保证"这个接口被提到过"，不保证"低权限角色被验证过"。

```java
@Test
void 矩阵完整性_每个接口都有匿名用例_且管理员用例必配成员用例() {
    byEndpoint.forEach((endpoint, cases) -> {
        // ① 每个接口都要有匿名用例
        assertThat(cases.stream().anyMatch(c -> c.role() == null))
                .as("%s 缺少匿名用例：未登录时它给什么？", endpoint).isTrue();

        // ② 用了 ADMIN 身份，就必须同时有 MEMBER 用例
        boolean hasAdmin  = cases.stream().anyMatch(c -> c.role() == Role.ADMIN);
        boolean hasMember = cases.stream().anyMatch(c -> c.role() == Role.MEMBER);
        assertThat(!hasAdmin || hasMember)
                .as("%s 有管理员用例，但缺少成员用例（Q-05）", endpoint).isTrue();
    });
}
```

**为什么是"有管理员就必须有成员"**：只测"管理员能进"证明不了角色分界。
必须再测"成员进不去（403）"，才能证明 `hasRole("ADMIN")` 真的生效了。

## 4. 验证守卫真的会红

**测试写完不代表它有用。** 一个永远绿的守卫，比没有更糟——它给你虚假的安全感。

做法：故意删掉一行用例，跑一次，看它是否失败。

```
删掉：new Case(POST, "/api/v1/admin/invites", Role.MEMBER, 403)

结果：
[ERROR] PermissionMatrixTest.矩阵完整性_...:198
[POST /api/v1/admin/invites 有管理员用例，但缺少成员用例（Q-05：必须验证低权限角色被拒）]
```

**第一次写的守卫没抓住。** 当时规则是"如果这个接口有 403 期望，就必须有成员 403 用例"——
删掉之后，这个接口就没有 403 期望了，条件直接不成立，校验被跳过。

改成"有 ADMIN 用例就必须有 MEMBER 用例"才真正生效。**这就是为什么要验证守卫。**

## 5. 一个编译器坑（顺手记下）

用备份还原文件时：

```powershell
Copy-Item $backup $file -Force     # 保留了备份的旧时间戳
mvn verify                          # → 跑的是修改前的 class！
```

`Copy-Item` 会保留源文件的 `LastWriteTime`。还原后文件时间戳比编译产物还旧，
Maven 的增量编译认为"class 比源码新"，**跳过重编译**。

现象很迷惑：文件内容明明是对的，测试却还按旧逻辑跑。

修法：还原后 `touch` 一下（或 `mvn clean`）。

## 6. 这套东西的价值与边界

**价值**：

- 新增接口不登记 → CI 红
- 管理员接口没测成员 403 → CI 红
- 接口漏了匿名用例 → CI 红

**边界**（它证明不了的）：

| 它证明不了 | 该由谁证明 |
|---|---|
| "只能改**自己**的成果"这种资源归属 | Service 层的归属校验 + 对应单测（S-01） |
| 数据是否泄漏（比如响应里带了别人的邮箱） | 具体接口的响应断言 |
| SQL 注入、越权查询 | 代码评审 + 参数化查询（D-15） |

矩阵管的是"**门**有没有锁"，不管"进屋之后能不能翻别人抽屉"。后者要在实现里做。

## 7. 动手练习

1. 写 `Case` 记录与 `matrix()` 用例表

4. 写完整性守卫：每个接口有匿名用例；有 ADMIN 就必须有 MEMBER
5. **故意删一行用例，确认守卫会红**，再恢复

## 8. 自测题

1. 为什么权限测试要按"身份"逐层测，而不是只测"匿名 401"？
2. 公开接口（比如登录）为什么要断言 400 而不是 200？
3. 覆盖守卫从哪里拿到"所有已注册接口"？为什么不手工维护清单？
4. 覆盖守卫有什么漏洞？完整性守卫补了什么？
5. 为什么矩阵里用 `{token}` 占位符而不是具体路径？
6. 为什么 token 直接用 JwtService 签，而不是每个用例先调登录接口？
7. 矩阵能证明"成员不能改别人的成果"吗？为什么？

<details>
<summary>答案</summary>

1. 只测匿名 401 只能证明"没登录进不来"；越权最常见的形态是"登录了、角色不够也能进"，必须再测成员 403、管理员 200。
2. 400 证明请求**到达了 Controller**（参数校验失败），说明它没有被安全链拦下——这才是"公开"的证据。若被拦下会是 401。
3. 从 `RequestMappingHandlerMapping` 遍历，那是 Spring MVC 运行时真正的路由表，不可能漏；手工清单会忘记同步。
4. 覆盖守卫只保证接口被提到过，不保证角色维度测全。完整性守卫要求每个接口有匿名用例、且 ADMIN 用例必配 MEMBER 用例。
5. 让守卫可以直接做字符串比对（具体路径每次不同），也让新增路径参数无需改结构。
6. 登录接口有 1.4 的限流（5 次/10 分钟），每个用例登一次会撞限流；直接签证也快得多。
7. 不能。矩阵管"门有没有锁"，资源归属属于"进屋后能翻哪个抽屉"，要在 Service 里做归属校验并单独测（S-01）。

</details>

## 9. 术语

| 名词 | 一句话 |
|---|---|
| 权限矩阵 | 接口 × 身份的表格，每格一个期望状态码 |
| 参数化测试 | 一份代码 + 多组数据，跑出多个用例 |
| `RequestMappingHandlerMapping` | Spring MVC 的"路径 → Controller 方法"映射表 |
| 覆盖守卫 | 断言"实现里有的，测试里也必须有" |
| 门禁（Gate） | 一批任务的验收线，不过不进下一批 |
| Q-05 | 规范里"每个权限敏感接口必须有 403 用例"那一条 |
