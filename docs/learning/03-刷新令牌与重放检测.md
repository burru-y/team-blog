# 03 · 刷新令牌：轮换与重放检测（零基础版）

> **前置**：[00-零基础必读](./00-零基础必读.md) §2（Cookie）、§5（无状态）；[02-JWT认证](./02-JWT认证.md)。
> **本篇目标**：读懂"兑换券"这套机制，并理解为什么撤销必须写在独立事务里。
> **对应代码**：`auth/{RefreshToken,RefreshTokenService,SessionRevoker,AuthService,RefreshCookie,RefreshTokenCleaner}`

---

## 0. 先讲人话

上节讲到：access token 只有 30 分钟有效期，这样泄漏了也不怕。

但用户不干："我每半小时就要重新登录一次？"

于是加一张**长期兑换券**：

```
通行证（access token）：30 分钟，丢了就丢了
兑换券（refresh token）：7 天，藏好，用来换新通行证
```

平时用通行证；它过期了，就拿兑换券去换一张新的。用户全程无感。

问题来了：兑换券有效期 7 天，**一旦被偷，贼能换 7 天的新通行证**。

这一节解决的就是这个问题。

---

## 1. 先理解问题

### 1.1 最朴素的做法，以及它为什么不够

```
登录 → 发一张 refresh token（7 天），存数据库
刷新 → 检查它还有效吗？有效就发新 access token
```

漏洞：这张兑换券在 7 天里**怎么用都行**。贼偷到之后，和用户"共用"同一张券，
服务端完全看不出异常——因为两边用的都是合法凭据。

**关键洞察：要发现被盗，就必须让"用过的券"不能再被用。**

### 1.2 轮换：用一次就换一张

```
登录 → 券1
刷新 → 券1 作废，发券2
刷新 → 券2 作废，发券3
```

现在券被偷了，会发生什么？

```
情况 A：贼先用券2 → 用户下次刷新时，发现券2 已作废 → 判定"有人重放" → 撤销全部
情况 B：用户先用券2 → 贼再用券2 时，同样触发
```

**不管谁先用，第二次使用一定暴露。** 这就是轮换的全部价值：把"7 天的静默泄漏"
压缩成"一次刷新之内必然暴露"。

### 1.3 发现之后怎么办？—— 全量撤销

发现重放时，你**无法判断**哪一方是贼：

- 可能是贼偷了券
- 可能是用户的浏览器并发刷新（两个标签页）

安全的假设只有一个：**这个账号的凭据已经泄漏**。所以：

1. 该用户所有 refresh token 全部作废
2. `token_version++`，让已签发的 access token 也立刻失效

代价是用户要在所有设备重新登录一次。**这是安全决策，不是技术限制。**

### 1.4 那登出呢？—— 两类"作废"必须分开

用户点"退出"，也要把当前这张券作废。但如果和"轮换作废"混在一起：

```
用户点退出 → 券作废
前端手滑又刷新一次 → 服务端以为"有人在重放" → 把用户所有设备踢下线
```

所以要在作废时记录**原因**。本项目用表里现成的 `replaced_by_id`：

| 作废原因 | `replaced_by_id` | 再次出现时 |
|---|---|---|
| 轮换（被新券替换） | 有值 | **重放** → 全量撤销，401 `SESSION_REVOKED` |
| 登出 | 为空 | 客户端重试 → 只拒绝，401 `UNAUTHENTICATED` |

## 2. 设计：三个问题

| 问题 | 答案 | 关键点 |
|---|---|---|
| 券长什么样？ | 32 字节随机数，Base64URL | 库里只存 SHA-256 哈希 |
| 怎么换？ | 每次刷新：作废旧券 + 发新券 | 用 `replaced_by_id` 记住替换关系 |
| 怎么撤销？ | 独立事务里批量作废 + `token_version++` | 见 §3.3，最容易写错的地方 |

## 3. 代码逐行

### 3.1 实体：只存哈希

```java
@Entity
@Table(name = "refresh_tokens")
public class RefreshToken {

    @Id private UUID id;

    @Column(name = "user_id", nullable = false)
    private UUID userId;

    @Column(name = "token_hash", nullable = false, length = 64, updatable = false)
    private String tokenHash;

    private OffsetDateTime expiresAt;
    private OffsetDateTime revokedAt;
    private UUID replacedById;

    @Column(name = "ip_hash", length = 64)
    private String ipHash;
}
```

**为什么存哈希不存明文**：库被拖走时，明文 refresh token 等于"所有人的账号"。
明文只在签发那一瞬间存在（写进 Cookie），库里只有 SHA-256。

**为什么这里用 SHA-256 而不是 BCrypt**：refresh token 是 32 字节**随机数**，没有"弱口令"
一说，不存在字典攻击。BCrypt 慢 250ms 是为了对抗人想出来的密码；对随机串用它纯属浪费。

**为什么只存 `user_id` 不建关联**：刷新时只要 id，不需要加载用户对象。少一次 join。

### 3.2 轮换：`rotate`

```java
@Transactional
public RotationResult rotate(String rawToken) {
    RefreshToken current = repository.findByTokenHash(hash(rawToken))
            .orElseThrow(() -> new BusinessException(UNAUTHENTICATED, "刷新凭据无效"));
    // ① 找不到：伪造或已清理

    if (current.isRevoked()) {
        if (current.getReplacedById() != null) {
            sessionRevoker.revokeAll(current.getUserId(), "refresh token 重放");   // ②
            throw new BusinessException(SESSION_REVOKED, "凭据已被使用过，已退出全部设备");
        }
        throw new BusinessException(UNAUTHENTICATED, "登录已失效，请重新登录");     // ③
    }

    if (current.isExpired(now)) {
        throw new BusinessException(UNAUTHENTICATED, "登录已过期，请重新登录");     // ④
    }

    String rawNext = newRawToken();
    RefreshToken next = RefreshToken.issue(current.getUserId(), hash(rawNext), now, refreshTtl);
    repository.save(next);
    current.replaceWith(next, now);        // ⑤ 作废旧券 + 记下被谁替换
    return new RotationResult(current.getUserId(), rawNext, next.getExpiresAt());
}
```

① 找不到：可能是伪造，也可能是过期被清理任务删了——都按"无效"处理。
② 被轮换掉的旧券又出现 → 重放 → 全量撤销。
③ 登出作废的券又出现 → 只拒绝（见 §1.4）。
④ 过期 → 让用户重新登录。
⑤ 作废和替换在**同一个事务**里完成，不可能出现"旧券作废了但新券没发出去"。

### 3.3 `SessionRevoker`：为什么必须新开事务

这是本节最难、也最容易写错的地方。先讲清楚事务是什么。

**事务** = 一组操作要么全成功、要么全不做。

```java
@Transactional
public void doSomething() {
    step1();          // 成功了
    step2();          // 成功了
    throw new RuntimeException();   // 抛异常
}
// 结果：step1、step2 全部撤销（回滚），数据库里像什么都没发生
```

Spring 的规矩：**方法抛 RuntimeException，整个事务回滚。**

现在看问题代码：

```java
@Transactional
public RotationResult rotate(...) {
    if (isReplay) {
        revokeAll(userId);                          // 更新 revoked_at
        throw new BusinessException(SESSION_REVOKED); // ← 抛异常！
    }
}
```

顺序是：撤销 → 抛异常 → **事务回滚 → 撤销被撤销**。

结果：检测到重放 → 用户收到 401 → **但攻击者的会话完好无损**。

而且**测试是绿的**（异常确实抛了、状态码确实 401），线上却完全没防住。这是最危险的那类 bug。

修法：把撤销放进**独立的事务**，先提交，再抛异常。

```java
@Service
public class SessionRevoker {

    @Transactional(propagation = Propagation.REQUIRES_NEW)   // ← 新事务
    public void revokeAll(UUID userId, String reason) {
        OffsetDateTime now = OffsetDateTime.now(clock);
        List<RefreshToken> active = repository.findByUserIdAndRevokedAtIsNull(userId);
        active.forEach(t -> t.revoke(now));
        repository.saveAll(active);

        userRepository.findById(userId).ifPresent(User::invalidateSessions);  // token_version++
    }
}
```

`REQUIRES_NEW` 的含义：**暂停调用方的事务，开一个新事务，提交后再回到调用方**。
所以撤销先落库，调用方随后回滚也影响不到它。

**两个必须注意的点**：

1. **必须是另一个 bean。** 如果在同一个类里自调用（`this.revokeAll(...)`），
   不经过 Spring 的事务代理，`REQUIRES_NEW` 完全不生效。
2. **测试不能用 `@Transactional` 包住。** 新事务的数据会提交到测试事务之外，回滚管不到
   （详见 §7.2）。

### 3.4 `RefreshCookie`：四个属性

```java
ResponseCookie.from("rt", rawToken)
        .httpOnly(true)                        // JS 读不到 → XSS 偷不走
        .secure(properties.cookieSecure())     // 只走 HTTPS
        .sameSite("Lax")                       // 跨站请求不带
        .path("/api/v1/auth")                  // 只发给认证端点
        .maxAge(properties.refreshTtl())       // 7 天
        .build();
```

| 属性 | 防什么 | 不写的后果 |
|---|---|---|
| `HttpOnly` | JS 读取 | 一段 XSS 就能偷走 7 天会话 |
| `Secure` | 明文链路截获 | 公共 WiFi 下被中间人拿走 |
| `SameSite=Lax` | CSRF | 别的网站能借你的登录态发请求 |
| `Path` | 无谓的传输 | 每个接口都白带 200 字节 |

**为什么 `Path` 不能窄到 `/api/v1/auth/refresh`**：登出也要读这张券。太窄的话浏览器
在 `/logout` 上不带 Cookie，用户点"退出"退不掉。

**为什么 refresh token 不放响应体**：放进去就意味着前端要用 JS 读它、存它，
一次 XSS 就偷走 7 天会话。`HttpOnly` 是这条链路里最便宜的安全措施。

### 3.5 清理任务：为什么留 30 天

```java
@Scheduled(cron = "0 30 4 * * *", zone = "Asia/Shanghai")
public void purgeExpiredTokens() {
    refreshTokenService.purgeExpired(Duration.ofDays(30));
}
```

每次登录、每次刷新都插一行，不清会无限增长。

**但不能删太早**：重放检测依赖"已作废的券还在库里"。删早了，重放会变成"查不到 → 401"，
和普通过期**无法区分**，泄漏就永远发现不了。

## 4. 两条时间线

### 4.1 正常刷新

```
10:00 登录         → 发 access(30min) + 券1，库里存 hash(券1)
10:25 用户刷新     → 找到券1，未作废、未过期
                    → 作废券1（revoked_at=10:25, replaced_by_id=券2）
                    → 发券2，返回新 access
10:50 用户刷新     → 找到券2 …… 依此类推
```

### 4.2 券被盗

```
10:00 登录 → 券1
10:10 用户刷新 → 券2（券1 作废，replaced_by=券2）
10:15 贼拿着券1 来刷新
      → 找到券1，revoked_at 有值，replaced_by 有值
      → 判定重放
      → SessionRevoker：该用户所有券作废 + token_version++
      → 返回 401 SESSION_REVOKED
10:16 用户手里的券2 也失效了（被全量撤销）
      → 用户被要求重新登录（所有设备）
```

**代价是用户被踢**，但换来的是"贼也进不去了"。

## 5. 五个容易写错的细节

### 5.1 撤销写在同一个事务里（最致命）

见 §3.3。表现：测试全绿、线上无效。

### 5.2 不区分两类作废

登出后前端又刷新一次 → 被当重放 → 把用户所有设备踢下线（见 §1.4）。

### 5.3 `Path` 设成 `/api/v1/auth/refresh`

登出时浏览器不带 Cookie，`logout` 拿不到券，登出实际没生效——但接口返回 200，
用户以为退了，其实券还在有效期内。

### 5.4 测试用 `@Transactional` 包住重放用例

```java
@Transactional                       // 测试事务
@Test void 重放() { ... revokeAll() } // REQUIRES_NEW，已提交
// 测试结束 → 回滚外层事务 → 但 revokeAll 的数据留在了库里
```

跑几次之后库里堆满垃圾，甚至影响后面的用例。重放用例必须**不加** `@Transactional`，
用 `@AfterEach` 显式清理。

### 5.5 清理任务删太早

见 §3.5。删早了，重放检测失效。

## 6. 反面教材

| 写法 | 后果 |
|---|---|
| 不轮换 | 券能用满 7 天，被盗无法发现 |
| 轮换后不记 `replaced_by_id` | 无法区分"重放"和"登出重试" |
| 撤销与抛异常同事务 | 撤销被回滚，防护形同虚设 |
| 撤销放在同类方法里（自调用） | `REQUIRES_NEW` 不生效，同上 |
| refresh token 放响应体 | 前端要存，XSS 一偷就是 7 天 |
| 只存明文 token | 库泄漏 = 全员账号失守 |
| 过期即删 | 重放检测失效，泄漏永远发现不了 |
| 登出只清 Cookie 不作废库里记录 | 券还能被复用（攻击者手里有） |

## 7. 测试怎么写

### 7.1 服务层：轮换、过期、登出、清理

包在 `@Transactional` 里，每条用例自己造数据、结束回滚（Q-09）。

```java
@Test
void 轮换_旧票作废且指向新票() {
    var first = service.issue(user.getId());
    var rotation = service.rotate(first.rawToken());

    RefreshToken old = repository.findByTokenHash(RefreshToken.hash(first.rawToken())).orElseThrow();
    assertThat(old.isRevoked()).isTrue();
    assertThat(old.getReplacedById()).isNotNull();
    assertThat(rotation.rawToken()).isNotEqualTo(first.rawToken());
}
```

### 7.2 集成测试：为什么不能加 `@Transactional`

重放用例会触发 `REQUIRES_NEW` 的撤销，那是**独立事务、会真正提交**。测试事务回滚管不到它。

```java
@SpringBootTest
@AutoConfigureMockMvc
// 注意：这里没有 @Transactional
class AuthIntegrationTest {

    @AfterEach
    void cleanUp() {
        createdUsernames.forEach(n -> userRepository.findByUsername(n).ifPresent(userRepository::delete));
    }
}
```

删用户会级联删掉它的 refresh token（V1 的 `ON DELETE CASCADE`），保证下次跑还是干净的。

### 7.3 验收用例

```java
// 1) 登录拿券1
// 2) 用券1 刷新 → 券2
// 3) 再用券1 → 401 SESSION_REVOKED
// 4) 用券2 刷新 → 401（已被全量撤销）
// 5) 用第 2 步拿到的 access 访问 /me → 401 SESSION_REVOKED（token_version 变了）
```

第 5 步是关键：证明"全量撤销"不只撤了券，连已经发出去的通行证也作废了。

## 9. 自测题

1. access token 已经能撑 30 分钟了，为什么还要 refresh token？
2. 轮换具体做了什么？不轮换会怎样？
3. 检测到重放时，为什么撤销**全部**会话，而不是只拒这一次？
4. `SessionRevoker` 为什么必须 `REQUIRES_NEW`？写在同一事务会怎样？
5. 为什么撤销方法必须放在另一个 bean 里？
6. 为什么 refresh token 不能放在响应体里？
7. 登出导致的作废和轮换导致的作废，为什么要用 `replaced_by_id` 区分？
8. 清理任务为什么保留 30 天？
9. 为什么重放用例不能用 `@Transactional`？

<details>
<summary>答案</summary>

1. access 短命是为了限制泄漏窗口，但用户不能每 30 分钟重登；refresh 让用户无感续期。
2. 作废旧券、发新券、记录替换关系。不轮换的话一张券能用满 7 天，被盗无法发现。
3. 重放说明券至少被两方持有，但无法判断谁是贼；撤销全部是唯一安全的假设，同时让 access 也失效。
4. 它要在抛异常之前**提交**。同一事务里抛 RuntimeException 会回滚，撤销不落库，等于没防。
5. 自调用不经过 Spring 的事务代理，`REQUIRES_NEW` 不生效。
6. 放响应体意味着前端要用 JS 存它，一次 XSS 就偷走 7 天会话；HttpOnly Cookie 让 JS 读不到。
7. 轮换作废的券再出现是重放信号（要全量撤销）；登出作废的券再出现只是客户端重试（不能误伤）。
8. 重放检测依赖"已作废的券还在库里"；删早了就分不清"伪造"和"过期"。
9. 重放会调用 `REQUIRES_NEW` 的事务，那是独立提交，测试事务回滚管不到，会留下脏数据。

</details>

## 10. 术语

| 名词 | 一句话 |
|---|---|
| refresh token | 长期兑换券，用来换新的 access token |
| 轮换（rotation） | 每用一次就换一张新券，旧的作废 |
| 重放（replay） | 拿已作废的旧券再用一次，通常意味着被盗 |
| 事务（transaction） | 一组操作要么全成、要么全不成 |
| 回滚（rollback） | 撤销事务里已做的改动 |
| `REQUIRES_NEW` | 挂起当前事务，开一个独立事务（提交后不影响外层） |
| 事务代理 | Spring 用代理对象包住 Service，事务逻辑在代理里 |
| httpOnly | Cookie 属性，JS 读不到 |
| SameSite | Cookie 属性，控制跨站是否携带 |
| 级联删除 | 删主表行时自动删子表行（`ON DELETE CASCADE`） |
