# 05 · 一次性邀请注册（零基础版）

> **前置**：[00-零基础必读](./00-零基础必读.md) §4（哈希）、§6（并发）；[01-用户实体层](./01-用户实体层.md)。
> **本篇目标**：理解"一次性凭证"怎么做到真正一次性，以及并发下最容易翻车的地方。
> **对应代码**：`admin/{AdminInvite,AdminInviteRepository,AdminInviteService,AdminInviteController}`, `auth/RegistrationController`

---

## 0. 先讲人话

这个站不开放注册。为什么？因为它是团队博客——**谁能进来是件需要控制的事**。

所以流程是：

```
管理员生成一条邀请链接 → 发给要入职的人 → 他点开、填用户名密码 → 成为成员
```

邀请链接本质上是一张"注册资格券"：

- 谁拿到都能用（所以不能公开张贴）
- 用一次就该作废（否则一条链接能拉无限的人）
- 有有效期（否则半年后翻到旧聊天记录还能注册）

听起来简单，但"用一次就作废"在**并发**下有个经典陷阱。这一节的重点就在那里。

---

## 1. 先理解问题

### 1.1 直接开放注册会怎样

```
任何人 POST /register → 成为 MEMBER → 能发内容、能看成员列表
```

一个团队博客，第二天就能进来 500 个机器人。所以注册必须由管理员"发放资格"。

### 1.2 邀请码为什么不能明文存库

如果有人拖了你的数据库：

| 存储方式 | 后果 |
|---|---|
| 明文 | 所有未使用的邀请都能直接用，攻击者批量注册 |
| **哈希**（本项目） | 拿到哈希也没用——邀请码是 32 字节随机数，反推不出来 |

这和 1.3 的 refresh token 是同一个思路：**"凭证"不落明文，只在签发那一刻返回一次**。

### 1.3 "只用一次"的陷阱：先查再改会翻车

最直觉的写法：

```java
AdminInvite invite = repo.findByToken(token);
if (invite.isUsed()) throw new BusinessException("已使用");   // ① 检查
invite.markUsed(now);                                        // ② 标记
createUser(...);                                             // ③ 建号
```

单线程没问题。但两个人**同时**提交呢？

```
时间 ──────────────────────────────────────────►

线程A： ① 读到 used_at = null   ─┐
线程B： ① 读到 used_at = null   ─┼─ 两个都认为"没人用过"
线程A： ② 写入 used_at = 时间A  ─┤
线程B： ② 写入 used_at = 时间B  ─┤  后写的覆盖先写的，但两边都没报错
线程A： ③ 创建账号 user_a        ─┤
线程B： ③ 创建账号 user_b        ─┘  结果：一张邀请拉进来两个人
```

这叫 **TOCTOU 竞态**（Time-of-Check to Time-of-Use，"检查时和使用时状态不一样"）。

**修法：把"检查"和"修改"合并成一条数据库语句。**

```sql
update admin_invites
   set used_at = now()
 where id = ?
   and used_at is null      -- ← 条件写在 SQL 里
```

数据库执行这条语句时会**锁住那一行**，两个请求排队：

```
线程A：update ... where used_at is null → 影响 1 行（成功占位）
线程B：update ... where used_at is null → 影响 0 行（条件不满足）
```

于是"谁先到谁赢"由数据库保证，代码里只要看**影响行数**。

## 2. 设计：三个问题

| 问题 | 答案 |
|---|---|
| 邀请码怎么生成、怎么存？ | 32 字节随机数，Base64URL；库里只存 sha256 |
| 怎么保证只用一次？ | 条件更新 `where used_at is null`，看影响行数 |
| 邮箱怎么绑定？ | 邀请上带了邮箱就以邀请为准，忽略请求里的 |

## 3. 代码逐行

### 3.1 实体

```java
@Entity
@Table(name = "admin_invites")
public class AdminInvite {

    @Id private UUID id;

    @Column(name = "token_hash", nullable = false, length = 64, updatable = false)
    private String tokenHash;

    private String email;          // 可空：指定了就必须用它

    @Enumerated(EnumType.STRING)
    private Role role;

    @Column(name = "created_by", nullable = false)
    private UUID createdBy;        // 谁发的，用于审计

    private OffsetDateTime expiresAt;
    private OffsetDateTime usedAt; // 用过的留痕，不删行
}
```

**为什么用过的邀请不删掉**：删了就分不清"链接用过"（410，用户能理解）和
"链接根本不存在"（404，多半是拼错了）。留一行数据换一个准确的提示，很划算。

**为什么 `tokenHash` 是 `updatable = false`**：邀请码不该被改。改了就相当于换了一张券，
而表里还有唯一约束 `uq_invite_hash`——真改会撞约束报错，不如在映射上直接禁止。

### 3.2 仓储：一条带条件的更新

```java
@Modifying
@Query("update AdminInvite i set i.usedAt = :now where i.id = :id and i.usedAt is null")
int markUsedIfUnused(@Param("id") UUID id, @Param("now") OffsetDateTime now);
```

**返回值是 `int`**：受影响行数。1 = 占位成功，0 = 被别人抢先。

**`@Modifying` 是必须的**：告诉 Spring Data "这是改数据的语句，不是查询"。
不加会报错（它默认按查询处理，期待返回结果集）。

> 注意：这种批量更新**不会同步更新内存里的实体**。所以后面不要再读 `invite.isUsed()`
> 来判断——那个对象还是旧值。判断只认影响行数。

### 3.3 兑换：先占位，再建号

```java
@Transactional
public User accept(String rawToken, String usernameRaw, String passwordRaw, String emailRaw) {
    AdminInvite invite = loadUsable(rawToken);                       // ① 存在、未用、未过期
    OffsetDateTime now = OffsetDateTime.now(clock);

    int claimed = inviteRepository.markUsedIfUnused(invite.getId(), now);
    if (claimed == 0) {
        throw new BusinessException(INVITE_INVALID, "邀请已被使用");  // ② 抢占失败
    }

    String email = invite.getEmail() != null ? invite.getEmail() : normalizeEmail(emailRaw);
    if (email == null) throw new BusinessException(VALIDATION_FAILED, "请填写邮箱");

    String username = User.normalizeUsername(usernameRaw);
    if (userRepository.existsByUsername(username)) throw new BusinessException(CONFLICT, "用户名已被占用");
    if (userRepository.existsByEmail(email)) throw new BusinessException(CONFLICT, "邮箱已被占用");

    User user = User.create(username, email, passwordEncoder.encode(passwordRaw), invite.getRole());
    return userRepository.save(user);                                // ③ 建号
}
```

**为什么顺序是"先占位、再建号"而不是反过来**：

- 先建号再占位：两个并发请求都建出账号，然后一个占位失败——多了一个孤儿账号
- 先占位再建号：占位失败的直接抛异常，一个账号都不会建；建号失败（用户名重复）时
  整个事务回滚，占位也一起撤销

**为什么用户名重复要让事务回滚**：这样用户换个名字重试时，邀请还是可用的。
如果占位已提交、建号失败，用户就"白丢了一张邀请"，得找管理员重发。

**邮箱为什么以邀请为准**：邀请可能是 HR 发给"张三"的，写明 `zhangsan@company.com`。
如果允许注册时随便填，就变成"谁拿到链接都能用别人的身份注册"。

### 3.4 权限：规则只放一处

```java
// SecurityConfig
.requestMatchers("/api/v1/invites/**").permitAll()      // 注册人还没有账号
.requestMatchers("/api/v1/admin/**").hasRole("ADMIN")   // 管理员域
.anyRequest().authenticated()
```

`hasRole("ADMIN")` 匹配的是权限 `ROLE_ADMIN`——JWT 过滤器里就是这么塞的：

```java
new SimpleGrantedAuthority("ROLE_" + user.getRole().name())
```

**为什么不在 Controller 里再写一遍 `if (!isAdmin) throw 403`**：两处判断早晚不一致
（一处改了另一处忘了）。URL 规则是唯一入口；将来需要"资源归属校验"（比如"只能改自己的成果"），
才在 Service 里加，因为那种校验依赖数据，URL 表达不了（S-01）。

## 4. 完整时间线

### 4.1 正常流程

```
T0  管理员 POST /api/v1/admin/invites {"email":"newbie@example.com","role":"MEMBER"}
    → 生成 32 字节随机码，库里存 sha256
    → 返回 {"token":"x7Kd...","expiresAt":"+7天"}
    → 管理员把它拼成链接发给对方

T1  受邀者打开注册页 GET /api/v1/invites/x7Kd...
    → 200 {"email":"newbie@example.com","role":"MEMBER","expiresAt":...}
    → 页面显示："这是给 newbie@example.com 的邀请，还有 6 天"

T2  提交 POST /api/v1/invites/x7Kd.../accept {"username":"newbie01","password":"..."}
    → 查库里存在、未用、未过期
    → 条件更新：used_at = now（影响 1 行）
    → 建账号，返回 201 + 用户资料
```

### 4.2 第二次使用

```
T3  同一个链接再提交
    → loadUsable 发现 usedAt 不为空
    → 410 {"error":{"code":"INVITE_INVALID","message":"邀请已被使用"}}
```

### 4.3 并发（两个请求同时到）

```
线程A：条件更新 → 1 行  → 继续建号 → 201
线程B：条件更新 → 0 行  → 抛 INVITE_INVALID → 410
```

只有一个成功。这不是"尽量"，是数据库行锁保证的。

## 5. 五个容易写错的细节

### 5.1 先查再改（TOCTOU）

见 §1.3。表现：测试怎么跑都过，上线后偶尔出现"一张邀请注册了两个账号"。

### 5.2 邀请码明文存库

见 §1.2。库被拖走 = 所有未用邀请作废。

### 5.3 用 404 而不是 410

- 404："这东西不存在"（可能是拼错了链接）
- **410 Gone**："这东西存在过，但已经不能用了"（用过、过期）

用 410 才能让注册页给出"这张邀请已被使用，请联系管理员"这种可行动的提示。

### 5.4 邮箱让用户随便填

见 §3.3。指定了邮箱的邀请，注册时必须忽略请求里的邮箱。

### 5.5 管理员权限写在 Controller 里

两处判断早晚不一致。URL 规则一处，资源归属校验在 Service 一处。

## 6. 反面教材

| 写法 | 后果 |
|---|---|
| `if (used) throw; invite.markUsed()` | 并发下两个人都注册成功 |
| 邀请码明文存表 | 库泄漏 = 所有邀请可用 |
| 用过就删行 | 分不清"用过"和"不存在"，提示错误 |
| 邀请指定了邮箱但仍采信请求 | 谁拿到链接都能冒名注册 |
| 先建号再占位 | 占位失败留下孤儿账号 |
| 占位用独立事务提交、建号在外层 | 建号失败后邀请已消耗，用户白丢一张 |
| 删除用户时不先删邀请 | `created_by` 外键挡着，删不掉（本项目测试踩过） |

## 7. 测试怎么写

### 7.1 单测覆盖不到并发

`AdminInviteServiceTest` 是 `@Transactional` 的，所有操作在同一个事务里串行执行——
**测不出"两个事务同时改一行"**。

所以并发这件事，用两个可验证的替代品：

1. **直接调两次 `markUsedIfUnused`**，断言第一次 1、第二次 0（证明"条件更新只成功一次"）
2. **集成测试里调用两次 accept**，断言第二次 410（证明"业务层确实依赖这个返回值"）

真正的并发压测要起多个线程 + 独立事务，成本高、还容易 flaky。当前两条已经覆盖了
**"逻辑依赖的机制"**。

### 7.2 集成测试的清理顺序（踩过）

```java
@AfterEach
void cleanUp() {
    inviteRepository.deleteAll();                 // 必须先删邀请
    createdUsernames.forEach(n -> ...delete);     // 再删用户
}
```

`admin_invites.created_by` 是外键指向 `users(id)`，且没有 `ON DELETE CASCADE`。
先删用户会报外键冲突——清理顺序错了，测试会"越跑越脏"。

### 7.3 验收用例

```java
// 第 1 次：201
mockMvc.perform(post("/api/v1/invites/" + token + "/accept")...).andExpect(status().isCreated());
// 第 2 次：410
mockMvc.perform(post("/api/v1/invites/" + token + "/accept")...).andExpect(status().isGone());
```

## 9. 自测题

1. 为什么邀请码不能明文存数据库？
2. "先查再改"在并发下会发生什么？数据库怎么解决？
3. 为什么兑换顺序是"先占位、再建号"而不是反过来？
4. 为什么用 410 而不是 404？
5. 邀请指定了邮箱，注册时为什么不能用请求里的邮箱？
6. 为什么"用过"的邀请不直接删掉？
7. 管理员权限为什么不写在 Controller 里？
8. 为什么单测测不出并发？现在用什么替代验证？

<details>
<summary>答案</summary>

1. 库被拖走时，明文邀请等于"所有未使用的注册资格"，攻击者可以批量注册。
2. 两个请求都读到 `used_at = null`，都认为可用，于是都建号。用一条 `update ... where used_at is null` 让数据库行锁保证只有一个成功，看影响行数判断。
3. 先建号再占位：占位失败会留下孤儿账号。先占位再建号：失败直接抛异常，且建号失败会回滚占位。
4. 410 表示"曾经存在但已不可用"，能给出"已被使用/已过期"的可行动提示；404 表示"不存在"，会让人以为链接拼错了。
5. 否则谁拿到链接都能用别人的身份注册；邀请上的邮箱才是"这批资格是给谁的"的真相。
6. 为了区分"用过"（410）和"不存在"（404），给用户准确提示。
7. 两处判断早晚不一致。URL 规则一处；依赖数据的归属校验放 Service。
8. 单测的 `@Transactional` 让操作串行、同事务，测不出两个事务并发改同一行。改用"条件更新返回 1/0"和"第二次 accept 返回 410"两个可验证的替代品。

</details>

## 10. 术语

| 名词 | 一句话 |
|---|---|
| 邀请码 | 一次性的注册资格凭证 |
| 哈希存储 | 只存摘要，不存明文，库泄漏也反推不出原值 |
| TOCTOU 竞态 | 检查和使用之间状态被改了，导致判断失效 |
| 条件更新 | `update ... where 条件`，用影响行数判断是否抢到 |
| 影响行数 | SQL 实际改了几行（0 表示条件不满足） |
| `@Modifying` | 告诉 Spring Data 这是改数据的语句 |
| 410 Gone | 资源曾经存在，现在不能再用了 |
| 行锁 | 数据库在更新一行时锁住它，其它事务排队 |
| 外键约束 | 子表引用的父表行不能随便删（除非级联） |
